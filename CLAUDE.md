# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**Seance** is TheLounge's Vue 3 client turned into a static, bouncer-less IRC client. The browser speaks IRCv3 directly to **nefarious2** (EvilNet's ircd) over a WebSocket — one IRC line per WS message, `text.ircv3.net` subprotocol — with no Node server in between. The target ircd is nefarious2's **`ircv3.2-upgrade` branch** (`master` has neither WebSocket nor the IRCv3.2 caps). Goal: a `public/` tree an IRC network can rebrand via `config.json` and ship as its own web/PWA/native client.

**Status** (see `docs/projects/initial_conversion.md` for the checklist): phases 0 (discovery), A (server moved to `attic/`), B (bus stubbed), C (minimum IRC) are done; D (fill-in) is done except D.7 read markers/`MARKREAD` and D.11 web push (both deferred); E is in progress — E.3 branding is done, E.1 dependency purge is underway, E.2 bus-contract reshape is optional, E.4 native shells not started. Milestones M4 (daily-driver) and M5 (shippable) are not yet ticked.

Upstream is still `github.com/thelounge/thelounge`; divergence only grows. localStorage keys are still `thelounge.*` (renaming needs a migration). Node.js >= 22, Yarn 1 (classic), MIT licensed.

## Common commands

`yarn` is not on PATH on this machine — use `corepack yarn <cmd>` (or `npx` for one-offs).

| Task                                                      | Command                                       |
| --------------------------------------------------------- | --------------------------------------------- |
| Install deps                                              | `yarn install`                                |
| Build the SPA (webpack → `public/`)                       | `yarn build` (`NODE_ENV=production` for prod) |
| Webpack watch                                             | `yarn watch`                                  |
| Serve the built SPA                                       | `python3 -m http.server -d public 8000`       |
| Lint everything (eslint + prettier + stylelint)           | `yarn lint`                                   |
| Auto-format                                               | `yarn format:prettier`                        |
| Full test (lint + mocha)                                  | `yarn test`                                   |
| Mocha only (builds first)                                 | `yarn test:mocha`                             |
| Mocha without the spec glob                               | `yarn test:nospec`                            |
| Coverage                                                  | `yarn coverage`                               |
| Install git pre-commit hook                               | `yarn githooks-install`                       |
| Playwright e2e (builds first, needs `SEANCE_E2E_IRC_URL`) | `yarn test:e2e`                               |

There is no `yarn dev`/`yarn start`; build and serve `public/` statically.

Run a single mocha file:

```sh
npx cross-env NODE_ENV=test TS_NODE_PROJECT='./test/tsconfig.json' \
  npx mocha --config=test/.mocharc.yml test/irc/client.ts
```

`yarn test:mocha` runs `webpack --mode=development` first because `test/tests/build.ts` inspects `public/`. Live tests (`test/irc/*.live.ts`) are `describe.skip` unless `SEANCE_IRC_URL` is set:

```sh
SEANCE_IRC_URL=wss://localhost:8443/ npx cross-env NODE_ENV=test \
  TS_NODE_PROJECT='./test/tsconfig.json' npx mocha --config=test/.mocharc.yml test/irc/client.live.ts
```

`SEANCE_IRC_CHANNEL` overrides the channel the newer files join (default `#seance`), so they can be pointed at a public network. They relax TLS verification for `localhost` only (self-signed dev cert). Run live files **one at a time** — they share module singletons (the bus spy, the network manager, the id allocator) and time out waiting for `init` when several run in one mocha process (verified 2026-08-25: all pass individually, 4/6 fail combined; the ircd was not throttling). Making them coexist is an open follow-up. Quick headless smoke check after a build (expects the connect form and no console errors):

```sh
chromium --headless=new --disable-gpu --virtual-time-budget=5000 \
  --dump-dom http://127.0.0.1:8000/ | grep -c 'id="connect"'
```

## Dev IRC server

`tools/nefarious-dev/run.sh` runs nefarious2 in Docker (`-d` to detach; `docker logs -f nefarious-dev`). It bind-mounts `tools/nefarious-dev/ircd.conf` + `local.conf`, generates a SAN-bearing self-signed cert into `tmp/nefarious-dev/ircd.pem`, and publishes on 127.0.0.1: `6667` plain IRC, `6697` IRC/TLS, `8067` `ws://`, `8443` `wss://`. Server name `irc.seance.test`, network `SeanceDev`, test channel `#seance`, oper `seanceop`/`seance`. No services, so no SASL/accounts locally; `CHATHISTORY_REQUIRE_AUTH` is off and `IPCHECK_CLONE_LIMIT` is raised because the test suites reconnect a lot.

Image (build once from the gitignored `tmp/nefarious2` checkout — see the header of `run.sh`): a single `docker build -t nefarious2:ircv3 .` of stock `ircv3.2-upgrade`, then `docker tag nefarious2:ircv3 nefarious2:ircv3-fixed` so `run.sh`'s default keeps working. No patch is needed any more — the two images are the same build, and `ircv3-fixed` survives only as a compatibility alias.

The WebSocket bugs that used to require a local branch (details and transcripts in `docs/resources/nefarious2-websocket.md`) — **#97** plain-port WS handshake corrupted by pre-101 auth notices, **#98** inbound frames >= 528 bytes disconnect, **#99** upgrade requests >= 512 bytes hang (browsers send ~550) — were **merged upstream 2026-08-28** (PR [#101](https://github.com/evilnet/nefarious2/pull/101), `fceb160`), together with the client-cert follow-up: dedicated WebSocket ports no longer demand a client certificate, and `websocket=autodetect` ports use ALPN to spot browsers, so headless Chromium no longer trips `ERR_SSL_CLIENT_AUTH_CERT_NEEDED` and a TLS pass-through proxy is no longer required. `tmp/nefarious2` is on `ircv3.2-upgrade` at `346a1c0` (2026-09-11). A dev image older than `aef2f29` rewrites C0 control bytes to U+FFFD in WS text mode — the symptom is every echoed `/me` rendering as raw `�ACTION …�`; rebuild the image, the client is not at fault.

`node tools/irc-ws-probe.mjs wss://localhost:8443/ nick [--insecure] [--binary] [--stay]` is a dependency-free CAP/NICK/USER probe that prints every line.

## Architecture

Two TypeScript trees (`client/`, `shared/`) share `tsconfig.base.json`; `tsconfig.json` references only those.

### `client/` — the app

Vue 3 + Vuex + Vue Router SPA built by webpack (`webpack.config.ts`) into `public/`. Components in `client/components/` (`.vue` SFCs); app logic in `client/js/` (`store.ts`, `router.ts`, `store-settings.ts`, `commands/` for UI-only slash commands, `helpers/`); themes in `client/themes/` (one CSS file each, `coffee` is the default; `docs/resources/themes.md`); service worker `client/service-worker.js` (offline shell, web push: one raw IRC line per push, parsed/stripped/merged by `client/js/push/*`, bundled as `js/push.js` and loaded with `importScripts`; see `docs/projects/push-payload-multiline.md`).

- **`client/js/boot.ts`** — boot sequence: `loadBranding()` (`config.json`) → commit static `configuration.ts` → apply stored settings → `appLoaded` → drop splash → handle `?uri=`/query params → route to the last channel or `Connect` → `autoconnectSavedNetworks()`, last, once the page has its route: the saved networks flagged autoconnect are dialed whatever page the URL opened on (a reload on Settings or Help brings them back too; the connect form no longer does this on mount). Importing `./irc/manager` registers the IRC bus handlers.
- **`client/js/foreground.ts`** — browser-side "the app is back": `visibilitychange`/`online`/bfcache `pageshow` call `reconnectAll()` (`irc/manager.ts`, de-bounced), which dials waiting networks now and probes open sockets (`WsTransport.probe()`: PING, 10 s of silence = dead socket → normal reconnect). The Capacitor shells do the same from `native.ts`.
- **`client/js/pwa.ts`** — installed-app glue: registers `service-worker.js` (secure contexts only), captures `beforeinstallprompt` into `store.state.installPromptAvailable` (Settings → "Install … as an app"), consumes `window.launchQueue` so `web+irc:` links reuse the running window (manifest `launch_handler: focus-existing`), and flags a new build when a newly activated worker announces a build token other than the page's own (`client/js/build.ts`; Help offers a reload) — `checkForUpdate()` re-fetches the worker script from the foreground hooks and hourly, since browsers only look on a page load. The token (`resolveBuild` in `webpack.config.ts`) is a hash of version and commit, `dev` in a development build. `tools/pwa-check.mjs <url>` asks headless Chromium for its installability verdict; see `docs/resources/pwa.md`.
- **Last opened conversation** — `Chat.vue` reports what it shows to `client/js/helpers/lastChannel.ts` (Vue-free, `test/helpers/lastChannel.ts`; `thelounge.state.lastChannel` = `{network uuid, target}`; channels and queries, never the lobby). On the next page load `socket-events/network.ts` opens it as soon as the network is announced (the autojoin channels are already placeholders) or waits in the lobby for its `join` (a query is reopened with `/query` on `network:status`); opening anything else first calls that off. None of that on a page the user opened on purpose — settings, help, the changelog, a network's edit form, search results (`router.ts` `onStandalonePage()`): a network announced there (boot's autoconnect) and its registration's `init` leave the view where it is, the networks come up in the sidebar and the remembered conversation waits for the user; the connect form is nowhere, so from there the view always moves. Browser check: `tools/scenarios/reload-on-settings.mjs`. A notification deep link (`helpers/pendingTarget.ts`) on the network wins and resolves the same way. `join.shouldOpen` is true for windows the user asked for (`/join` via `IrcClient.requestJoin`, `/query`; a `/whois` no longer opens a query — its summary follows the user, `docs/projects/reply-routing.md`); a join nobody asked for (a held session's restore, a forced join, an incoming query) never moves the view. `ChatInput.vue` focuses the input when a conversation opens unless `helpers/device.ts` `hasVirtualKeyboard()` says a touch-primary device would pop its on-screen keyboard; a click on the sidebar row of the conversation already open changes no route, so `ChannelWrapper.vue` asks for the caret with the `input:focus` eventbus event instead. The composer shows that it has the caret: `#form:focus-within` colours its top edge (accent in the Ink & Amber themes, the input focus green in `style.css`) and the caret takes the accent, since a caret alone is a thin blinking line that is easy to miss. Browser check: `tools/scenarios/input-focus.mjs` (every way into a conversation, also `--mobile`).
- **Touch and iOS** — `client/js/helpers/viewport.ts` publishes the visual viewport as `--viewport-height` on touch-primary devices (iOS never shrinks the layout viewport for the keyboard; `body` and `#viewport` in `style.css` are sized and positioned from it) and `html[data-keyboard="up"]` while a text field has focus and the visual viewport is shorter than the window — the one gate for rules that make room for the keyboard (the home-indicator strip under `#form`). Never gate those on `#input:focus`: iOS's shake-to-undo alert dismisses the keyboard and hands the field its focus back without it (phone-measured 2026-09-12). `router.ts` makes every `router.push` a `replace` so the history stays one deep and iOS's edge swipe has nothing to go back to; what used to mean "back" (Escape on Help, the Android shell's back button) calls `leavePage()` instead — never add a `router.push` call site expecting history. On touch the message action toolbar opens on a tap (`Message.vue` `actions-open`, one message at a time) because long press is a text selection there; `Sidebar.vue`'s swipe stands down under a selection and inside text fields, and ends cleanly on `touchcancel`. The composer lets iOS's Return newline land and removes it (`ChatInput.vue` `onEnterKey`), since cancelling the keypress leaves the shift key stuck; the send button prevents `mousedown` so the keyboard stays up. Browser check: `tools/scenarios/message-actions-single.mjs --mobile`; the keyboard and swipe behaviour need a real device.
- **The iOS status bar** — a home-screen web app on iOS 26+ gets no say over the status bar from `theme-color`, from the manifest's `theme_color` or from `apple-mobile-web-app-status-bar-style`; all three are ignored. What iOS reads is the `background-color` of a **real, painted element** positioned `fixed` (or `sticky`) within 4px of the top of the page, at least 80% wide and tall enough — that is `#status-bar-tint`, a bare `<div>` first in `<body>` (`client/index.html`) styled in `style.css`. Height is the undocumented part and it is the whole ballgame: the community's iOS 26 figure is 3px, **4px was measurably ignored on iOS 27 and 6px is where sampling starts**, so the rule ships 8px. Find no element and iOS falls back to `<body>`, which from 26.2 also renders the page under a feathered blur reaching ~93pt down the screen — that blur is what soft-focuses the channel header, and nothing else removes it (`black-translucent`, `black`, `default`, `viewport-fit=cover` were all measured and all did nothing). Two more disqualifiers: a pseudo-element is never sampled, and neither is a fixed element carrying a `backdrop-filter`. **The element has to paint** — the community's iOS 26 notes have `visibility: hidden` still being sampled and on iOS 27 it is not (measured) — so it covers the first `--status-bar-tint-height` (8px) of the page. Over the chat that is header background and invisible; the sidebar puts its logo there, so `#sidebar` reserves the same variable. Anything else placed flush against the top of the page has to do likewise. The whole rule is behind `(hover: none) and (pointer: coarse)` as well as the `@supports` probe, because on desktop Safari the sidebar is always open and would take the same slice. The colour it takes is `--canvas-bg-color`, the same token `html`'s background uses, so the bar and the chat under it agree in every theme; a theme that does not set it keeps `--body-bg-color`. Verifying any of this needs the icon deleted and re-added — iOS freezes `apple-mobile-web-app-*` at install — and a pixel measurement, not an eye: a 1px hairline peaked at 72 of 230 under the blur and 230 without it.
- **Markdown** — what a message renders as is decided by `layout()` (`client/js/helpers/ircmessageparser/layout.ts`), a Vue-free `LayoutNode` tree: `parseStyle → applyMarkdown → finders → merge → layout tree`, then an adapter — `parse()` (`parse.ts`, the Vue one, which walks the tree with a private `toVNodes`) or `toPlainText` (`Chat.vue`'s `plainTopic`). Markdown itself is `parseMarkdown.ts` (`applyMarkdown` → `{fragments, verbatim}`); neither file imports Vue, the store or the DOM, so mocha loads them: `test/helpers/layout.ts` and `test/helpers/parseMarkdown.ts`. A code block renders through `CodeBlock.vue` (rows, gutter counter, and a `Show all N lines` toggle once it is over 12 lines long — `excerptRange` in `codeLines.ts`, `test/helpers/codeLines.ts`) and `highlighter.ts` (Prism, alias table, lazily imported grammar/flourite chunks — also Vue-free, `test/helpers/highlighter.ts`). `#`–`######` at a line start are headers: a `header` wrap carrying its level, rendered as `.md-header`/`.md-h1`…`.md-h6`. Vocabulary in `CONTEXT.md`; see `docs/projects/markdown-messages.md`.
- **Network header** — the sidebar's lobby row (`NetworkLobby.vue`) is two rows inside one `.channel-list-item[data-type="lobby"]` (one click target, one drag handle, one hover): `.lobby-title` (chevron, network name at full width, unread badge) and `.lobby-status` under it — `.lobby-tools` on the left (connection state, notification bell, edit, join: 1.5rem boxes with a 0.25rem gap, every glyph centred — the bell is a span and needs `text-align: center`, buttons centre by themselves — and all four glyphs FontAwesome solids of about 13px, because the eye measures the gaps between ink, not between boxes: a thin text `+` or a smaller bell reads as uneven spacing; the scenario measures the ink with a canvas) and `.lobby-nick` on the right (the nick this connection uses — `network.nick`, live through the `nick` event; the tools never shrink, a long nick gets an ellipsis). The jump-to results show the same header without the toolbar. Nothing in `yarn test` renders it; browser check: `tools/scenarios/network-panel.mjs`.
- **A conversation on a network that is down** — `ChatInput.vue` `canSend`: in a channel or query the send button is disabled and Enter keeps the draft while `network.status.connected` is false, unless the draft is a slash command (`/connect` has to work from anywhere); the lobby is never gated, its input is for commands. The view fades like a pending message (`Chat.vue` `isDisconnected` → `#chat.disconnected .chat-content`, opacity 0.55) and so do the sidebar rows of that network's channels and queries (`ChannelWrapper.vue` `network-down`; the lobby row turns red as before). A strip above the input (`.connection-bar`, `role="status" aria-live="polite"`) says `Reconnecting to <network> in Ns…` with a "Connect now" button while a retry is pending (`status.retryAt`, the transport's delay sent on the close and dropped when the retry starts dialling; a half-second ticker in `ChatInput.vue` counts it down), `Connecting to <network>…` with a turning glyph while a dial is in flight, or `Disconnected from <network>.` with a Connect button when nothing is being tried (both buttons send the sidebar's `/connect`, which restarts the schedule) — the header spinner stays. Everything is computed from `network.status`, so it clears on registration. Nothing in `yarn test` renders it; browser check: `tools/scenarios/disconnected-channel.mjs`, through `tools/scenarios/lib/irc-proxy.mjs` (a TCP proxy that cuts the socket and refuses dials), also with `--mobile --width=390 --height=844`.
- **Reactions** — a reaction is free text (`👍`, `🎉🎉🎉`, `lol`), so the picker (`ReactionPicker.vue`, opened from the 😀 in the hover toolbar or the `+` at the end of a reaction row) is a search field that doubles as the free-text entry, the nine Unicode groups, and a recents row. It is `<Teleport>`ed to `<body>` and positioned against its anchor (the scrollback would clip it). The catalog is generated from gemoji into `client/js/helpers/emoji-catalog.json` by `tools/generate-emoji-catalog.mjs` and only reached through `loadEmojiCatalog()`, an `import()` that keeps it in its own chunk; searching, `:shortcode:` expansion and `normalizeReaction` are Vue-free in `helpers/emoji.ts`, the MRU list in `helpers/reactionRecents.ts` (`thelounge.reactions.recent`). See `docs/resources/reactions.md`.
- **File uploads** — `client/js/upload.ts` (`Uploader`, Vue-free behind the `UploadHost` interface, `test/irc/upload.ts`) posts straight to the deploy's `uploads` endpoint from `config.json`. Every way in (drop, paste, the paperclip's `#upload-input`) lands in `triggerUpload`, which checks size/type, then **asks before sending**: `UploadHost.confirm(files)` → the `upload:confirm` eventbus request that `UploadPreview.vue` (mounted in `App.vue`) answers with the files the user kept. Progress is real (`XMLHttpRequest` via `xhrFetch`, wrapped into a `Response`; `UploadHost.progress` → `store.state.uploadProgress` → the `.upload-bar` strip above the input in `ChatInput.vue`, with cancel = `Uploader.abort()`, which is silent) — **but an upload listener forces a CORS preflight**, which curl-oriented uploaders (litterbox: `OPTIONS` → 405) refuse, so `xhrSend` retries a request that died before any progress as a plain POST and `Uploader.progressBlocked` remembers the endpoint for the page (indeterminate bar); a preset or deploy that knows better sets `uploads.progress: false` (litterbox does) and no preflight is ever tried. Never add headers or listeners to the upload request without checking the endpoint answers `OPTIONS`. The "remove metadata" setting re-encodes through a canvas, which keeps one frame, so `metadataPlan()` exempts GIF/SVG and anything `helpers/animatedImage.ts` sniffs as animated (WebP `VP8X` flag, PNG `acTL`, AVIF `avis`; `test/helpers/animatedImage.ts`); a re-encoded file takes the blob's real type and a matching extension (`fileNameForType`). See `docs/resources/branding.md` § Uploads.
- **Settings backup** — Settings → General → Backup and restore exports a gzipped JSON envelope (`.seance-settings`, `CompressionStream`, no dependency) of the preference keys in localStorage — `settings` (the store's live object, since the key is only written once a setting changes), saved networks (passwords stripped unless the box is ticked), sort orders, mutes, ignore lists, trusted media, recent reactions — and restoring one replaces exactly those keys and reloads; `thelounge.sts`, `thelounge.push*`, `thelounge.mentions` and `thelounge.state.*` are never carried or written. `client/js/helpers/settingsBackup.ts` is Vue-free (`test/helpers/settingsBackup.ts`); browser check `tools/scenarios/settings-backup.mjs`. See `docs/resources/settings-backup.md`.
- **Settings is a modal** — `/settings/*` routes are unchanged (deep links, reloads, `onStandalonePage()` all still hold), but `Windows/Settings.vue` renders them as a pane over a dimmed backdrop covering the whole app, sidebar included (absolute in `#viewport`, above the sidebar's z-index): a header (title + ✕), a horizontal tab strip (`Settings/Navigation.vue` — the pane is the `settings` size container; below 48rem the inactive tabs drop to icons only, the active tab keeps its label, and the active tab is scrolled into view on route change), a body that scrolls by itself, and a fixed footer whose Done button is `leavePage()` — settings apply instantly, there is no Save. Escape closes it too (`keybinds.ts`, never from inside a form field), as do ✕ and a backdrop click; on ≤768px the pane is the whole screen. Consequence: nothing behind the backdrop is clickable, so a scenario leaves settings through Done before touching the sidebar. Browser check: `tools/scenarios/settings-modal.mjs` (also `--width=390 --height=844`).
- **Command aliases** — Settings → Aliases defines user slash commands (`thelounge.aliases`, carried by the settings backup). All logic is `client/js/helpers/aliases.ts` (Vue-free, `test/helpers/aliases.ts`): `$1`…`$9`, `$2-`, `$*`, `$chan`, `$me`, `$$`; multi-line bodies are one command per line; nested aliases expand to a depth cap and a name already being expanded falls through, so an alias can wrap the built-in it shadows. `ChatInput.onSubmit` expands before the UI-only command check (never while editing; `//` escapes) and emits each line as its own `input`; alias names join command autocompletion. Editor: `Settings/Aliases.vue` — rows saved as they become valid, inline errors, a live "Try it" preview — and the `/alias` IRC-layer command (`irc/commands/alias.ts`, `test/irc/commands.ts`): bare it lists (monospace block), `/alias <name>` shows one, `/alias <name> <commands>` creates or overwrites in place; deletion stays in Settings. See `docs/resources/aliases.md`; browser check: `tools/scenarios/aliases.mjs`.
- **Web push** — `client/js/webpush.ts` (Vue + store, so not under mocha) keeps **one push subscription per network**: a browser holds one subscription per service-worker registration, bound to one VAPID key, and every ircd announces its own key, so each push-enabled network gets its own registration of `service-worker.js` at `push/<uuid>/` (`client/js/push/scope.ts`, `test/push/scope.ts`; the worker reads its network from `self.registration.scope`, is push-only there — no shell cache, no fetch handling, deep links to the app URL — and re-registers with that network alone). **Nothing but the page refreshes those workers**: no navigation ever happens inside `push/<uuid>/`, a push event re-checks the script at most once a day and `register()` with the same URL checks nothing, so `syncStoredWithBrowser` calls `registration.update()` on every stored network's registration at boot (and `ensureRegistration` on reuse) — otherwise a device that subscribed before a deploy keeps the old worker, old actions and old reply path included; browser check: `tools/scenarios/push-worker-update.mjs`. Entries live in `thelounge.push` keyed by network uuid with the key they were made against (`helpers/pushStore.ts`, `test/helpers/pushStore.ts`; the old per-key map is migrated, its endpoints UNREGISTERed as networks connect). On `webpush:available` the entry is re-REGISTERed when its key matches; otherwise the connect-time prompt (`PushPrompt.vue`, yes/no/never, naming the network) asks to `subscribe` (skipped when permission is already granted — it just subscribes; `thelounge.push.neverAsk`) or to `renew` — governed by the `pushKeyChange` setting (Wary `ask` prompt / Naive `trust` renew silently / Suspicious `ignore`; the prompt's Never sets `ignore`). **A rotation is never healed silently by default**: `pushSubscription()` drops the differently-keyed browser subscription first (`helpers/pushKeys.ts`), `subscribe(uuid)` unregisters the replaced endpoint on that network, and `refreshState` reports `stale`: Settings → Notifications says so, and the Edit-network form offers Renew for that network (`networkPushInfo(uuid).stale`, `webpush.renew(uuid)`). Browser flows: `tools/scenarios/push-renew.mjs` (rotation policies) and `push-per-network.mjs` (two networks, migration), both on the per-registration fake in `tools/scenarios/lib/fake-push.mjs`. See `docs/projects/push-per-network.md`. **A reply typed into a notification is one IRCv3 reply**: it answers the notification's newest message (`replyTo` = its msgid → `+draft/reply` via the `send` bus emit, the throwaway connection when the server offers `message-tags`, or the outbox), the worker asks open pages one at a time with a `deadline` the page honours (a page that thaws later must not send it again), and the worker records what it showed in the page's `seen` ring so a push delivered twice shows nothing (`addMessage` is idempotent by msgid). **A multiline message is pushed one line at a time in `draft/multiline`'s fallback form** — `batch=<base msgid>` on every line, the msgid on the first line only, the batch's `time` and the `evilnet.github.io/line=<i>/<sent>/<total>` ordering tag on every line — so the worker groups lines by the `batch` tag, backfills the entry's msgid from whichever line brings it, and checks the `seen` ring by msgid, by batch reference (the opener's msgid the page recorded) and by `<batch>#<index>`; tests pin the shape in `test/push/line.ts` and the harness. Actions are `[Mark read, Reply]`. **Mark read is the account's read marker at the notification's newest message** (`data.time`, the click's time when the push carried none): the worker asks an open page first (`{type: "markread", …, deadline}`, answered through the `markread` bus emit → `IrcClient.markRead` → `handlers/markread.ts` `markReadAt`, which sends `MARKREAD <target> timestamp=<time>` at once and moves the channel's own marker forward so the debounced path never follows with an older one), then its own throwaway connection with `draft/read-marker` requested (`swMarkRead`; `swIrcOpen` takes the optional caps to ask for — a `FAIL`, a 421 or a server without the cap is "not sent"), then the same `outbox` as a reply (entries carry a `type`) — never the app, a marker is nothing to type. The notification closes locally whatever happened; the server relays the marker to every push subscription, which is what closes it on the other devices. Browser check: `tools/scenarios/push-mark-read.mjs` — nefarious2 defaults the `CAP_draft_read_marker` feature to **off** and the rig's conf does not set it, so the scenario switches it on for the run through the rig's oper (`tools/scenarios/lib/rig-feature.mjs`) and back off after. Harness: `test/tests/service-worker.ts` (the real worker in a `vm` sandbox with a scripted ircd). See `docs/projects/push-subscription.md` § A reply is one reply and § Mark read replaces Mute 30m.
- **`client/js/socket.ts`** — `EventBus`, an in-process replacement for socket.io-client. `on/once/off` subscribe to server→client events, `dispatch(event, payload)` fires them; `emit(event, payload)` is routed to the single `handle(event, fn)` registered for it (unhandled emits `console.warn`). The `socket.on/emit` call-site shape across `socket-events/*` and components is kept **on purpose** so the IRC layer plugs in without touching ~50 call sites. No networking lives here.
- **`client/js/socket-events/*`** — the bus consumers that mutate the store (`init`, `msg`, `join`, `names`, `network`, `more`, ...). `index.ts` lists them.
- **`client/js/branding.ts`** + **`client/config.json`** — deploy branding schema/loader; `config.json` is copied to `public/` and fetched at runtime, and read by webpack for `index.html`/manifest.

### `client/js/irc/` — the IRC layer

Data flow: `transport.ts` (`WsTransport`: one line per frame, PING/PONG, reconnect backoff, 500-byte guard) → `message.ts` (hand-rolled parser/serialiser, `casemap.ts`) → `caps.ts` / `sasl.ts` / `isupport.ts` → `client.ts` (`IrcClient`: one per network, owns the `SharedNetwork` model and `channel.ts` state) → `handlers/` → `socket.dispatch(...)`. Typed input comes back via `bus.ts` (`socket.handle("input" | "open" | "names" | "more" | "msg:react" | "msg:redact" | "network:*")`) → `commands/`.

- **`handlers/`** — one file per command/numeric exporting `{COMMAND: handler}`; `handlers/index.ts` holds the `modules` list and the `unhandled` fallback. **To add a handler: add a file and one entry in `modules`.**
- **`commands/`** — one file per slash command exporting a `Command`; `commands/index.ts` holds the `modules` list and `dispatchInput`. **To add a command: add a file and one entry in `modules`.** Unknown commands are sent raw.
- **`multiline.ts`** — `draft/multiline`: `parseMultilineValue`/`IrcClient.multilineLimits()` (the one gate the whole feature is behind), `multilineBatch` (a received batch joined into one message, tags off the opener), `planMultiline`/`sendMultiline` (multi-line input as `BATCH … draft/multiline` with `draft/multiline-concat` chunks). **Batches go out one at a time, paced past the server's cooldown**: nefarious2 charges a cooldown per delivered batch and, for a batch opened inside that window, drops the opener while still delivering its lines as standalone messages (they duplicate; blank ones draw `ERR_NOTEXTTOSEND` and the closer `FAIL BATCH NO_ACTIVE_BATCH`). The echo comes back long before the cooldown ends, so the next batch waits out an estimated cooldown too — `batchCooldownMs`, the undiscounted `(2 + bytes/128) s` — held by the queue's `pace` timer (`paceAfter`), set after **every** delivered batch (so the gate outlives the message and the _next_ message's batch is paced too) and timed from **delivery** (the echo, or a settle period without `echo-message`), not from the send, so a batch the server processes late under throttling still starts its cooldown at the right moment. A `FAIL BATCH MULTILINE_COOLDOWN` (estimate too low) still re-sends rather than reports. `FAIL BATCH MULTILINE_*` and the server's per-message `WARN BATCH MULTILINE_FALLBACK` are in `handlers/standard-replies.ts`. See `docs/projects/multiline-messages.md`.
- `manager.ts` (`NetworkManager` registry, `createNetwork`), `bus.ts` (bus handlers, store-free), `history.ts` (`draft/chathistory` + batches; distinct from `client/js/history.ts`, the input history), `catchup.ts` (paced per-channel history/marker fetch after JOIN — the active channel at once, the rest one per 4 s, because ircu-family servers charge ~2 s of fake lag per command and stop reading at 10 s; see `docs/projects/connect-burst.md`), `persistence.ts` (nefarious2's built-in bouncer, `draft/persistence`: after `PERSISTENCE STATUS ON` the autojoin waits for the server's restoration batch, which is applied as state only; also the `PERSISTENCE ATTACH default <msgid>` catch-up cursor — offered in the `CAP END` flush after a successful SASL, its `evilnet.github.io/bouncer-replay` batch appended as new messages, and `catchup.ts` stood down while it is accepted. See `docs/projects/seamless-reconnect.md`), `sts.ts`, `saved-networks.ts` (`thelounge.networks`), `ids.ts` (one shared id allocator across networks; history ids are negative), `errors.ts`, `hostmask.ts`, `wire.ts`, `types.ts`.

### Working in the IRC layer

- `Handler = (client: IrcClient, msg: IrcMessage) => void` (`types.ts`). Handlers mutate the client's model and emit through the client — `client.pushMessage(chan, partial, increasesUnread?)`, `client.findChannel(name)`, `client.isSelf(nick)`, `client.timeOf(msg)` (honours `@time`), `client.lobby`, `client.channels` — never the transport or the store directly. `handlers/away.ts` is a small model.
- `Command = {commands: string[]; allowDisconnected?: boolean; input(ctx)}` with `ctx = {client, chan, cmd, args, rest}`. Build lines with `formatLine(...)` (`message.ts`) or `trailingLine(cmd, params)` (`wire.ts`) and call `client.send(line)`. `commands/away.ts` is a small model.
- UI-only commands (`/collapse`, `/expand`, `/search`, `/join` of an already-listed channel) are intercepted in `client/js/commands/` before the bus sees them; service aliases (`/cs`, `/ns`, ...) pass through raw.
- Event names, payload shapes and store expectations are fixed by `docs/resources/bus-contract.md`; when adding a new event, extend `shared/types/socket-events.ts` and a `socket-events/*` consumer together.
- Replies, reactions, deletion and edits (bus-contract §1.4): `Channel.idByMsgid` / `idOf()` is the msgid → id map; `client.react()` / `redact()` / `editMessage()` send, `handlers/tagmsg.ts` / `handlers/redact.ts` / `privmsg.ts` (`+seance/edit`) dispatch `msg:react` / `msg:redact` / `msg:edit`. **An edit takes its original's place**, own or anyone's: the store (`helpers/messageUpdates.ts` `applyEdit`) moves the new message behind the hidden original and gives it the original's `time` (`editedAt` keeps the edit's), the pending copy of an own edit stands in the same way (`pending.ts` dispatches its `msg:edit`), and an edit raises no unread, no notification and no unread marker unless it highlights. Anything that refers to another message by msgid must go through `client.afterReplay(fn)` so that inside a chathistory replay it runs after the batch's messages have ids. Wire constants (`REPLY_TAG`, `EDIT_TAG`, `REACT_TAG`, `UNREACT_TAG`, `REDACTION_CAP`, `TYPING_TAG`) live in `wire.ts`.
- **Reconnects are quiet, by content not by context.** A reattach can bring the server's join burst several times over (session restore, our re-JOIN, the bouncer's alias attach), so: `topic.ts` prints a 332/333 only when the topic differs from the one the channel shows (`Channel.topicAsked` is the `/topic` escape hatch), `mode.ts` prints a 324 only when the modes differ from `Channel.modeText` (`Channel.modesAsked`, set by a bare `/mode`, is the escape hatch), and a JOIN for a channel already JOINED produces no line and no second `CHATHISTORY`/`MARKREAD`/`MODE` (`Channel.rejoining`, `client.restoring` and the state check in `handleMessage`). The catch-up (`CHATHISTORY AFTER`) is what shows what actually happened. Keep new join-burst handlers consistent with this. The bouncer's own setup chatter (`NOTE BOUNCER ALIAS_ATTACHED`, the `Session resumed…` NOTICE) is silenced by the settling window instead — `persistence.ts` `beginSettling`, opened by _every_ registration, because `PERSISTENCE STATUS` does not reach us on every server's attach path.
- **A SASL login that was asked for must succeed.** When `options.sasl` is set and the exchange does not end in 903, `IrcClient.saslFailed()` reports why in the lobby and — unless the deploy set `features.saslDisconnectOnFail: false` in `config.json` (`saslRequired`) — QUITs instead of registering unauthenticated. That covers missing credentials (caught in `onOpen`, before `CAP LS`), a server with no usable `sasl` cap (`startSasl`), a `CAP NAK` and the 902/904-907 numerics — rejections a retry cannot fix, so the network stays down. The 12 s **timeout** is the one exception: slow services are not a wrong password, so it QUITs and hands the socket to `transport.abandon()`, which reports it as lost and reconnects on the usual schedule (`closeExplained` silences the duplicate close report). `handlers/cap.ts` drops whatever the negotiator had queued once `client.isQuitting`, so no `CAP END` follows the `QUIT`. See `docs/resources/nefarious2-websocket.md` § SASL for what the server does.
- **The retry schedule spaces automatic retries only; anyone who asks restarts it.** `WsTransport.connect()` from outside (the foreground poke `reconnectAll` on a `reconnect-wait` network, a click, `redial()`) zeroes the attempt counter, and so does a socket lost while `probe()` was waiting, so a failed foreground dial waits 1 s next, never the 60 s cap that built up while the app was away. Waits at the cap stay at or above 45 s (jitter `[3/4, 1]`): nefarious2's IPcheck refuses the fourth connection from an address within 40 s gaps and a refusal renews the window (`docs/resources/nefarious2-websocket.md` § Connection throttle). `transport.abandon(reason)` is how a layer above drops a socket without dropping the network. See `docs/projects/seamless-reconnect.md` § Round seven.
- **The catch-up cursor is offered exactly once per connection, and only then.** `IrcClient.cursor` (the newest msgid shown on the network, by `@time`, persisted in `saved-networks.ts`) goes out as `PERSISTENCE ATTACH default <msgid>` from `saslProgress` on SASL _success_, before `CAP END` in the same flush — never without SASL (the server answers `FAIL PERSISTENCE ACCOUNT_REQUIRED`), never after 001, never without the `attach-cursor` token in the `draft/persistence` CAP 302 value, and never with a msgid of 64 bytes or more. While the server accepts it (`client.serverReplay`) the restoration JOINs must not schedule a `CHATHISTORY AFTER` of their own (`persistence.ts` `serverReplayCovers`) — the server's replay is that catch-up, and it arrives as an appended `chathistory` batch, not as `more`.
- Typing notifications (bus-contract §1.5): `client.typing(chan, state)` sends `@+typing=<state> TAGMSG` with the spec's 3 s per-target throttle (`TYPING_INTERVAL_MS`; session reset by `sendMessage`/`onClose`), the `typing` bus emit routes to it in `bus.ts`, and `handlers/tagmsg.ts` dispatches `typing {chan, nick, state}` for other users' tags (never own echo or replay). Tests: `test/irc/typing.ts` (sinon fake timers).
- **Pending outgoing messages** (bus-contract §1.9, `irc/pending.ts`): with `echo-message` a sent line shows at once as a _pending copy_ — a `msg` with `msg.pending: true`, dispatched straight from `pending.ts` (never `pushMessage`) — and `msg:settled {chan, id}` takes it down when the server answers: the echo, a rejection numeric, an `ACK`, `PENDING_TIMEOUT_MS` (60 s) of silence, or the close. The echo is matched by the `@label=s<n>` every outgoing PRIVMSG/NOTICE (and multiline opener) carries under `labeled-response` — nefarious2 relays it on the echo and on the rejecting numeric — so **tests that pin an outgoing line with both caps negotiated expect `@label=s<n>` in front**. The store keeps copies as a trailing block (`helpers/messageUpdates.ts` `insertMessage`) so the echo lands in place. Tests: `test/irc/pending.ts`; browser: `tools/scenarios/pending-messages.mjs`.

## Conventions

- Prettier is enforced (pre-commit hook via `yarn githooks-install`). If `yarn lint` fails, run `yarn format:prettier` first.
- **Size the UI in `rem`, never `px`.** `html { font-size }` is the one UI scale (`:root` in `style.css`; the font-size setting's steps are `html[data-font-size=…] { font-size: N% }`, `medium` = 100% = the browser default, `large` = 125% is the default, the ends run 62.5%–212.5% on purpose, `client/js/helpers/fontSize.ts`; the sidebar is `--sidebar-width`, half rate and capped to the screen), and everything — text, header/footer height, sidebar and user-list width, button padding, icon targets, menus — is `rem`/`em` off it so a step grows the whole interface together and the browser's own font-size preference is honoured. A new `font-size: 14px` or `height: 36px` in the chrome is a bug: it stays put while the rest scales. Media-query breakpoints stay in px (they cannot see the root size); what has to follow the scale asks a **container query** instead — `#chat` is an inline-size container named `chat`, and the message row's three modes are chosen by the pane's width in `ch` and `rem`: columns (time fixed in `ch` per clock setting, nick `flex: 0 1000 12ch` down to a 9ch floor and an ellipsis, text `flex: 1 1 30ch`; the nick gives way first and alike in every row, so the columns stay aligned), the user list as an overlay instead of a side panel once the pane cannot hold the widest gutter, 30 characters of text and the list (`--userlist-width` cannot be read in the condition, so its `6rem + 84px` is spelled out), and the phone's inline flow once the columns alone do not fit — that block used to be the 479px media query. Both `@container chat` blocks sit after every column rule on purpose: same specificity, later wins. Browser check: `tools/scenarios/message-gutter.mjs` (`SEANCE_CLOCK=12h+s` etc.), which sweeps window widths at three font steps with the user list open. The slider itself stays in px (`Appearance.vue` `.font-size-slider`): the control that changes the scale must not change with it. A drag renders only the sample box under the slider (`fontSizeScale` in `helpers/fontSize.ts` must agree with the CSS steps); the page takes the step on release, so nothing moves under the pointer. Browser check: `tools/scenarios/font-size-setting.mjs`.
- `client/` compiles with `strict: true`; `noImplicitAny: false` remains in the tsconfigs with a "TODO: Remove eventually" — write explicit types in new code. No Node built-ins in `client/` (it must bundle for the browser; `transport.ts` uses only the global `WebSocket`).
- **Pipeline the registration exchange.** Lines are processed in order and pre-registration commands are not charged fake lag, so never wait for a reply whose outcome the server already knows: `CAP END` (or the SASL opener) goes out in the same flush as `CAP REQ`, and the active channel's history/marker in the same flush as the `JOIN` (`caps.ts` `pipelineEnd`, `catchup.ts` `prefetchCatchup`).
- **Don't add per-channel commands to the connect path.** Every command costs ~2 s of server-side fake lag and the socket is ignored past 10 s (`docs/resources/nefarious2-websocket.md` § Fake lag). Autojoin is one `JOIN a,b,c` (`joinChannels`), `MODE` is asked lazily on first open, and anything else per channel goes through `catchup.ts`.
- `MAX_LINE_BYTES = 500` (`client/js/irc/message.ts`) caps every outbound line, tags included: nefarious2 kills connections on inbound WS frames >= 528 bytes (#98) and the branch rejects message bodies over 512 bytes as excess flood, and browsers cannot control fragmentation. `splitMessage` chunks long text; do not raise the cap.
- After changing `client/`, run `yarn build` (or `yarn watch`) — the mocha build test and the headless check both read `public/`. `public/` is gitignored and shared by every branch, so it does not change on checkout: rebuild after switching branches.
- **The suite has no browser and no DOM.** No component is ever mounted (the Playwright e2e in `test/e2e/` is the exception, and only against a live ircd), so a change under `client/components/`, `client/css/` or the store is unverified by `yarn test` however green it is. Check those in a real browser (`docs/resources/browser-testing.md`).
- Tests mirror the source under `test/`: `test/irc/*.ts` for the IRC layer, `test/shared/`, `test/helpers/` (`client/js/helpers/`, e.g. `parseMarkdown.ts`, `layout.ts`, `highlighter.ts`), `test/push/` (`client/js/push/`, the service worker's push module), `test/tests/` (`build.ts`, `eventBus.ts`), `test/client/` (browser specs webpack bundles in development mode into `test/public/testclient.js`; ignored by mocha), `test/e2e/` (Playwright, ignored by mocha, needs a built `public/` and `SEANCE_E2E_IRC_URL`). Mocha config `test/.mocharc.yml` (tsx loader, `check-leaks`).
- IRC unit tests use a `FakeTransport` injected through `transportFactory` and drive lines with `transport.line(...)`, asserting on a `sinon.spy(socket, "dispatch")`. **Gotcha:** `test/irc/client.ts` installs that spy in a root-level `beforeEach`, which mocha applies to every file in the run; other files (`multi-network.ts`, `history.ts`, ...) check `socket.dispatch.isSinonProxy` and only `restore()` a spy they own. Follow that pattern in new test files or the suite fails when run together.
- Modules that must run under mocha (`irc/*`, `saved-networks.ts`, `sts.ts`) stay free of store/DOM imports; tests swap storage via `useStorageBackend`.
- Live tests are gated on `SEANCE_IRC_URL` (and `SEANCE_IRC_CHANNEL`, default `#seance`) and need the dev ircd running.
- localStorage keys are still `thelounge.*` (`thelounge.networks`, `thelounge.sts`, `thelounge.mentions`, `thelounge.muted`, `thelounge.media.trusted`, `thelounge.sort.*`, `thelounge.state.lastChannel`, ...). Do not rename without a migration.
