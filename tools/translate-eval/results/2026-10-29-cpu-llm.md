# Which library runs Qwen3-1.7B on the CPU, and how fast (2026-10-29)

The spike from `docs/projects/translation-devices.md` § First step. Two candidates for a CPU copy of the language model, run one at a time in headless Chromium on this host, single-threaded.

## Decision

```
CPU_LLM_LIBRARY        = "wllama"          // @wllama/wllama 3.8.1 (llama.cpp in WebAssembly)
CPU_LLM_COPY           = {source: "unsloth/Qwen3-1.7B-GGUF", file: "Qwen3-1.7B-Q4_K_M.gguf", sizeBytes: 1107409472}
CPU_LLM_PEAK_BYTES     = 2921910272        // peak RSS of the whole Chromium process tree, minus the idle page's (3783143424 - 861233152)
CPU_CONTEXT_WINDOW     = 1024              // tokens; see "The 15 s rule" below: it cannot be met on this host at any window
CPU_BATCH_MAX_LINES    = 2
CPU_REQUEST_TIMEOUT_MS = 360000            // 6 min; 3x the measured 2-line batch (101120 ms) is 303360, which is less
OPUS_GPU_LARGEST_BYTES = 59495424          // en-de fp16 model.shared.weight: [58101, 512] x 2 bytes
```

Why wllama, by the spec's rule (out if it fails to load or the output is wrong; else prefer transformers.js unless its peak is above 2.0 GB where the other's is below, or the other decodes at least 1.5x faster):

- transformers.js **does not load the shipped configuration**: `graphOptimizationLevel` `basic` (the level `seq2seq.real.ts` uses for q8) and `all` both fail with `Can't create a session. ERROR_CODE: 6, ERROR_MESSAGE: std::bad_alloc` (the renderer's tree reached 6.9 GB first). Only `disabled` loads.
- With `disabled` it runs, but at **0.25-0.43 decode tok/s** (wllama 1.17-1.26: wllama is **2.8-3x faster at decode**, past the 1.5x bar) and a **5.86 GB peak** (wllama 2.92 GB). Neither is under 2.0 GB, so the memory clause does not separate them; the decode clause does.
- transformers.js also gave a **wrong output** on the composer-with-context prompt (it did not stop: a rambling answer to 160 tokens, below). wllama answered it correctly.
- In favour of transformers.js, noted for the record: its prefill is **5x faster** (6.4-8.7 tok/s against 1.4-1.6), so a one-line request with a short answer finishes sooner on it (fixture 1: 54 s against 103 s). Not enough to override the rule: an unshippable 5.9 GB heap and a load that only works with the optimiser off.

## Host and harness

- Host: Intel Xeon E5-2680 v4 @ 2.4 GHz (Broadwell, AVX2, no AVX-512), 56 cores, 503 GB. Load average about 5 during the runs. Every run: `nice -n 19 taskset -c 0-3`, one at a time.
- Chromium: Playwright's `chromium-1248` binary (`~/.cache/ms-playwright/chromium-1248/chrome-linux64/chrome`), headless, `--no-sandbox --disable-dev-shm-usage`. No `--js-flags` were needed.
- **Single thread.** The page was served by `python3 -m http.server` with no COOP/COEP headers, so `crossOriginIsolated` is `false` (logged by both workers) and there is no SharedArrayBuffer, which is GitHub Pages' situation. `numThreads = 1` / `n_threads: 1` on top.
- Memory: the driver polls `ps -eo pid,ppid,rss` every 250 ms, sums the RSS of the whole Chromium tree rooted at the browser process, and reports `peak - idle`, the idle page being the same page 3 s after load, before any model work (idle: 847-866 MB; it moves a little between runs).
- Where things live (throwaway, not committed): `/claude-settings/jobs/fd0afeed/tmp/cpu-spike/`
  - `dump.ts` (`npx tsx dump.ts prompts.json`): imports `buildMessages` from `client/js/translate/prompt.ts` (the 1.7B profile is `prompt.ts` itself) and `emptyContext` from `engine.ts`, and writes the messages for fixture lines 1, 2 and 4 of `tools/translate-eval/suite.json`, the polish line `your going to love this` (`purpose: "polish"`), a composer translation with context (topic, names, terms, voice lines and three earlier lines, the 700-token budget's usual shape) and a two-line `read` batch with the same context.
  - `www/`: `index.html` (`?lib=tjs|wllama|opus&only=<indexes>&max=<new tokens>&opt=<session options JSON>`), `worker-tjs.js`, `worker-wllama.js`, `worker-opus.js`, `common.js`; `tjs-wasm.js` and `tjs-gpu.js` are esbuild bundles of `@huggingface/transformers` 4.2.0 from the repo's `node_modules` (`esbuild … --bundle --format=esm --platform=browser`, with `--alias:onnxruntime-web/webgpu=onnxruntime-web/wasm` for the first, as `webpack.config.ts` does, and none for the second); symlinks `models` -> `/seance/tmp/models/cpu-llm`, `ort` -> the repo's `node_modules/onnxruntime-web/dist`, `wllama` -> `node_modules/@wllama/wllama/esm` (installed with `npm i --prefix <scratch> @wllama/wllama@3.8.1`, never into the repo).
  - `drive.mjs <url> <timeout-min>`: launches Chromium through Playwright, polls RSS, prints the workers' `BENCH …` console lines with the current and peak RSS. `EXTRA="--enable-unsafe-webgpu --enable-unsafe-swiftshader --use-webgpu-adapter=swiftshader"` for step 4.
- Prompt rendering for both libraries: ChatML built by hand, `<|im_start|>role\ncontent<|im_end|>\n` per message, then `<|im_start|>assistant\n<think>\n\n</think>\n\n`. Greedy (`do_sample: false` / `temperature: 0`), up to 160 new tokens, stop on EOS / `<|im_end|>`.
- Models in `/seance/tmp/models/cpu-llm/`: `onnx-community/Qwen3-1.7B-ONNX` (`onnx/model_quantized.onnx` 1,742,387,852 bytes, config, tokenizer, generation_config) and `unsloth/Qwen3-1.7B-GGUF` `Qwen3-1.7B-Q4_K_M.gguf` (1,107,409,472 bytes = 1,056 MiB, from the Hugging Face tree API).

```sh
cd /claude-settings/jobs/fd0afeed/tmp/cpu-spike/www && python3 -m http.server 8077 --bind 127.0.0.1 &   # no COOP/COEP
cd .. && nice -n 19 taskset -c 0-3 node drive.mjs 'http://127.0.0.1:8077/?lib=wllama&max=160' 40
nice -n 19 taskset -c 0-3 node drive.mjs 'http://127.0.0.1:8077/?lib=tjs&max=160&opt={"graphOptimizationLevel":"disabled"}' 40
EXTRA="--enable-unsafe-webgpu --enable-unsafe-swiftshader --use-webgpu-adapter=swiftshader" \
  nice -n 19 taskset -c 0-3 node drive.mjs 'http://127.0.0.1:8077/?lib=opus' 15
```

## Step 3: wllama 3.8.1, `unsloth/Qwen3-1.7B-GGUF` Q4_K_M

`loadModelFromUrl` with `{n_ctx: 2048, n_threads: 1, n_gpu_layers: 0, useCache: false}`, the single-thread `wllama.wasm` (8.76 MB) from the package, `createCompletion` on the raw ChatML string, streamed (one chunk per token). Loads in 15.4 s; one harmless warning (`control-looking token: 128247 '</s>' was not control-type`).

**Peak RSS 3,783,143,424; idle 861,233,152; delta 2,921,910,272 (the 2.9 GB `CPU_LLM_PEAK_BYTES`).** The load alone reached 3.78 GB (the 1.1 GB file in JS plus the copy in the heap); generation added nothing (3.4-3.6 GB after). With `n_ctx` 1024 the KV cache is about 115 MB less than at 2048 (28 layers x 8 KV heads x 128 x 2 (K and V) x 2 bytes = 112 KiB a token).

Notes for the engine:

- llama.cpp **reuses the KV cache of the common prefix** between calls (`cached_tokens`: 112-126 tokens, the system prompt). Those requests' first token came at 29-87 s against 92-169 s. The engine should keep the system prompt and context in front and not reset the context between requests.
- Prefill is no faster per token than decode here (about 0.64 s against 0.83 s a token). Single-thread WASM SIMD on this core delivers roughly 4-5 GFLOP/s. `n_batch`/`n_ubatch` were left at the defaults; tuning them was not tried.

## The 15 s rule

The brief asks for a smaller `CPU_CONTEXT_WINDOW` than 1024 if a composer translation with context takes more than 15 s on this host. It takes 107 s with the system prompt cached and about 3 minutes cold (fixture 1: 103 s for a one-line question, no context). The prompt cost is the system prompt plus context (about 140 + 120 tokens), not the window, so the 15 s mark (about 20 uncached tokens at 1.5 tok/s) is below the system prompt alone: no window meets it on this host. So `CPU_CONTEXT_WINDOW` stays at 1024, which holds the 700-token context budget, the prompt and a 160-token answer. Whether another device (a modern laptop or phone, several times this core's speed, and with threads where the page is isolated) meets 15 s is **not measured**; this is a one-host figure. The consequence for the design is that the CPU copy of the language model works but a request takes minutes here; the `CPU_REQUEST_TIMEOUT_MS` of 6 min is what keeps a reading queue from failing on it.

## Step 4: transformers.js `translation`, `Xenova/opus-mt-en-de`, `device: "webgpu"`, `dtype: "fp32"`, SwiftShader

Chromium with `--enable-unsafe-webgpu --enable-unsafe-swiftshader --use-webgpu-adapter=swiftshader`, in a worker. The adapter: vendor `google`, architecture `swiftshader`, `maxStorageBufferBindingSize` and `maxBufferSize` 1,073,741,824, **no `shader-f16`** (the feature list has no such entry). Loaded in 8.7 s; `The build is green, can someone restart the bot?` translated in 78.6 s to `Der Bau ist grün, kann jemand den Bot neu starten?` (one sentence, the right translation; "Bau" for "build" is the model's). Peak RSS 3,755,687,936, delta 2,890,108,928 (fp32 files, 196 MB encoder and 222 MB merged decoder, on the software rasteriser). The code path works as a test seam; the shipped GPU copies are fp16.

**`OPUS_GPU_LARGEST_BYTES`.** Read with the `onnx` Python package (`load_external_data=False`, largest initializers by element count) from `Xenova/opus-mt-en-de` `onnx/encoder_model_fp16.onnx` (97,996,404 bytes) and `onnx/decoder_model_merged_fp16.onnx` (111,275,221 bytes):

| File | Initializer | Dims | Type | Bytes |
| --- | --- | --- | --- | --- |
| `encoder_model_fp16.onnx` | `embed_tokens.weight` | [58101, 512] | FLOAT16 | 59,495,424 |
| `decoder_model_merged_fp16.onnx` | `model.shared.weight_merged_0` | [58101, 512] | FLOAT16 | 59,495,424 |

Next largest in either file: the 512 x 2048 matmuls, 4,194,304 bytes. So `OPUS_GPU_LARGEST_BYTES = 59495424` (56.74 MiB, matching the spec's "~57 MiB"). Other pairs have their own vocabulary sizes and take this figure as an approximation.

## Threads (Task 12, 2026-10-29)

wllama's multithreaded path, for `DESKTOP_THREAD_CAP` (`client/js/translate/threads.ts`; spec § Multithreading).

**There is no separate multi-thread build in 3.8.1.** `esm/wasm/` holds one `wllama.wasm` (the `'multi-thread/wllama.wasm'` path key is deprecated in favour of `default`); `loadModel` starts pthreads at runtime when `isSupportMultiThread()` (a `SharedArrayBuffer` can be posted, the atomics probe validates) and `n_threads > 1`, else it runs single-threaded (`ProxyToWorker(…, 0)`). The thread workers are `blob:` workers the library starts itself. Each run below logged, inside the worker, `crossOriginIsolated=true`, `isMultithread()` (false at 1 thread, true above) and `getNumThreads()` equal to the asked count.

Harness: a copy of the spike's `www/` with `n_threads` from `?threads=`, the `wllama` link pointed at the repo's own `node_modules/@wllama/wllama/esm` (3.8.1), served by a Python server that adds `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: credentialless` (and the `.mjs`/`.wasm` types). The "composer with context" prompt (index 4) alone, in a fresh browser per run, so nothing is cached (`cached_tokens: 0`, 258 prompt tokens, 24 new; every run gave the same output as the spike's single-threaded one). `nice -n 19`, one run at a time; the cores' idle share was read before each run (mostly 90-100 %, one or two of the eight at 30-80 % from other sessions).

Main series, every run on the same eight cores (`taskset -c 0-7`), only `n_threads` changing:

| Threads | Time to first token | Total | Prefill tok/s | Decode tok/s | Total vs the count before |
| --- | --- | --- | --- | --- | --- |
| 1 | 165.2 s | 186.0 s | 1.56 | 1.16 | |
| 2 | 83.4 s | 95.2 s | 3.09 | 2.04 | 1.95x faster |
| 4 | 42.2 s | 48.4 s | 6.12 | 3.86 | 1.97x faster |
| 8 | 24.7 s | 31.4 s | 10.45 | 3.54 | 1.54x faster |

1 → 8 threads: **5.9x** on the total (186.0 s to 31.4 s). Prefill keeps scaling (1.71x from 4 to 8); decode stops at 4 (3.86 against 3.54 tok/s: at a token's few milliseconds of work the barriers cost as much as the extra cores give).

A second series with the taskset as wide as the thread count (1 core for 1 thread, 2 for 2, 4 for 4; the 8-thread run above is the same run) is slower at every count below 8, because the browser's own processes (its main, renderer and GPU process threads) share those cores with the compute threads, and core 0 was 77 % busy with another session's work during the 1-thread run:

| Threads (cores) | Time to first token | Total | Decode tok/s |
| --- | --- | --- | --- |
| 1 (core 0) | 337.6 s | 380.3 s | 0.56 |
| 2 (0-1) | 119.4 s | 137.7 s | 1.31 |
| 4 (0-3) | 51.6 s | 70.6 s | 1.26 |

The rule is the main series' total time (the metric a composer translation waits on): the gain from 4 to 8 threads is 54 %, far over 15 %, so the cap is the most this host may measure:

```
DESKTOP_THREAD_CAP = 8   // 4 -> 8 threads still gained 54 % on the total; counts past 8 not measured (the host's limit for this work is 8 cores)
```

`cpuThreads` leaves one core to the page (`hardwareConcurrency - 1`, so an 8-core laptop runs 7) and takes at most 4 on a phone. Chromium's `navigator.hardwareConcurrency` follows the process's CPU affinity (it reported 8 under `taskset -c 0-7` and 4 under `0-3`), not the host's 56 cores. Peak memory did not change with threads (2.93-3.05 GB over the idle page, against the single-threaded 2.92 GB): the KV cache and the weights are shared, each thread adds only its scratch.

The batch and the deadline (`CPU_BATCH_MAX_LINES` 2, `CPU_REQUEST_TIMEOUT_MS` 6 min) stay as measured single-threaded: they are what a page without isolation (WebKit, a first load) needs.
