# Bus contract for the IrcClient (Phase C)

Reference for whoever writes `client/js/irc/client.ts`. `client/js/socket.ts` is an in-process `EventBus`: `socket.dispatch(event, payload)` (L115) fans a server→client event out to the listeners registered in `client/js/socket-events/*.ts` and components; `socket.handle(event, fn)` (L100) registers the single handler that services a client→server `socket.emit(event, payload)` (L83; unhandled emits `console.warn`). Dispatch is synchronous, listeners are never awaited, and `socket.connected` is not read by anything in `client/`. Types: `shared/types/socket-events.d.ts` (`ServerToClientEvents` L22-102, `ClientToServerEvents` L115-175).

Everything below was read from the code on 2026-08-24; the attic references point at the last TheLounge server (`attic/server/`) for "how did this used to be produced".

### 1.4 Replies, reactions, deletion and edits

Wire behaviour matches poxchat and what nefarious2 (`ircv3.2-upgrade`) actually does — see `docs/resources/nefarious2-websocket.md` for the server facts. Caps involved: `message-tags` (client tags), `echo-message` (our own msgids), `draft/message-redaction` (REDACT; **off by default in nefarious2**, enabled in `tools/nefarious-dev/local.conf`), `draft/chathistory` (reactions and REDACTs are replayed as history).

| Feature | Outbound                                                                                                                                                                                                                                                                                                                                                                                            | Inbound → store                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Reply   | `@+draft/reply=<msgid> PRIVMSG <target> :text` (also on `/me`; never on NOTICE). `+draft/reply` is what poxchat reads; nefarious2 accepts it and the ratified `+reply`.                                                                                                                                                                                                                             | Accept `+reply` and `+draft/reply` → `msg.replyTo = <msgid>`. The parent may not be loaded: the UI resolves it from `channel.messages` when rendering and shows "(unknown message)" otherwise.                                                                                                                                                                                                                                                                                                                                                                               |
| React   | `@+draft/react=<text>;+draft/reply=<msgid> TAGMSG <target>`; remove with `+draft/unreact` (poxchat/nefarious convention, not in the IRCv3 draft). Tag values are escaped per message-tags.                                                                                                                                                                                                          | TAGMSG with `+draft/react` or `+draft/unreact` **and** a reply tag → `msg:react {chan, id, text, nick, remove}` where `id` is the loaded target message. Without a loaded target the TAGMSG is dropped. `+typing` and other TAGMSGs are ignored. Store: `msg.reactions[]`, a nick at most once per text; `remove` deletes the nick and drops the entry at zero.                                                                                                                                                                                                              |
| Delete  | `REDACT <channel> <msgid> [:reason]`. Channels only (nefarious2 answers `FAIL REDACT INVALID_TARGET` for anything else). Server policy: author (unlimited when logged in, else exact `nick!user@host` match), chanops within `REDACT_WINDOW` (300 s default), opers.                                                                                                                                | `:nick!u@h REDACT <target> <msgid> [:reason]` (no tags on the live line; tagged inside chathistory batches, and the deleted message itself is filtered out of later replays) → `msg:redact {chan, id, by, reason?, time}` for a loaded target, else a plain lobby-style line in the channel ("nick deleted a message"). Store: `msg.redacted = {by, reason, time}`; `text` is kept so the UI can offer click-to-reveal. `FAIL REDACT <code>` → an error message in the channel (`REDACT_FORBIDDEN`, `REDACT_WINDOW_EXPIRED`, `UNKNOWN_MSGID`, `INVALID_TARGET`, `DISABLED`). |
| Edit    | No server support anywhere. Client→server emits: `input` gains optional `reply` / `edit` (msgids; only plain text and `/me` honour `reply`, only plain text honours `edit`); `msg:react {target, msgid, text, remove?}`; `msg:redact {target, msgid, reason?}`. Slash commands: `/react <text> [msgid]`, `/unreact <text> [msgid]` (default: the newest message with a msgid), `/redact <msgid> [reason]` (alias `/delete`).

Ordering guarantees: `msg:react` / `msg:redact` / `msg:edit` are only ever dispatched after the `msg` they refer to, with resolved ids — including inside a history replay, where they are applied after the batch's messages are delivered. The IRC layer owns the msgid→id map (`Channel.idByMsgid`); the store never looks msgids up except to render a reply quote.

### 1.5 Typing notifications

`+typing` client tag (https://ircv3.net/specs/client-tags/typing) on `TAGMSG`; needs `message-tags` only. nefarious2 relays it and never stores a `+typing`-only TAGMSG, so nothing arrives in chathistory.

- **Client→server `typing {target, state}`** — the UI reports its own activity, unthrottled: `active` on every input change while the text is non-empty and not a slash command; `paused` after ~5 s without input while text remains; `done` when the input is cleared. Not emitted at all when the `sendTypingNotifications` setting is off. On submit the UI emits `input` first and then clears the field — the IRC layer resets its typing state when it sends the PRIVMSG, so the trailing `done` is a no-op (the message itself ends typing on the receiver).
- **IRC layer** (`IrcClient.typing(chan, state)`): sends `@+typing=<state> TAGMSG <target>` subject to the spec's rule that no two typing notifications are sent within 3 s: `active` is re-sent every 3 s while the UI keeps reporting it; `paused`/`done` are sent once per transition (delayed until 3 s after the previous send if needed, collapsing to the latest state) and only if an `active`/`paused` was announced before. Nothing is sent to the lobby, without `message-tags`, or while disconnected. Sending a PRIVMSG/NOTICE to the target cancels pending timers and resets the state (no `done`).
- **Server→client `typing {chan, nick, state}`** — inbound `+typing` TAGMSG from someone else (our own echo is ignored, ignore list applies, replay ignored) for a loaded channel or query. Store: `ClientChan.typing[]` of `{nick, state, expiresAt}`; an entry expires 6 s after `active`, 30 s after `paused`, immediately on `done`, and when a `msg` from that nick arrives in the channel (or the nick parts/quits/is kicked, where the consumers already exist). UI: a 20 px line above the input — "alice is typing…", "alice and bob are typing…", "alice, bob and 2 others are typing…". poxchat rule for the layout: the line only appears when a typing entry first shows (the scrollback shifts up once), stays as an empty line after the entries go (`ClientChan.typingReserved`), and is released in the same render as the next message appended to that channel, so the message fills the slot and the view never bounces.

## 3. Store and routing expectations

`client/js/store.ts` `State` (L33-49): `networks: ClientNetwork[]`, `activeChannel?: {network, channel}`, `isConnected`, `currentUserVisibleError`, `serverConfiguration`, `appLoaded`, `mentions`, `settings` (module).

- `networks[]`: every entry needs the full `SharedNetwork` shape plus `isJoinChannelShown`/`isCollapsed`; every channel must come from `toClientChan()`. `channels[0]` is assumed to be the lobby (`socket-events/part.ts` L8, `socket-events/quit.ts` L18, `network:name`, `boot.ts` L70, attic `network.ts` L186-196/L671-673). Attic allocated the lobby id before the other channel ids (`client.ts` L345).
- `chan.id`: unique across all networks, used by `findChannel(id)` (L111-121), the `#/chan-<id>` route (`router.ts` L85-89, `RoutedChat.vue` L29-47 sets `activeChannel` from it), and the router guard `router.ts` L118-128 which **refuses navigation to an id that is not yet in the store** — insert the channel before calling `switchToChannel`. `open` ignores ids `< 1`; attic counters started at 1 (`client.ts` L115-116).
- `msg.id`: attic used one monotonically increasing counter per user across all channels (`chan.ts` L65); the client compares ids for the unread marker (`MessageList.vue` L229/L266), `firstUnread`, `more.lastId` and mention dedupe (`mentions.ts` L45-54). Keep it global and increasing.
- `network.uuid`: `findNetwork` (L122-130), `removeNetwork` (L209-214), the `/edit-network/:uuid` route, and the localStorage keys for network order, channel order, mute status and collapse state (`sort.ts` L29-30/L86, `mute.ts` L48/L79, `init.ts` L36-37). Make it stable across reloads (e.g. derived from host+nick or persisted) or those preferences are lost.
- `isConnected`: only `init` sets it `true`, only `error` sets it `false`. Gates sending and history loading (see 1.2).
- `activeChannel`: set by `RoutedChat.vue`, cleared when leaving `RoutedChat` (`router.ts` L130-154, which also marks read and trims to 100 messages). `switchToChannel(chan)` / `navigate(name, params)` are exported from `router.ts` L156-169.
- `serverConfiguration`: static `client/js/configuration.ts` L12-44 committed in `boot()`; `lockNetwork`, `public`, `defaults` (host/port/tls/nick/join/sasl…), `fileUpload: false`, `prefetch: false`.
- Boot (`client/js/boot.ts` L21-75): commit configuration, apply settings, `appLoaded`, wait for the router, then if the route is unknown go to `RoutedChat` of `networks[0].channels[0]` or, with no networks (always, today), `Connect`. `?host=…&nick=…&join=…` / `?uri=web+irc://…` pre-fill the Connect form (L77-102). Navigation before `appLoaded` is deferred (`router.ts` L97-109).

Minimal connect sequence that makes the UI work: allocate ids → dispatch `network` (or `init` with `active` = lobby id) with lobby + configured channels (`state: PARTED`, `totalMessages: 0`, `messages: []`) → `connecting` → on registration `nick`, `network:status {connected:true}`, `network:options` → on JOIN `join` (`state: JOINED`, `index ≥ 1`) → NAMES end `users` (client will ask `names`) → `init` (or a direct `store.commit("isConnected", true)`) so input is enabled → on disconnect `network:status {connected:false}` and, if you want the banner, `error`.
