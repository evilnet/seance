# Web push: implementation map

Moved out of `CLAUDE.md` on 2026-11-02. Design records: `docs/projects/push-per-network.md`, `push-subscription.md`, `push-payload-multiline.md`.

## Web push

**Web push** — `client/js/webpush.ts` (Vue + store, so not under mocha) keeps **one push subscription per network**: a browser holds one subscription per service-worker registration, bound to one VAPID key, and every ircd announces its own key, so each push-enabled network gets its own registration of `service-worker.js` at `push/<uuid>/` (`client/js/push/scope.ts`, `test/push/scope.ts`; the worker reads its network from `self.registration.scope`, is push-only there — no shell cache, no fetch handling, deep links to the app URL — and re-registers with that network alone). **Nothing but the page refreshes those workers**: no navigation ever happens inside `push/<uuid>/`, a push event re-checks the script at most once a day and `register()` with the same URL checks nothing, so `syncStoredWithBrowser` calls `registration.update()` on every stored network's registration at boot (and `ensureRegistration` on reuse) — otherwise a device that subscribed before a deploy keeps the old worker, old actions and old reply path included; browser check: `tools/scenarios/push-worker-update.mjs`. Entries live in `thelounge.push` keyed by network uuid with the key they were made against (`helpers/pushStore.ts`, `test/helpers/pushStore.ts`; the old per-key map is migrated, its endpoints UNREGISTERed as networks connect). On `webpush:available` the entry is re-REGISTERed when its key matches; otherwise the connect-time prompt (`PushPrompt.vue`, yes/no/never, naming the network) asks to `subscribe` (skipped when permission is already granted — it just subscribes; `thelounge.push.neverAsk`) or to `renew` — governed by the `pushKeyChange` setting (Wary `ask` prompt / Naive `trust` renew silently / Suspicious `ignore`; the prompt's Never sets `ignore`). Its No ("not now") lasts for the page: `answerPrompt` records it by kind, network and key, so the reconnects that follow (every registration announces `webpush:available`) do not ask again and a permission granted since (another network's Yes) does not subscribe it silently either; a reload asks once more, a key rotation still brings its renew prompt, and switching the network's push option back on clears it. **The prompt is one at a time**: while it is open, or the `subscribe()` a Yes started is in flight (the browser's permission dialog; `promptHold`, at most `PROMPT_HOLD_MAX_MS` = 60 s), a network that needs the question waits (`waiting`) — a silent subscribe asks nothing and never waits; `scheduleHandoff` — called when the prompt closes and when the Yes's subscribe settles — gives the waiting networks their turn 300 ms later, still connected only, so two networks autoconnecting each get asked (or, after a Yes, subscribe silently). An answer counts only for the network the rendered dialog names and only once the prompt has been up 450 ms (`PROMPT_ARM_MS`, `data-armed` on `#push-prompt`; scenarios wait for it before clicking) — a double-click's second click lands on the next prompt inside that — and a held Escape's repeats answer nothing (`emitEscape(repeat)`; only the prompt ignores them). A prompt closes unanswered when its network disconnects or its push is switched off; switching push off mid-subscribe waits for the run, which re-checks `stillWanted` after every await and stops short of storing or registering. Browser check: `tools/scenarios/push-prompt-every-network.mjs`. **A rotation is never healed silently by default**: `pushSubscription()` drops the differently-keyed browser subscription first (`helpers/pushKeys.ts`), `subscribe(uuid)` unregisters the replaced endpoint on that network, and `refreshState` reports `stale`: Settings → Notifications says so, and the Edit-network form offers Renew for that network (`networkPushInfo(uuid).stale`, `webpush.renew(uuid)`). Browser flows: `tools/scenarios/push-renew.mjs` (rotation policies) and `push-per-network.mjs` (two networks, migration), both on the per-registration fake in `tools/scenarios/lib/fake-push.mjs`. See `docs/projects/push-per-network.md`. **A reply typed into a notification is one IRCv3 reply**: it answers the notification's newest message (`replyTo` = its msgid → `+draft/reply` via the `send` bus emit, the throwaway connection when the server offers `message-tags`, or the outbox), the worker asks open pages one at a time with a `deadline` the page honours (a page that thaws later must not send it again), and the worker records what it showed in the page's `seen` ring so a push delivered twice shows nothing (`addMessage` is idempotent by msgid). **A multiline message is pushed one line at a time in `draft/multiline`'s fallback form** — `batch=<base msgid>` on every line, the msgid on the first line only, the batch's `time` and the `evilnet.github.io/line=<i>/<sent>/<total>` ordering tag on every line — so the worker groups lines by the `batch` tag, backfills the entry's msgid from whichever line brings it, and checks the `seen` ring by msgid, by batch reference (the opener's msgid the page recorded) and by `<batch>#<index>`; tests pin the shape in `test/push/line.ts` and the harness. **The page's own notification for a subscribed network is shown by that network's push worker**, in the push's shape (`socket-events/msg.ts` → `webpush.pushWorkerFor`, the worker's `showMessage`): Chrome counts visible notifications per registration, so a push the `seen` ring drops while the page's copy sits on the root worker is a silent push, and enough of those bring "This site has been updated in the background" (a desktop page that runs in the background, `docs/projects/push-subscription.md` § The dropped duplicate is a silent push); reading a conversation (opening it, the window coming back to it, another session's `markread` to the end) closes it there with a `{type: "read", target}` message (`readOnWorker`), since the server's read push only follows a message it pushed; browser check `tools/scenarios/push-page-notification.mjs`. Actions are `[Mark read, Reply]`. **Mark read is the account's read marker at the notification's newest message** (`data.time`, the click's time when the push carried none): the worker asks an open page first (`{type: "markread", …, deadline}`, answered through the `markread` bus emit → `IrcClient.markRead` → `handlers/markread.ts` `markReadAt`, which sends `MARKREAD <target> timestamp=<time>` at once and moves the channel's own marker forward so the debounced path never follows with an older one), then its own throwaway connection with `draft/read-marker` requested (`swMarkRead`; `swIrcOpen` takes the optional caps to ask for — a `FAIL`, a 421 or a server without the cap is "not sent"), then the same `outbox` as a reply (entries carry a `type`) — never the app, a marker is nothing to type. The notification closes locally whatever happened; the server relays the marker to every push subscription, which is what closes it on the other devices. Browser check: `tools/scenarios/push-mark-read.mjs` — nefarious2 defaults the `CAP_draft_read_marker` feature to **off** and the rig's conf does not set it, so the scenario switches it on for the run through the rig's oper (`tools/scenarios/lib/rig-feature.mjs`) and back off after. **Under WebKit every push event shows a notification** (`strictUserVisible()` in the worker), or WebKit revokes every subscription of the origin after three silent pushes: a push the page took or a redelivery shows quietly (the conversation's notification re-shown silently, else a silent stub with no text and no count), a read relay leaves a silent stub, and a push that has shown nothing after 20 s shows a silent fallback under its own tag, which the real notification closes; on Chrome, which counts the notifications visible on the registration when the event ends, a read relay closes what it found just after the event (`closeForTarget(…, defer)`, 0.5 s — still up when Chrome counts, nothing new shown, nothing buzzes; the log records the close), Mark read on a notification turns it into a silent "Marked as read" in place for the relay to close (`markedReadHere`), a hidden page waits 8 s before closing on another session's read echo (`readOnWorker(…, echo)`), and only a relay that found nothing while no window is visible shows a brief silent stub (`keepChromeCount`); the worker remembers each conversation's read marker (`reads`, from Mark read and every relay) and a late push for a message at or before it shows no fresh card (`alreadyRead`); a relay on Chrome closes what it matched inside its event while another card stays up and turns only the last into a silent "Marked as read" in place (`closeOrConvert`; Mark read's `markedReadHere` likewise), whose close is a `scheduleStubClose` entry in IndexedDB `closes` (the linger and the stubs too) run by its timer, by a one-shot Background Sync (`seance-closes` — refused by Chrome from a worker with no window of the app open, the pocket phone) or by the next event's sweep, since Android ends the process with the push event and a bare timer never fired — and on Android with no window of the app open at all (`closesRunLater` false) nothing runs later, so the last card closes inside the event, Mark read closes at once and no stub is shown: a silent push, the budget's cost, by the user's choice over a card that stands until the next push;; a push the page already took (the `seen` ring) goes through the same `keepChromeCount` on Chrome — a blank silent stub under the message's tag when no window is visible and nothing is up, logged `dropped as seen`, since the relay — the server's broadcast of the account's read marker to every subscription, one per pushed conversation — is otherwise a silent push that spends the budget behind "This site has been updated in the background"; a conversation muted on this device shows quietly on every browser; a push from someone on the network's ignore list (the page mirrors each list into the worker's `prefs` entry, `push-prefs.ts` `mirrorIgnoreList`, as it loads and on every change, and the worker matches the line's `nick!user@host` with the page's own rule, `push/ignore.ts` `ignoredSender`) is dropped as one the page took — quiet under WebKit, `keepChromeCount` on Chrome, logged `dropped as ignored`, never its text; the JSON tier names the nick alone, so there only a nick entry matches; notification tags carry the network (an older worker's network-less one is merged and closed); the page `WEBPUSH UNREGISTER`s an endpoint whose own registration has no subscription, and at boot drops the root registration's subscription and any `push/<uuid>/` registration of a network it no longer has (`dropRootSubscription`, `dropStaleRegistrations`: a second subscribed registration drops every message as already shown — a silent push each). **Settings → Notifications → Diagnostics** is a text report to copy — the environment, the permission, each network's announced key, entry, registration and live subscription, the page's journal of every subscribe decision and server answer (`webpush.ts` `note`/`diagnostics`) and the worker's own log of every activation, push and its outcome, show failure, subscription change and click (`service-worker.js` `logPush`, IndexedDB `pushlog`) — with a Subscribe now button (a tap, for every connected network); `docs/projects/push-subscription.md` § Diagnostics. A subscribe asks for the notification permission only while it is undecided — WebKit's `requestPermission()` without a gesture resolves `"denied"` even when the permission is granted, which is why a revoked iPhone never re-subscribed — and a granted permission subscribes at once. `docs/projects/push-subscription.md` § iOS. Harness: `test/tests/service-worker.ts` (the real worker in a `vm` sandbox with a scripted ircd). See `docs/projects/push-subscription.md` § A reply is one reply and § Mark read replaces Mute 30m.
