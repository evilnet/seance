# Client features

How the parts of the client behave and why, moved out of `CLAUDE.md` on 2026-11-02. Each section names its source files, tests and browser check.

## Attention

**Attention** — `client/js/irc/presence.ts` (Vue-free, DOM-free): `IrcClient.setAttended(bool)` records whether the page is attended (unattended: hidden at once; visible-but-unfocused after `UNFOCUSED_AWAY_MS`) and `syncPresence` decides what goes out — on Auto `AWAY *` when it goes unattended and `AWAY` when it returns, unless `/away` is in force (`userAwayChanged`); the presence modes and do not disturb weigh in too (next bullet), and a page hidden while connecting declares it before `CAP END` (`registrationAwayLine`) or at registration (`presenceRegistered`). `pushMessage` schedules MARKREAD for the open channel only while attended, and attention returning marks it. `foreground.ts` feeds it from `visibilitychange`/`focus`/`blur` via `manager.setAttendedAll`. The server side is nefarious2's per-connection `AWAY *` (pre-away) and its webpush attention rule. Tests: `test/irc/presence.ts`.

## Increase Contrast and Reduce Motion

**Increase Contrast and Reduce Motion** — the stylesheet reads two attributes on `<html>`, `data-contrast="more"` and `data-reduce-motion`, never the media queries: `client/js/helpers/systemAccessibility.ts` (called first thing in `boot()`) sets them from `prefers-contrast`/`prefers-reduced-motion` in a browser and the iOS shell, live, and in the Android shell from `SystemAccessibility.kt`, which watches High contrast text, the Contrast setting and the animator scale, because Android's WebView answers the media queries with the values its process started with (Chromium's `WebViewObserveAccessibilityState` is off by default) and the keep-alive service holds that process for days. The Android rule is Chromium's (`fromAndroidSettings`, `test/helpers/systemAccessibility.ts`). Two blocks at the end of `style.css`: high contrast points every muted/faint text token (`--body-color-muted`, `--chat-fg-muted`, `--chat-fg-faint`, `--rail-fg-muted`) at the full text colour, outranking a theme's `:root`; reduced motion sets every animation and transition to 0.01ms with `!important` (end events still fire for Vue's `<Transition>`). The per-element `html[data-reduce-motion] …` rules elsewhere stay for their still looks; a JS reader subscribes with `onSystemAccessibility` (`LinkPreview.vue`). A new reduced-motion or contrast rule uses the attribute, not `@media`.

## Switches

**Switches** — in the native shells every checkbox is an on/off switch (`helpers/nativeSwitches.ts`: the `v-switch` directive, registered in `vue.ts`, marks it as it mounts; every `<input type="checkbox">` in a component carries it, and `test/tests/nativeSwitches.ts` fails one that does not): on iOS it carries WebKit's `switch` attribute (the native switch; the shell's iOS 26 minimum is past the 17.4 that brought it), sized 2×1.22em in `style.css`; on Android it gets `role="switch"` for TalkBack and `style.css` draws a Material switch under `html[data-platform="android"]` (track in `--button-color` when on, thumb in `--button-text-color-hover`). Everywhere, checkboxes and radios take `accent-color: var(--button-color)`.

## `client/js/pwa.ts`

**`client/js/pwa.ts`** — installed-app glue: registers `service-worker.js` (secure contexts only), captures `beforeinstallprompt` into `store.state.installPromptAvailable` (Settings → "Install … as an app"), consumes `window.launchQueue` so `web+irc:` links reuse the running window (manifest `launch_handler: focus-existing`), and flags a new build when a newly activated worker announces a build token other than the page's own (`client/js/build.ts`; Help offers a reload) — `checkForUpdate()` re-fetches the worker script from the foreground hooks and hourly, since browsers only look on a page load. The token (`resolveBuild` in `scripts/build-info.mts`) is a hash of version and commit, `dev` in a development build. `tools/pwa-check.mjs <url>` asks headless Chromium for its installability verdict; see `docs/resources/pwa.md`.

## Install guide

**Install guide** — the first thing a browser that can install the app shows is a modal walkthrough of how (`InstallGuide.vue` + `InstallGuideArt.vue`, inline SVG schematics that take the theme; opened by `pwa.ts` `openInstallGuideAtStart()` at the end of boot, never over a `?uri=` link, never in an installed window or a native shell). Platform detection and the copy are Vue-free in `helpers/installGuide.ts` (`test/helpers/installGuide.ts`): iOS by browser (Share → Add to Home Screen, with the button's place per browser and iPad), Android by browser (⋮ → Install app, Samsung's Add page to, …), desktop Chrome/Edge (the address-bar icon; the real `beforeinstallprompt` button when it has fired), macOS Safari (File → Add to Dock); Firefox desktop gets nothing. "Don't show this again" is `thelounge.state.installGuide = dismissed`, honoured on every way out; Settings → General reopens it. **Automation starts with it dismissed**: `browser-drive.mjs` unless the scenario exports `installGuide = true`, Playwright through `test/e2e/storage-state.json`. Browser check: `tools/scenarios/install-guide.mjs` (`--mobile --platform=android|ios`). See `docs/resources/pwa.md` § The install guide.

## Last opened conversation

**Last opened conversation** — `Chat.vue` reports what it shows to `client/js/helpers/lastChannel.ts` (Vue-free, `test/helpers/lastChannel.ts`; `thelounge.state.lastChannel` = `{network uuid, target}`; channels and queries, never the lobby). On the next page load `socket-events/network.ts` opens it as soon as the network is announced (the autojoin channels are already placeholders) or waits in the lobby for its `join` (a query is reopened with `/query` on `network:status`); opening anything else first calls that off. None of that on a page the user opened on purpose — settings, help, the changelog, a network's edit form, search results (`router.ts` `onStandalonePage()`): a network announced there (boot's autoconnect) and its registration's `init` leave the view where it is, the networks come up in the sidebar and the remembered conversation waits for the user; the connect form is nowhere, so from there the view always moves. Browser check: `tools/scenarios/reload-on-settings.mjs`. A notification deep link (`helpers/pendingTarget.ts`) on the network wins and resolves the same way. `join.shouldOpen` is true for windows the user asked for (`/join` via `IrcClient.requestJoin`, `/query`; a `/whois` no longer opens a query — its summary follows the user, `docs/projects/reply-routing.md`); a join nobody asked for (a held session's restore, a forced join, an incoming query) never moves the view. `ChatInput.vue` focuses the input when a conversation opens unless `helpers/device.ts` `hasVirtualKeyboard()` says a touch-primary device would pop its on-screen keyboard; a click on the sidebar row of the conversation already open changes no route, so `ChannelWrapper.vue` asks for the caret with the `input:focus` eventbus event instead. The composer shows that it has the caret: `#form:focus-within` colours its top edge (accent in the Ink & Amber themes, the input focus green in `style.css`) and the caret takes the accent, since a caret alone is a thin blinking line that is easy to miss. Browser check: `tools/scenarios/input-focus.mjs` (every way into a conversation, also `--mobile`).

## Channel order

**Channel order** — a drag in the sidebar (`NetworkList.vue` → `sort.ts` `sortChannels`) stores the network's channel names under `thelounge.sort.channels` (`saved-networks.ts` `setChannelOrder`) and rewrites the saved network's autojoin string in that order. `IrcClient.createChannel` reads `channelOrder(uuid)` and places every channel by it — the autojoin placeholders, a held session's restore JOINs, `/join`, queries — remembered names first, then alphabetical; `applyStoredChannelOrder` (`network`/`init` events) is the same rule over what is already there. Tests: `test/irc/client.ts` "channel order", `test/irc/saved-networks.ts`.

## The phone layout is decided by the short side

**The phone layout is decided by the short side.** `helpers/device.ts` `PHONE_LAYOUT_QUERY` — `(max-width: 768px), (max-height: 500px) and (hover: none) and (pointer: coarse)` — is the one breakpoint that makes the sidebar and the user list overlays; `style.css` and `Mentions.vue` carry the same list verbatim and `isPhoneLayout()` is what the JS asks (`App.vue`, `router.ts`, `vue.ts`). A phone in landscape is 812–932px wide, so a width-only breakpoint gave it the desktop side panel with a third of the screen; tablets are 744px and up on their short side and keep the panels both ways. Browser check: `tools/scenarios/landscape-phone.mjs --mobile` (five shapes, no ircd). **Compose mode**: `#viewport` is a `size` container named `viewport` (its height is `--viewport-height`, which no media query can see — iOS never shrinks the layout viewport for the keyboard), and `@container viewport (max-height: 18rem)` hides `#chat .header` while `#input` has the caret, since the keyboard and Safari's form bar leave a landscape phone ~130–180px and the header took a third of it; the placeholder names the channel and the keyboard's Done brings the header back; the `alice is typing…` strip (`TypingIndicator.vue`) shares the composer's row there (`order` between `#input` and the buttons, a third of the row at most) instead of taking one. Gated on the caret on purpose: on height alone a landscape phone at a large font step would lose the header, and with it the way to the sidebar and the menu. Browser check: `tools/scenarios/landscape-compose.mjs --mobile` (resizes to 926×180 in place of a keyboard; needs the ircd).

## Touch and iOS

**Touch and iOS** — `client/js/helpers/viewport.ts` publishes the visual viewport as `--viewport-height` on touch-primary devices (iOS never shrinks the layout viewport for the keyboard; `body` and `#viewport` in `style.css` are sized and positioned from it). `router.ts` makes every `router.push` a `replace` so the history stays one deep and iOS's edge swipe has nothing to go back to; what used to mean "back" (Escape on Help, the Android shell's back button) calls `leavePage()` instead — never add a `router.push` call site expecting history. There is no exception, an open image included: `helpers/imageViewer.ts` takes back with a `CloseWatcher` where the browser has one (Chromium) and pushes no entry, since an entry pushed for it outlives the image as forward history; on iOS an edge swipe leaves an open image alone. On touch the viewer owns the whole gesture (`touch-action: none`; any finger anywhere pans or pinches, and no touch reaches the swipes on `<body>`) and only a still one-finger tap at the fitted size closes it; its `touchend` is cancelled so no compatibility mouse events follow. Browser check: `tools/scenarios/image-viewer-back.mjs`. Hover or long press is decided by the **last pointer**, not the device: `helpers/inputModality.ts` writes `data-input="touch"|"pointer"` on `<html>` from each real `pointerdown`/`pointermove` (`pointerType`; a synthetic event without one is ignored, and a pen counts as a mouse only while it hovers — its taps are a finger's on an iPad and a mouse's on a Surface, so they change nothing), starting from `hasVirtualKeyboard()`, and the toolbar's CSS (`:where(html[data-input=…])`, keeping the old specificities), `Message.vue`'s long press and `MessageActions.vue`'s Copy text (the text is unselectable exactly while the last pointer was a finger; `onInputKindChange` feeds one shared ref) read it — a touchscreen laptop whose browser calls its screen primary (`(hover: none)`) used to lose the hover toolbar to its trackpad while the long press listened only to a finger; browser check `tools/scenarios/touch-laptop-toolbar.mjs --touch-laptop` (a `browser-drive.mjs` flag), and the `--mobile` scenarios tap rather than click, since a mouse click now means a mouse. On touch the message action toolbar opens on a **long press** (`Message.vue` `actions-open`, 500 ms, one message at a time, a tap anywhere closes it) and the text of a message that has one (`has-actions` = `canAct`) is `user-select: none` there so the platform's own long press (a text selection) cannot race it — a row with no toolbar (topic, mode, notice, condensed join) stays selectable, so its first long press is the platform's; the toolbar's Copy text stands in for the quick case, the message whose toolbar is open is selectable again once the opening press has lifted (`select-armed` in the coarse-pointer rule — armed mid-press, the platform's detector would start a selection off the same held finger) so a second long press there is the platform's own selection — and the moment one exists (`helpers/touchSelection.ts`, `selection-live` on `.chat`) the toolbar stands down and the whole scrollback turns selectable so the handles can cross messages; a tap collapses the selection and puts the rule back. Presses on links, buttons and nicks are left to them; `Sidebar.vue`'s swipe stands down under a selection and inside text fields, and ends cleanly on `touchcancel`. The composer lets iOS's Return newline land and removes it (`ChatInput.vue` `onEnterKey`), since cancelling the keypress leaves the shift key stuck; the send button prevents `mousedown` so the keyboard stays up. Browser check: `tools/scenarios/message-actions-single.mjs --mobile`; the keyboard and swipe behaviour need a real device.

## Message action toolbar

**Message action toolbar** (`MessageActions.vue`, `#chat .msg-actions` in `style.css`) — three quick reactions (the newest single-emoji reactions used, `quickReactions()` in `helpers/reactionRecents.ts`, defaults before any; one tap reacts, a pressed one is taken off; every toolbar follows the same list through the `RECENTS_CHANGED` bus event), the smiley that opens the picker, a divider, then reply, copy (code, and the whole text on touch), edit, a divider and delete, every glyph a FontAwesome solid via `::before` (the Unicode ↩ ✕ it used to be drew differently on every OS, and a ✕ at the end of a bar reads as "close"). An action emits `done` and on touch `Message.vue` closes the toolbar on it (Copy excepted — it is showing "Copied"); the emoji catalog chunk is prefetched at idle by the first conversation opened (`Chat.vue` → `prefetchEmojiCatalog()`, `helpers/emoji.ts`), and the bar grows in over 100 ms (`pop-in`, shared with the picker; hover stays instant). The bar is one row, always: `@container chat` queries in `rem` drop the quick reactions one at a time at 21 / 18.5 / 16rem of pane and narrow every button to 1.75rem under 14rem — an own message's eight buttons are ~20.75rem and a 390px phone is 19.5rem at the large step. It floats **above** the row, bottom edge on the row's top padding, so it never covers the text it acts on; the first message in the log, with nothing above it, keeps it inside the row. `MessageList.vue` sets `selecting` on `.chat` while the primary button is down and the pointer has moved, and every toolbar stands down under it, so dragging a selection never pops one. The jump-to-recent arrow (`.scroll-down`, its size and inset are `--scroll-down-size`/`--scroll-down-inset` on `#chat`) has priority: it stacks above the toolbar, and while it is up (`:has(.scroll-down-shown)`) toolbars sit left of its column. Browser checks: `tools/scenarios/message-actions-toolbar.mjs` (hover, drag, arrow, glyph, quick buttons), `message-actions-single.mjs --mobile` (long press), `quick-reactions.mjs --mobile` (one-tap react, close on action, catalog prefetch) and `toolbar-select-hold.mjs --mobile` (second long press = native selection).

## The iOS status bar

**The iOS status bar** — a home-screen web app on iOS 26+ gets no say over the status bar from `theme-color`, from the manifest's `theme_color` or from `apple-mobile-web-app-status-bar-style`; all three are ignored. What iOS reads is the `background-color` of a **real, painted element** positioned `fixed` (or `sticky`) within 4px of the top of the page, at least 80% wide and tall enough — that is `#status-bar-tint`, a bare `<div>` first in `<body>` (`client/index.html`) styled in `style.css`. Height is the undocumented part and it is the whole ballgame: the community's iOS 26 figure is 3px, **4px was measurably ignored on iOS 27 and 6px is where sampling starts**, so the rule ships 8px. Find no element and iOS falls back to `<body>`, which from 26.2 also renders the page under a feathered blur reaching ~93pt down the screen — that blur is what soft-focuses the channel header, and nothing else removes it (`black-translucent`, `black`, `default`, `viewport-fit=cover` were all measured and all did nothing). Two more disqualifiers: a pseudo-element is never sampled, and neither is a fixed element carrying a `backdrop-filter`. **The element has to paint** — the community's iOS 26 notes have `visibility: hidden` still being sampled and on iOS 27 it is not (measured) — so it covers the first `--status-bar-tint-height` (8px) of the page. Over the chat that is header background and invisible; the sidebar puts its logo there, so `#sidebar` reserves the same variable. Anything else placed flush against the top of the page has to do likewise. The whole rule is behind `(hover: none) and (pointer: coarse)` as well as the `@supports` probe, because on desktop Safari the sidebar is always open and would take the same slice. The colour it takes is `--canvas-bg-color`, the same token `html`'s background uses, so the bar and the chat under it agree in every theme; a theme that does not set it keeps `--body-bg-color`. Verifying any of this needs the icon deleted and re-added — iOS freezes `apple-mobile-web-app-*` at install — and a pixel measurement, not an eye: a 1px hairline peaked at 72 of 230 under the blur and 230 without it.

## Markdown

**Markdown** — what a message renders as is decided by `layout()` (`client/js/helpers/ircmessageparser/layout.ts`), a Vue-free `LayoutNode` tree: `parseStyle → applyMarkdown → finders → merge → layout tree`, then an adapter — `parse()` (`parse.ts`, the Vue one, which walks the tree with a private `toVNodes`) or `toPlainText` (`Chat.vue`'s `plainTopic`). Markdown itself is `parseMarkdown.ts` (`applyMarkdown` → `{fragments, verbatim}`); neither file imports Vue, the store or the DOM, so mocha loads them: `test/helpers/layout.ts` and `test/helpers/parseMarkdown.ts`. A code block renders through `CodeBlock.vue` (rows, gutter counter, and a `Show all N lines` toggle once it is over 12 lines long — `excerptRange` in `codeLines.ts`, `test/helpers/codeLines.ts`) and `highlighter.ts` (Prism, alias table, lazily imported grammar/flourite chunks — also Vue-free, `test/helpers/highlighter.ts`). `#`–`######` at a line start are headers: a `header` wrap carrying its level, rendered as `.md-header`/`.md-h1`…`.md-h6`. A masked link (`[label](url)`) shows its real host after the label and asks before opening when the label names another address (`helpers/linkSafety.ts` `judgeLink`, verdict on the `href` node, `helpers/openLink.ts`; browser check `tools/scenarios/masked-links.mjs`). Vocabulary in `CONTEXT.md`; see `docs/projects/markdown-messages.md`.

## Network header

**Network header** — the sidebar's lobby row (`NetworkLobby.vue`) is two rows inside one `.channel-list-item[data-type="lobby"]` (one click target, one drag handle, one hover): `.lobby-title` (chevron, network name at full width, unread badge) and `.lobby-status` under it — `.lobby-tools` on the left (connection state, notification bell, edit, join: 1.5rem boxes with a 0.25rem gap, every glyph centred — the bell is a span and needs `text-align: center`, buttons centre by themselves — and all four glyphs FontAwesome solids of about 13px, because the eye measures the gaps between ink, not between boxes: a thin text `+` or a smaller bell reads as uneven spacing; the scenario measures the ink with a canvas) and `.lobby-nick` on the right (the nick this connection uses — `network.nick`, live through the `nick` event; the tools never shrink, a long nick gets an ellipsis). The jump-to results show the same header without the toolbar. Nothing in `pnpm test` renders it; browser check: `tools/scenarios/network-panel.mjs`.

## A conversation on a network that is down

**A conversation on a network that is down** — `ChatInput.vue` `canSend`: in a channel or query the send button is disabled and Enter keeps the draft while `network.status.connected` is false, unless the draft is a slash command (`/connect` has to work from anywhere); the lobby is never gated, its input is for commands. The view fades like a pending message (`Chat.vue` `isDisconnected` → `#chat.disconnected .chat-content`, opacity 0.55) and so do the sidebar rows of that network's channels and queries (`ChannelWrapper.vue` `network-down`; the lobby row turns red as before). Once the network has been down for 10 s straight (`CONNECTION_BAR_GRACE_MS`, from `status.downSince`, which `socket-events/network.ts` stamps client-side — a resume or a dropped socket usually comes back sooner, and a strip for that was noise), or at once when nothing is retrying (a `/disconnect`, a failed SASL login) or Enter was refused for being down, a strip above the input (`.connection-bar`, `role="status" aria-live="polite"`) says `Reconnecting to <network> in Ns…` with a "Connect now" button while a retry is pending (`status.retryAt`, the transport's delay sent on the close and dropped when the retry starts dialling; a half-second ticker in `ChatInput.vue` counts it down), `Connecting to <network>…` with a turning glyph while a dial is in flight, or `Disconnected from <network>.` with a Connect button when nothing is being tried (both buttons send the sidebar's `/connect`, which restarts the schedule and dials at once; a wait the server said is its throttle says so: `status.retryReason` = `"throttled"`) — the header spinner stays. Everything is computed from `network.status`, so it clears on registration. Nothing in `pnpm test` renders it; browser check: `tools/scenarios/disconnected-channel.mjs`, through `tools/scenarios/lib/irc-proxy.mjs` (a TCP proxy that cuts the socket and refuses dials), also with `--mobile --width=390 --height=844`.

## Animated image previews play once

**Animated image previews play once** — `LinkPreview.vue` `shouldPlay`: a GIF, WebP, APNG or AVIF sequence plays one play from its load, then a `<canvas class="media-still">` drawn at the image's measured box stands in for the `<img>` (a cross-origin draw taints the canvas, which only forbids reading it back); it plays again while the pointer is over the preview frame (the frame, not the image — its tools float over it), keeps looping while its message is the newest in the conversation, and with `prefers-reduced-motion` only ever plays under the pointer. The image viewer always animates. One play is timed from the file (`helpers/animatedImage.ts` `animationInfo`: GIF GCE delays, WebP `ANMF`, APNG `fcTL`, ≤10 ms delays played at 100 ms as browsers do; `test/helpers/animatedImage.ts`) through a CORS `fetch` after the `<img>` has loaded — mostly a cache hit; a host without CORS headers leaves a CORS error on the console and a 6 s fallback for `.gif`/`.webp` (`.png`/`.avif` are presumed still). Browser check: `tools/scenarios/animated-preview.mjs` (serves its own GIF on 8032, with and without CORS).

## The inbox

**The inbox** (`docs/projects/inbox.md`, issue #125) — the @ popover (`Mentions.vue`, placed under the @ button on desktop, the whole screen on the phone layout) lists unread mentions grouped by conversation (newest conversation first, each read oldest first, text clamped to three lines, a long line cut to just before its mention), a private conversation as one row (its newest line and "N unread"). One count, `mentionCount` (the `visibleMentions` getter: muted conversations' entries are kept but hidden), is the @ button's badge, the title, the favicon and the app icon. An entry is a reference by network uuid, target and msgid (`helpers/inbox.ts`, Vue-free, `test/helpers/inbox.ts`; never a session-local id; a query's key is the conversation), stored in `thelounge.mentions` (100, 20 per conversation); the IRC layer builds the entries of unread highlights in a channel or query (`IrcClient.inboxEntry`) — live, caught up, or past the marker in a history page — and dispatches them as `inbox:add`, `moveReadMarker` says how far a conversation is read as `inbox:read` — opening it here, another session's `MARKREAD` — which drops what it covers, so reading anywhere clears it everywhere, and `inbox:drop` names a deleted message or an edit's original by msgid, loaded or not. Clicking an entry opens the conversation (a group whose conversation this page does not have says why under its name). A dismissal is this device's only, remembered in `thelounge.mentions.dismissed` so the catch-up does not bring it back; parting a channel or closing a query dismisses its entries (`dismissConversation`, from `socket-events/part.ts`). Browser check: `tools/scenarios/inbox.mjs` (also `--mobile --width=390 --height=844`; the dev rig has no accounts, so it shows nothing across devices).

## Reactions

**Reactions** — a reaction is free text (`👍`, `🎉🎉🎉`, `lol`), so the picker (`ReactionPicker.vue`, opened from the smiley in the message action toolbar or the `+` at the end of a reaction row) is a search field that doubles as the free-text entry, the nine Unicode groups, and a recents row. It is `<Teleport>`ed to `<body>` and positioned against its anchor (the scrollback would clip it). **Only the groups near the scroll are rendered**: 1870 buttons put the open at 180 ms on a 4×-throttled CPU (and Android rasterises every glyph in the DOM), so the picker opens on recents + Smileys and every other group is a placeholder sized to the grid it becomes, rendered as the scroll nears it, by its tab or by the keyboard (`rendered`/`renderNear`/`countColumns` in `ReactionPicker.vue`, height from `--rows` in `style.css`; a placeholder group's options are not built either; see `docs/resources/reactions.md`). The catalog is generated from gemoji into `client/js/helpers/emoji-catalog.json` by `tools/generate-emoji-catalog.mjs` and only reached through `loadEmojiCatalog()`, an `import()` that keeps it in its own chunk; searching, `:shortcode:` expansion and `normalizeReaction` are Vue-free in `helpers/emoji.ts`, the MRU list in `helpers/reactionRecents.ts` (`thelounge.reactions.recent`). See `docs/resources/reactions.md`.

## File uploads

**File uploads** — `client/js/upload.ts` (`Uploader`, Vue-free behind the `UploadHost` interface, `test/irc/upload.ts`) posts straight to the deploy's `uploads` endpoint from `config.json` — unless the network advertises its own host (`draft/FILEHOST` ISUPPORT → `IrcClient.filehostUrl()`, kept on `serverOptions.FILEHOST`): then `UploadHost.filehost()` wins and `uploadFilehost` does a `TOKEN GENERATE FILEHOST #chan` (`irc/authtoken.ts` `TokenRequests`, answered by `handlers/token.ts` / `FAIL TOKEN` in `standard-replies.ts`) followed by a raw `POST` with `Authorization: Bearer` expecting `201` + `Location`; `test/irc/authtoken.ts`. `upload.ts` must stay free of `irc/manager` (it pulls in `document`), so `ChatInput.vue` hands `clientForNetwork` to `upload.mounted`. Every way in (drop, paste, the paperclip's `#upload-input`) lands in `triggerUpload`, which checks size/type, then **asks before sending**: `UploadHost.confirm(files)` → the `upload:confirm` eventbus request that `UploadPreview.vue` (mounted in `App.vue`) answers with the files the user kept. Progress is real (`XMLHttpRequest` via `xhrFetch`, wrapped into a `Response`; `UploadHost.progress` → `store.state.uploadProgress` → the `.upload-bar` strip above the input in `ChatInput.vue`, with cancel = `Uploader.abort()`, which is silent) — **but an upload listener forces a CORS preflight**, which curl-oriented uploaders (litterbox: `OPTIONS` → 405) refuse, so `xhrSend` retries a request that died before any progress as a plain POST and `Uploader.progressBlocked` remembers the endpoint for the page (indeterminate bar); a preset or deploy that knows better sets `uploads.progress: false` (litterbox does) and no preflight is ever tried. Never add headers or listeners to the upload request without checking the endpoint answers `OPTIONS`. The "remove metadata" setting re-encodes through a canvas, which keeps one frame, so `metadataPlan()` exempts GIF/SVG and anything `helpers/animatedImage.ts` sniffs as animated (WebP `VP8X` flag, PNG `acTL`, AVIF `avis`; `test/helpers/animatedImage.ts`); a re-encoded file takes the blob's real type and a matching extension (`fileNameForType`). See `docs/resources/branding.md` § Uploads.

## Settings backup

**Settings backup** — Settings → General → Backup and restore exports a gzipped JSON envelope (`.seance-settings`, `CompressionStream`, no dependency) of the preference keys in localStorage — `settings` (the store's live object, since the key is only written once a setting changes), saved networks (passwords stripped unless the box is ticked), sort orders, mutes, ignore lists, trusted media, recent reactions, do not disturb (`thelounge.dnd`) — and restoring one replaces exactly those keys and reloads (the file records the platform it was made on, and `matchSystemTextSize`/`matchSystemAppearance`, whose defaults differ between the shells and the web, take the restoring platform's default when they held only the source's: `helpers/platformDefaults.ts`); `thelounge.sts`, `thelounge.push*`, `thelounge.mentions`, `thelounge.querylog.*` and `thelounge.state.*` are never carried or written. `client/js/helpers/settingsBackup.ts` is Vue-free (`test/helpers/settingsBackup.ts`); browser check `tools/scenarios/settings-backup.mjs`. See `docs/resources/settings-backup.md`.

## Settings is a modal

**Settings is a modal** — `/settings/*` routes are unchanged (deep links, reloads, `onStandalonePage()` all still hold), but `Windows/Settings.vue` renders them as a pane over a dimmed backdrop covering the whole app, sidebar included (absolute in `#viewport`, above the sidebar's z-index): a header (title + ✕), a horizontal tab strip (`Settings/Navigation.vue` — the pane is the `settings` size container; below 48rem the inactive tabs drop to icons only, the active tab keeps its label, and the active tab is scrolled into view on route change), a body that scrolls by itself, and a fixed footer whose Done button is `leavePage()` — settings apply instantly, there is no Save. Escape closes it too (`keybinds.ts`, never from inside a form field, and never while an overlay is up over it: App.vue's Escape `preventDefault`s a press it hands an overlay, since a closing overlay can be gone from the DOM before `keybinds.ts`'s listener runs), as do ✕ and a backdrop click; on ≤768px the pane is the whole screen. Consequence: nothing behind the backdrop is clickable, so a scenario leaves settings through Done before touching the sidebar. Browser check: `tools/scenarios/settings-modal.mjs` (also `--width=390 --height=844`). **Help and the release notes** (`/help`, `/changelog`: `Windows/Help.vue`, `Windows/Changelog.vue`) are modals in the same frame — the `.settings-modal` pane and its header, body and Done footer, with no tab strip (the release notes' footer leads back to Help with `« Help`); Escape, ✕, Done and the backdrop close them alike. Browser check: `tools/scenarios/help-modal.mjs` (also `--width=390 --height=844`).

## Command aliases

**Command aliases** — Settings → Aliases defines user slash commands (`thelounge.aliases`, carried by the settings backup). ## Who plays an alert's sound

**Who plays an alert's sound** — a page's `<audio>` is media playback: on a Mac it takes the output (AirPods switch over), on iOS it stops Music for good. So `socket-events/msg.ts` asks `helpers/notificationSound.ts` `alertSound` (Vue-free, `test/helpers/notificationSound.ts`): a system notification carries the sound (`silent` when the `notification` setting is off, page and push-worker notifications alike), and the page plays `pop.wav` only when there is no notification, on Linux and ChromeOS (whose notifications are usually silent), or on an iPhone/iPad with the web app on screen — then as `navigator.audioSession` `ambient`, which mixes with Music, the notification silent. The shells have no Notification API: `helpers/nativeAlerts.ts` hands the alert to the OS, on iOS and macOS through the shell's `LocalNotifications` (Swift, `shells/tauri/src-tauri/swift`; one id per network + window, `alertId`, so a new alert replaces the last and reading clears it; the tap opens it via `openTarget`), on Android through the shell's push service (`NativePush` `show` → `PushService.show`, merged with that conversation's pushes, cleared on read, recorded in the seen ring as it is shown, so `msg.ts` skips `recordSeenOnShell` for it). iOS prompts for notification permission only once: the first ask (the badge's first highlight, or a notify switch) asks for banners, sound and the badge together; a device that granted the old badge-only prompt keeps silent alerts until Banners and Sounds are switched on in iOS Settings. Browser check: `tools/scenarios/notification-sound.mjs`.

## Lua scripting

**Lua scripting** (`docs/resources/lua-scripting.md`; the user's guide to writing scripts, every example run against the sandbox, is `docs/areas/scripting/`) — off unless Settings → Scripts → Enable scripting (`irc/scripting/enabled.ts`; while off the Fengari chunk is never fetched). `irc/scripting/engine.ts` (`LuaSandbox`) opens only base/coroutine/table/string/math/utf8 (never `luaL_openlibs`: its `require` brought `io`/`os`/`debug` back), text-only `load`, no `string.dump`, a capped `string.rep`, a 100k-instruction hook that coroutines inherit and that a `pcall` loop cannot outlast, and one environment per script with a read-only `seance` bound to its id (storage and errors credited to the script that ran), its own read-only views of the standard library, its own `_G` and `load`, and a locked string metatable; every handler gets its own copy of the event; each handler and command runs through the host's `run` (a fresh budget for it and for the loop after it; `MAX_EVENT_INSTRUCTIONS` per event; at most `MAX_HANDLERS` per event and `MAX_COMMANDS`; an event runs the handlers it started with); a failing script command is never sent raw; the dispatch tables live in the bootstrap chunk's locals; pattern matching has a step budget (200k `match` calls per call, a `gmatch` step on its own) patched into `fengari/src/lstrlib.js` at build time by `scripts/fengari-match-budget.js` (a transform in `vite.config.mts`), which fails the build if Fengari's source moved — mocha loads Fengari unpatched, so `test/scripts/fengari-match-budget.ts` runs the patched source and `test/tests/build.ts` checks the chunk; JS exceptions in the VM become Lua errors (`lua_atnativeerror`) and error objects are described without `__tostring`, since either used to leave the state dead for every script. Every event carries `networkUuid`, which `seance.reply`/`seance.send` route by (never by name, never falling back to another network); the manager's `generation` keeps a sandbox that loaded after a switch-off or a newer reload from being installed; "Check syntax" only compiles (`checkSyntax`). `irc/scripting/manager.ts` routes events (the handlers call `scriptManager.dispatch*`, never during a replay) and sends: a typed command's lines at once, an event handler's through `IrcClient.background` (at most `MAX_QUEUED_LINES` waiting), and a script's own echo never wakes its `message` handlers. `irc/scripting/storage.ts` caps the source (16k characters each, 256k the library) and `seance.storage` (16k per script, 128k together) and reads every write back (`ScriptStorageError`). A settings restore brings scripts and the switch back off (`settingsBackup.ts` `disarmScripts`). UI: the Settings → Scripts tab (`Settings/Scripts.vue`, `/settings/scripts`: the switch and the library) and its editor (`Settings/ScriptEdit.vue`, `/settings/scripts/<id>`, a child route: an overlay one layer above the settings modal, z-index 30 in `#viewport`, wider than it, closed by Done/✕/Escape back to the list; the code is CodeMirror 6 with the Lua mode, `helpers/luaEditor.ts`, its own lazy chunk `js/code-editor.<hash>.js`, tokens as the `tok-*` classes the chat's Prism blocks use so every theme's `--tok-*` palette applies, a plain textarea until the chunk loads), helpers in `irc/scripting/library.ts`; no sidebar icon. `/lua` runs a snippet. Tests `test/irc/scripting.ts`; browser checks `tools/scenarios/scripting-editor.mjs`, `test-lua-live.mjs` (two bots, every event a script can take, in `SEANCE_IRC_CHANNEL`, default `#seance-testing`, which must be empty: the first bot takes ops to kick, voice and set the topic; `SEANCE_IRC_URL`).

## UI sizing: rem, never px

**Size the UI in `rem`, never `px`.** `html { font-size }` is the one UI scale (`:root` in `style.css`; the font-size setting's steps are `html[data-font-size=…] { font-size: N% }`, `medium` = 100% = the browser default and the default step (it was `large`, 125%, until 2026-11; a profile that stored `large` keeps it), the ends run 62.5%–212.5% on purpose, `client/js/helpers/fontSize.ts`; the sidebar is `--sidebar-width`, half rate and capped to the screen), and everything — text, header/footer height, sidebar and user-list width, button padding, icon targets, menus — is `rem`/`em` off it so a step grows the whole interface together and the browser's own font-size preference is honoured. In the native shells the system's text size stands in for the step while the `matchSystemTextSize` setting is on (the default there; Settings → Appearance hides the slider meanwhile): `helpers/systemTextSize.ts` sets `html[data-system-text]` and `--system-text-scale`, the system's body size over the browser's 16px — on iOS from a hidden `-apple-system-body` probe watched by a `ResizeObserver` (Dynamic Type), on Android from `Configuration.fontScale` as body text (16sp) feels it — Android 14+ scales large text nonlinearly — reported live by the shell's `SystemAccessibility` (the WebView's own text zoom is pinned at 100% in `SeancePlugin.kt`: it scales glyphs but never rem lengths, so text outgrew its boxes) — and `style.css` makes the root `100%` × that — 1rem is the system's body text size, 17px at iOS's default and 16px at Android's — capped at the `huge` step with `min()`; the chat header's buttons are capped at 56px (`--header-button-size`) in a pane narrower than 24rem (`@container chat`) so all five still fit a phone there, and keep growing in a wider one. A new `font-size: 14px` or `height: 36px` in the chrome is a bug: it stays put while the rest scales. Media-query breakpoints stay in px (they cannot see the root size); what has to follow the scale asks a **container query** instead — `#chat` is an inline-size container named `chat`, and the message row's three modes are chosen by the pane's width in `ch` and `rem`: columns (time fixed in `ch` per clock setting, nick `flex: 0 1000 12ch` down to a 9ch floor and an ellipsis, text `flex: 1 1 30ch`; the nick gives way first and alike in every row, so the columns stay aligned; below `72.5ch + 2.5rem` of pane the nick column starts at 9ch rather than 12ch, so short nicks stop standing off from their time), the user list as an overlay instead of a side panel once the pane cannot hold the widest gutter, 30 characters of text and the list (`--userlist-width` cannot be read in the condition, so its `6rem + 84px` is spelled out), and the phone's inline flow once the columns alone do not fit — that block used to be the 479px media query. Both `@container chat` blocks sit after every column rule on purpose: same specificity, later wins. Browser check: `tools/scenarios/message-gutter.mjs` (`SEANCE_CLOCK=12h+s` etc.), which sweeps window widths at three font steps with the user list open. The slider itself stays in px (`Appearance.vue` `.font-size-slider`): the control that changes the scale must not change with it. A drag renders only the sample box under the slider (`fontSizeScale` in `helpers/fontSize.ts` must agree with the CSS steps); the page takes the step on release, so nothing moves under the pointer. Browser check: `tools/scenarios/font-size-setting.mjs`.
