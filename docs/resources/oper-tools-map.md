## Oper tools

**Oper tools** (`docs/projects/oper-tools.md`, wire facts `docs/resources/nefarious2-oper.md`) — being an IRC operator is first-class. **No dedicated windows**: server notices (`:server NOTICE * :*** Notice -- …`) and WALLOPS are classified by the server profile (`irc/profiles/`: `nefarious2` by `+Nefarious(` in 004, `generic` otherwise; 67 notice kinds, each with a default route and a plain-words template) and routed by importance in `irc/snotice.ts` — `active` (stored in the lobby, shown in the active window via `showInActive`), `network` (lobby, no unread) or `off` — the oper's per-kind overrides in `thelounge.oper` (`irc/operprefs.ts`, carried by the settings backup). Every routed line is kept in IndexedDB per saved network (`irc/noticelog.ts`, ~2000 lines / 24 h) and restored into the lobby on page load, because a discarded Android PWA would otherwise lose them (the server never replays them). Oper state (`irc/oper.ts`, `oper:state` → `network.oper`) comes from our own `+o`/`+O` **whoever sets it** — AfterNET opers are granted by X3 on SASL login, no 381 — and asks PRIVS, the snomask (`MODE <me> +s +0` → 008) and the profile's features (`GET`) on oper-up, puts back the oper's chosen snomask, and re-fetches PRIVS on `Your privileges were modified`. The server sends our modes after the MOTD on every path — fresh registration, bouncer revive and attach — since nefarious2 `d759a1a` (evilnet/nefarious2#121), so a reconnect asks for none (the old `wasOper` stopgap is gone; a stored `wasOper` is dropped on load); `operRegistered` only follows up an `+o` that landed before 001. `/stats`, `/check`, `/privs` (`irc/commands/oper.ts`) go out through `irc/request.ts` — labeled-response correlation that resolves with the whole answer (a labeled batch, labeled lines up to an end numeric, or `ACK`), tolerating evilnet/nefarious2#119 (untagged NOTICEs inside the batch) and #120 (untagged 270/302/303/340 + ACK) — and land as one `MessageType.REPORT` card (`Oper/ReportView.vue`, typed values in `Oper/ReportValue.vue`) where they were typed. The shield in the network header (only while opered; five tools tighten under a `lobby-status` container query) opens `Windows/OperPanel.vue` at `/oper/<uuid>/<tab>`, the Settings modal's frame, three tabs each one question (the revised plan of 2026-10-10, step 1): **Opers** (`Oper/OperActivity.vue`, logic in `helpers/operActivity.ts`: the notice log rolled up by oper or by kind for today / 24 h / since reload — `actorOf` credits an action to the nick a kind's template names, the server's own go to a "servers" row, the network running itself — connects, bursts, log lines — is never an action and only the by-kind "Everything else" row; `coarseKindOf` folds kinds into G-lines, kills, modes, opers, jupes, links, rehash, WALLOPS; an outlying count is amber), **Alerts** (`Oper/OperAlerts.vue`: the profile's `alertLines` — `irc/profiles/nefarious/alerts.ts`, "Bans added or removed", "Every connect and quit", … — each a Here / Network / Off radiogroup over a few kinds kept in step, `helpers/operAlerts.ts`; Here asks how long and a temporary choice is `OperPrefs.temporary` in `irc/operprefs.ts` — `routeFor` honours it until it lapses, then puts back what stood before, lazily and on the tab's mount; Off clears the snomask bit once every kind on it is off and a kind back on sets it, `reconcileMask`, only ever the changed kinds' bits; the kinds nobody cares about and the raw mask with its presets are two folded rows) and **Me** (`Oper/OperMe.vue`: one status line, the privileges folded past 12, the user modes as a grid). The badge on a notice (`Oper/NoticeBadge.vue`, in chat and in the Opers timelines) opens the same "where these show" menu (`helpers/operMenu.ts` `noticeRouteItems`: the kind by name, Here for today / 3 days / a week / for good, Network, Off, the current one checked, and "Stop receiving … notices" which clears the bit, or `-w` for WALLOPS); every change goes through `applyNoticeRoute` and announces itself as the `oper:routes` eventbus event, which the Alerts tab re-reads on. Old `/oper/<uuid>/notices` and `/modes` links open Alerts and Me. A nick's menu gains Check / Kill… / G-line… / Shun… / Z-line… / Find clones (`helpers/operMenu.ts`, gated by PRIVS — except that a G-line or shun is also offered when an oper service takes it, `canBan`: a services-opered AfterNET user holds only X3's `auto_oper_privs`, which lacks `GLINE` and `SHUN`); an IP, host or mask chip in a notice or card opens the same actions; `Oper/ActionDialog.vue` suggests masks from USERIP/USERHOST, checks the server's width rules first (`irc/profiles/nefarious/bans.ts`), previews the matches with CHECK and confirms a ban by listing it back (nefarious2 answers bans with silence). `isErrorNumeric` (`irc/errors.ts`) knows nefarious2's 5xx list replies (542, 545, 546, 548, 549, 535–537). **Services support** (step 2, 2026-10-10; wire facts `docs/resources/x3-services.md`): a per-network setting, never detected — `SavedNetwork.services` / `network.services` = `{package: "x3", bots: {oper, account, channel, report, snoop}}` (`saved-networks.ts` `asServices`, carried by the settings backup, live on `IrcClient.services` through `setServices` on `network:edit`), set in `NetworkForm.vue`'s "Services support" section, shown only once the network is connected and opered: a package select (None / X3) that prefills the empty role fields with the package's usual names (`irc/services/x3` `X3_DEFAULTS`: `O3`, `AuthServ`, `ChanServ`, `#operserv`, `#mrsnoopy`) and a liveness line — `irc/services.ts` `checkServices` WHOISes each bot through `request.ts` (311 = online; a 310/313 "service" or one of X3's default realnames = looks like X3) and `describeServiceCheck` words it ("✓ O3, AuthServ and ChanServ are online and look like X3.", "AuthServ isn't online (no such nick)."). The package's formats are a **services profile** (`irc/services/types.ts`, `irc/services/x3/index.ts`, registry `irc/services/index.ts`, mirroring `profiles/`): `parseSnoop` (every mod-snoop keyword; the connect form of `NICK` is keyword `connect`), `parseAudit` (`(<#chan>) [nick!ident@host:acct]: command args` → the human, the command lowercased, and a `coarse` kind: gline/shun/block/trace-with-a-ban → glines, trace kill → kills, ChanServ channel commands → modes, god → opers, addalert/delalert → alerts, rehash/die/restart → rehash), `parseModuleLog`, `banCommand`/`x3Duration` and `parseBanReply`. **The feed** (`irc/servicesfeed.ts`, from the PRIVMSG handler): a line from one of the three bots in the snoop channel that `parseSnoop` matches, or in the report channel that `parseAudit`/`parseModuleLog` matches, is appended to the notice log as a `snoop` / `audit` entry (`kind` `x3.snoop.<keyword>` / `x3.audit.<coarse>` / `x3.log.<severity>`, `category: "SERVICES"`, an audit entry's `from` = the human) — never routed, never re-rendered (the channel shows it as the ordinary message it is), and `restoreNotices` never puts those back into the lobby; the badge on one is plain (`NoticeBadge.vue`). `helpers/operActivity.ts` takes an `ActivityOptions {serviceNicks}` (the component passes `serviceNicksOf(network.services)`): an audit entry is credited to the human by its coarse kind (a bot's own WALLOPS or audit line lands on the services row); `countLabel` reads in the singular ("1 G-line", "1 oper-up"). **The snoop channel is a quiet source for the cards and a place to click, never oper actions** (rubin, 2026-10-11: "it doesn't need to show up as 'everything else' content, since it isn't 'oper actions', which is what that panel is"): a `snoop` entry is `isCounted() === false` and in no row, kind or timeline of the Opers tab, and the tab has no "Not in #mrsnoopy" line (the cards say it: the channel card under Last hour here, the user card under Seen before — `UserModel.snoopMissing`). Instead the nicks a snoop line names render as nicks whether or not they are in the channel: `noteServicesLine` returns the entry it recognised (appended to the notice log only for a live line — a chathistory replay after a reload or a reconnect's catch-up parses and marks the same but the log already has those lines), `snoopNicks(entry)` is the `nick`/`newNick`/`kicker`/`killer`/`setter` fields that are not a server (no dot), and the PRIVMSG handler hands them to `handleMessage` as `feed.nicks`, added to the message's `users` (the list `findNames` renders as `Username.vue`, whose click and right-click open the user menu — Investigate first, working for a nick in no channel of ours since `ContextMenu.vue` stands in `{nick, modes: []}`), and a recognised snoop line is never a highlight (our own connect in the feed is the bot's report, not a word to us); the `#chan` in a JOIN/CREATE/PART/KICK/MODE line is an `InlineChannel` whose menu has `operChannelItems`. AfterNET's X3 appends the cloaked host and the cloaked IP after the modes of a `UMODE` line when `+x` is among them: the rule keeps them as `cloak`/`cloakIp`, never `host`/`ip` (`helpers/commonality.ts` and `helpers/verdict.ts` read only the connect/quit/kill/oper/auth and join/part fields). **Bans through O3**: with X3 set and an oper service named, `ActionDialog.vue` sends a G-line or shun as `PRIVMSG O3 :gline <mask> <X3 duration> <reason>` (`services:ban` → `irc/services.ts` `servicesBan`, `awaitServiceReply` watching that nick's NOTICEs, 10 s), the title and button say "via O3", no CIDR suggestion, no scope or force, and the verdict is O3's own words ("G-line issued for …" = set; "Invalid G-line …", "Gline …? Now that would be smooth.", "Invalid time span …", "Access denied." = refused; silence = "O3 did not answer."); KILL and Z-line stay on the server. **The investigation cards** (step 3, 2026-10-10): `Oper/InvestigateCard.vue`, one overlay over the whole app in the Settings modal's frame (full-screen on the phone layout), opened by the `oper:investigate` eventbus event — Investigate at the top of a nick's oper menu, Investigate in a channel's menu (the sidebar row, an inline `#chan`; `helpers/operMenu.ts` `operChannelItems`) when opered, or `/investigate <nick|#chan>` (`irc/commands/investigate.ts`) — closed by ✕, Escape or the backdrop; cards stack (a nick in the channel card opens the user card on top, ✕ goes back); the user column is `Oper/InvestigateUser.vue`, rendered twice for Compare side by side (a second `Investigation` as a second column, one column with tabs under 40rem of the `investigate` container, rows whose values match tinted `same`). The data is `irc/investigate.ts` `Investigation` (Vue-free: `start`, `refresh`, `stop`, `lookup(nick)`, `traceCount()`, `criteria()`, `onChange` over a plain model the component copies on every tick): the first `BURST` (3) commands at once and the rest one every `PACE_MS` (2 s), the bots' queries one at a time on their own lane (`irc/services.ts` `collectServiceReply`: the lines from the one a lookup says starts the answer to the one that ends it, or 1.5 s of quiet — `SERVICE_QUIET_MS`). Channel: `CHECK #chan` (`parseCheck` in `profiles/nefarious/check.ts`: the fields, the member rows, the bans), `WHO #chan %tcuihsnfdlar,<token>` (an oper's real IP in `i`; a non-oper's 255.255.255.255 is no IP), `USERIP` five nicks at a time for anyone still without one; with X3 (`ServicesLookups` on the services profile, `irc/services/x3/lookups.ts`), O3 `chaninfo`, ChanServ `info`, then O3 `whois` per user (country, city, version, nick age, channels), the first `LOOKUP_CAP` (20) by itself and the rest from a Look up button in their block. User: `CHECK nick`, `WHOIS nick nick`, `USERIP nick`, then `STATS g` / `S` / `Z` when opered (`parseBanRow` in `profiles/nefarious/stats.ts`); with X3, O3 `whois`, AuthServ `accountinfo` once an account is known, and O3 `gtrace print host superset <host>` only when the server listed no bans at all (its list is X3's too). The kept feed gives the rest without asking — `helpers/commonality.ts` (`commonality()`: authed, connect age, realname, ident shape per character with the group's literal glob, the /24 or /64, server, version, common at max(3, two thirds); `lastHourHere` with joins within a minute folded; `connectTimes`/`joinTimes`) and `helpers/verdict.ts` (`maskCovers` — wildcard ident/host/IP, IPv4 CIDR, `$R`, `$V`; `bansNear` — live STATS rows covering the user with the setter from the feed's `ban.add`, then the recent `ban.*` notices; `seenBefore` — connect/exit/nick/ban-hit/kill/oper-up notices and snoop connect/quit/kill/oper/auth lines sharing the IP, host, realname or account, by nick, newest first, with their fate, never the user's own lines (their nick by the network's casemapping from their own IP or host; an earlier session of the nick from elsewhere counts); `verdict` — one sentence naming what matched and never more, "the nick was seen from …" for that earlier session, never "the same as" themself).
