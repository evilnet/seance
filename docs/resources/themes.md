# Themes

A theme is one plain CSS file in `client/themes/`, written to `public/themes/` by the build and loaded after `css/style.css` through the `<link id="theme">` in `index.html`. Picking a theme in Settings → Appearance rewrites that link's `href` to `themes/<name>.css?v=<build>` (`client/js/settings.ts`, `helpers/themeHref.ts`); `js/loading-error-handlers.js` does the same from localStorage before the app boots so there is no flash of the wrong theme. A theme is authored as plain CSS that `@import`s the theme it builds on (frost → cobalt → coffee → day), in one form only: `@import "<file>.css";` or `@import "<file>.css" <media query>;` at the start of a line of its own, double-quoted, naming a theme in the same folder (relative `url()`s are copied as written, so they must be relative to `themes/`); the build fails on any `@import` left after inlining. The build inlines that chain itself, each import in place under its media condition (`vite.config.mts` `inlineImports`), then Lightning CSS transforms the result for the bundle's browsers and minifies it in production (`bundleTheme`), so every theme is one request and no `@import` reaches the browser (`test/tests/build.ts`). Nothing else changes: a theme's rules simply cascade over the base stylesheet, and the user's custom stylesheet (Settings → Appearance) cascades over the theme. One theme, `ps`, is also the one exception to "one CSS file": it brings a script chunk of its own through a small theme-neutral hook (below).

`style.css` declares its palette as custom properties on `:root` (`--body-color`, `--window-bg-color`, `--link-color`, `--highlight-bg-color`, the `--tok-*` code colours, …) and reads them everywhere it can, so most of a theme is a `:root` block. Where the base stylesheet still has literal colours (the sidebar rows and badges, header icons, the input and the context menu, message-type icons, the mIRC colour table) a theme restates those selectors.

## The theme registry

What the app knows about a theme, apart from its stylesheet, is its entry in `client/js/themeRegistry.ts` (`THEMES`, in the order Settings lists them): `name` (the file, and the stored setting's value), `displayName` (what Settings calls it), `themeColor` (the browser chrome's `<meta name="theme-color">`, or `null` to leave it to the deploy's `themeColor`, then the build's: day, morning, macos), `looks` (`"offered"`, the reader's choice of Classic, Messenger or Workspace; `"painted"`, always Messenger in its own paint, ps; absent, Classic alone; § Looks) and `scene` (a loader for page elements of its own, `() => import(…)`, so the scene stays a chunk of its own; ps alone, § The `ps` theme). The light/dark pairs stay a list of their own, `client/js/helpers/themePairs.json`, because the build writes it into the early loader and Settings' hint follows its order (§ Following the system's light or dark mode). Everything else reads these: Settings' list (`configuration.ts` `themes`), the looks (`helpers/messageLayout.ts`), the scene hook (`themeScene.ts` `SCENES`) and the build test. The module is data alone, with no store or DOM, so mocha loads it. `test/tests/themeRegistry.ts` fails on a stylesheet in `client/themes/` without an entry, an entry without a stylesheet, or a pair naming a theme it does not list. An entry carries only what something reads today.

**To add a theme:** drop `client/themes/<name>.css` in and add its entry to `THEMES` in `client/js/themeRegistry.ts`; a theme on coffee's tokens takes `looks: "offered"` unless it copies a period client (§ Looks), and a light/dark pair adds a line to `client/js/helpers/themePairs.json`. Start from `creama.css` or `cobalt.css` for another colour direction on the same rules (tokens only), from `morning.css` for a theme on TheLounge's variables.

## The handoff themes

`coffee` and `creama` implement the warm direction of the colour redesign handed off in `docs/resources/themes/` (`README.md`, `ink-amber-theme.md` and the `ink-amber-*.png` mockups); `cobalt` and `frost` implement the cool one, `cobalt-frost-theme.md` with its own mockups. The handoff is colour only, and so are the themes: layout, spacing and type are untouched, and its suggestions beyond colour (a `data-theme` switch, sweeping the components for literal colours, hover/focus/mention states) were deliberately left for later — except the composer's focus ring, which is in: the bar is flush with the window, so `#form:focus-within` draws it as the top edge (accent border plus a 2px inset of `--focus-ring`) and the caret takes the accent (`caret-color`), in `coffee.css` and, through the import, the three token-only themes; `style.css` gives `day` and `morning` the same in their green.

The two directions share every rule. `coffee.css` is the one file with selectors in it; `creama.css`, `cobalt.css` and `frost.css` are token values alone, so a fifth direction is one more `:root` block and costs nothing in bundle size beyond its own colours. The handoff intended exactly that — both directions use the same token names, "so they are drop-in interchangeable".

The custom properties use the handoff's token names (`--chat-bg`, `--rail-accent`, …) so a value can be checked against its tables, plus a few the handoff does not have: the tints (`--tint-soft`/`--tint-strong`, translucent overlays that must be light on a dark surface and dark on a light one), the notice-box pairs (`--note-*`, `--warn-*`, `--error-*`, `--ok-*`), `--menu-bg`, and the message semantics (`--event-join`, `--event-quit`, `--nick-default`, `--notice-color`, `--action-color`). TheLounge's own variables are mapped onto the tokens at the end of `:root`, which is what keeps the rest of `style.css` in step.

Deviations from the handoff, all for contrast (`docs/projects/accessibility.md`), are listed in the header comment of each file, and both light variants needed the same ones: muted text, the link colour, the join green and the placeholder tone are darker than specified because the handoff's own light values missed its 4.5:1 rule (`frost` moves the link blue `#1f6feb` → `#2166e0` and the muted grey `#6b7a8c` → `#65727f`); `coffee`'s footer icons use the light rail's muted tone. Nick colours are the biggest addition: the handoff gives three per variant, `style.css` hashes nicks into 32 slots (`.user.color-1`…`-32`), so each theme carries a generated 32-colour palette — hues swept around the wheel at one oklch lightness and the chroma both directions agree on (0.115), every slot ≥ 4.6:1 on a dark chat surface or ≥ 5:1 on a light one, so a nick still reads on a highlighted row.

The rail gradient is on `body` as well as `#sidebar`, so the gutter `day.css` keeps around the window continues the sidebar instead of stopping at its edge; the two gradients coincide because both span the viewport.

## The `ps` theme

`ps.css` is a fork of the `<3` theme (`heart.css`, whose design record is `docs/projects/heart-theme.md`; the fork's own is `docs/projects/ps-theme.md`, whose plan 1, "the seam", landed 2026-09-24, plan 2, "the chrome", 2026-09-25, plan 3, "the plains", and plan 4, "the rest", 2026-09-26): coffee's rules with two palettes of its own, and — unlike every other theme — a scene of its own. **Fonts** (the user's picks, 2026-09-26, in place of Mulish and Fraunces): Source Sans 3 for the words (500, bold 700; the variable files carry 200–900, upright and italic) and Newsreader for the names (700, the static 16 pt instance Google serves for `wght@700`, the bytes the user picked by eye) — the nick column, channel and network names, the header title and the names in Appearance's font-size sample — ship beside it under `themes/ps/` as Google Fonts' woff2 files, Latin, Latin Extended and Vietnamese as separate files, OFL texts alongside. A nick named inside a message (a mention, an action's actor, a join or quit line's nick) is the words' face, in the nick's colour, bold (the user's I2), never a second face mid-line. `node tools/ps/fetch-fonts.mjs` fetches them and rewrites the `@font-face` rules between `ps.css`'s `ps:fonts` markers. A face needs all three of its files, or plain, accented or Vietnamese text draws partly in the fallback, so coverage is proved by rendering, not by FontFace status (the latin-ext trap, `docs/projects/ps-theme.md` §8); every other script, Cyrillic and Greek included, falls back to the system stack mid-line; a family name with a space or a figure is quoted, or the browser drops the rule. The two seconds formats' time columns come in to `8ch` and `10ch` (from `style.css`'s 8.5 and 10.5), so the gap after the time is about the nick's gap to the text in every clock format, and `#chat .content`'s basis is restated as `calc(30ch + 0.875rem + 1px)` so the text keeps its 30 characters beside the user list's panel (`style.css`'s border-box 30ch held the column's padding and rule too); the nick column's basis comes down to `9ch`, `style.css`'s floor (the user's pick), so a short nick sits nearer the time and one over about 8 letters ends in the column's ellipsis; the column stays border-box, since `style.css`'s `box-sizing: inherit` would hand content-box to a reply quote, which then overflowed. **Motion**: every `.msg` fades in on insertion — the entrance animations use `backwards` fill (never `both`), so none pins an opacity once it ends — the sidebar rows, header and composer rise on load, and a mention glows. An own message is the exception: its pending copy stands at `style.css`'s 0.55 with no animation, and the echo that replaces it, a new row, settles up from 0.55 (`ps-settle`) instead of fading in from nothing, which blinked every sent line. The `<3` theme's glitter is gone, and **embers** stand in for it (CSS only, on pseudo-elements, `@keyframes ps-ember`): the echo of an own message (`.msg.self:not(.pending):last-child`, a message or an action) lights four small glowing sparks from the row and its text column, and a reaction lights two from the chip's text as the first chip enters with its group or a later one alone; the chip's rule restates `style.css`'s `reaction-pop` beside a do-nothing hold (`ps-ember-hold`) so Vue keeps the enter class while the sparks rise, and the text column clips with a 3.25 rem margin (`overflow-clip-margin`) meanwhile rather than lifting its anti-Zalgo clip. Only in a channel's view (never a query, the lobby or search results), and never under reduced motion, where the scene also takes out of the render tree what exists only in flight (the birds, the rain, snow and seeds, the lightning, the smoke) and keeps the veil, the still fireflies and the colours of the hour.

**The scene** (`client/js/themeScene.ts`, `client/js/scenes/ps/{engine,colour,palette,markup}.ts` and `client/js/scenes/psng/`, the "NG" renderer that replaced the classic one on 2026-10-17 — its spec is `docs/projects/ps-ng.md`) replaces the old per-conversation meadow: one live sky behind the whole app, the same for every channel, following the viewer's own local clock. `themeScene.ts` is the app's one hook for a theme to bring page elements of its own — a table (`SCENES`) of the themes that have a scene, keyed by name, built from the registry's `scene` loaders (§ The theme registry); only `ps` has one. `settings.ts` calls it when a theme is applied, `boot.ts` wires it to `visibilitychange` (`installThemeSceneHooks`), and `App.vue` tells it what kind of conversation is open (channel, query or neither): in a query the scene shows the inside of the yurt instead of the plains, moving on NG's groups as the plains do (its fire, lamp and steam, its windows' clouds, weather and stars; the stove burns while the plains' chimney smokes, soft flames flowing in its door, and is out by day), its light on the hour and its windows in the day's weather (`ps-private`; `docs/projects/ps-yurt.md`, which superseded spec §5.7's frosted plains on 2026-11-15). Applying `ps` mounts its scene into `#theme-scene`, an empty `<div>` in `client/index.html`; `style.css` keeps it `display: none` for every theme, and only `ps.css` shows it, so the element stays invisible even in the instant between a theme switch and its scene's removal. Switching away destroys the mounted scene. The engine and palette (`engine.ts`, `colour.ts`, `palette.ts`) are Vue-free and DOM-free, so mocha loads them directly (`test/scenes/ps/engine.ts`, `palette.ts`): a `Date` in, sunrise/sunset/season/weather and the sun's and moon's positions out of the engine, then the day's colour table out of the palette. `scene.ts` uses the DOM (never Vue or the store) to build the scene once, then — once a minute, and again the moment the page becomes visible — writes what the engine and palette computed as custom properties on its own root, and publishes on `<html>` the four values the rest of the chrome reads: `data-ps-light` (`day`/`night`), `data-ps-text` (`ink`/`light`), `--ps-halo` (the ink treatment's glow) and `--canvas-bg-color` (the sky-top colour of the hour, also read by the iOS status bar tint), and by day the glass's four tints. How much it moves is Settings → Appearance's Scene animation (under the theme select while ps is the theme; spec §10.4: Auto, Full, Calm or Still, Auto following the device, with whether a window not in use rests it and whether a sender's lines are combined): motion comes back group by group as `ps.css`'s own CSS animations, only `transform` and `opacity`, each group while its `psng-m-<group>` class is on the scene (`psng/groups.ts`, `psng/tiers.ts`; `docs/projects/ps-ng.md` §9). A hidden page or a page nobody attends to — 15 s after the window loses the focus, or 2 minutes without input (`createAttention` in `themeScene.ts`) — freezes the scene where it stands, its colours kept on the hour, and the focus, the page coming back or any input runs it on from there (spec §10.2); reduced motion and Still hold no animation at all; a bfcache restore catches it up, and a chunk that failed to load is retried once the network is back. **Without the chunk** (still loading, failed, or an older build), `ps.css` alone paints a fixed, legible daylight sky and ink text — never an unstyled or midnight page.

**The plains** (plan 3, `docs/projects/ps-theme.md` §5). Twelve layers, back to front: the Milky Way, 190 stars, the horizon glow, the moon, the sun, the clouds (five; nine in rain and a storm, and a low overcast deck behind them, lighter in plain rain (a shallower band, flatter billows), its billows' height tied to their width so a portrait phone draws the same wide ellipses; the wet weather's own clouds change at once when the day's weather does), the ground group (the land and river, the fireflies, the yurt and its smoke, the animal layer), the near grass, the skeins, the day birds, the weather's veil and the weather layer; the sky is the root's own background. The markup comes from Vue-free, DOM-free builders mocha loads: `plains.ts` (the land and river, the near grass and its flowers, the fireflies, the yurt and its smoke, the clouds, the weather's own clouds (`weatherClouds`), and `weatherLayers`), `birds.ts` (the moonlit skeins by night and around sunset, a buzzard and skylarks by day, none in rain or a storm, and `birdsAt`, their timing) and `palette.ts`'s levels (the river's water, dry in high summer; the flowers; the snow on the roof; the fireflies; the wind and the grass's sway; the heat; the veil) with the derived land and yurt colours, all published as custom properties and never mixed in CSS. Geometry is `%` of the scene, what travels across it `cqw`/`cqh` (`#theme-scene` is a size container), small marks `rem`. **The weather layer** holds the day's weather alone — seeds on any wind, rain drops, the storm's lightning, snowflakes, or the heat band; nothing on a clear day — and is rebuilt when the day's weather changes, at local midnight with the page open or on waking into another day; a phone gets half its particles and half the fireflies. **The yurt** stands with its centre 22 % of the window's width in from the message column's far end — the scene's edge, or the user list's inner edge while a channel shows it (`html:has(.userlist-open …)`, `--ps-yurt-in`) — clamped whole on screen, in CSS alone (`ps.css` `--ps-yurt-x`; 2026-10-17, the user: right-anchor it and lose the JS), so a sidebar opening or closing never moves it; it never slides, and a move (the user list toggled, a resize) is a cut. **Nothing animates unseen** (`layers.ts`): a layer outside its window (the stars, fireflies and smoke by day, the sun at night, the skeins by day, a flock past the night's count, the buzzard off the thermals, the larks out of season, the seeds while the wind shows none, the heat band off a hot midday) leaves the render tree at once; the scene states its `box-sizing` rather than inheriting it, which made every restyle four times dearer.

**The chrome is glass over the plains** (`docs/projects/ps-theme.md` §6). The sidebar, the channel header, the user list, the composer (one surface with its reply, upload and connection bars and the typing strip) and the reaction chips are a translucent tint, `rgb(255 251 244 / var(--ps-g-tint))` by day and `rgb(12 17 32 / var(--ps-g-tint-a))` once the scene sets `data-ps-light="night"`, under `backdrop-filter: blur(0.625rem) var(--ps-g-lift,) saturate(1.12)` and a hairline edge on the side that meets the message column. **The day glass is luminous** (the user's pick; `glass.ts`): `--ps-g-lift` is `brightness(1.3)` on `:root[data-ps-light="day"]` alone, and each surface reads its own tint, which the scene solves each 5-minute step and publishes on `<html>` (`--ps-g-tint-header`, `-composer`, `-side` for a docked sidebar or user list, `-float` for the chips and a user list laid over a narrow chat): the lowest, within 0.40–0.78, that keeps the soft ink at 4.6 : 1 and the join green's marks at 3.1 : 1 through the filter over whatever can stand behind that surface; without the scene every surface falls back to the generated `--ps-g-tint-a` (78 %) unbrightened, and the night glass is the generated 74 %, unbrightened. A composer whose top rises above the near grass (a reply bar and a longer draft on a short window, a large font step, a touch keyboard) is marked `ps-form-tall` on `<html>` and takes the chips' tint. **On the phone layout** the always-on glass (the header, the composer, the chips) has no backdrop filter and the generated tint — the measured budget's pre-decided fallback, since the phone at 4× CPU ran over its budget — while the open drawer and the user list, laid over the chat, keep the blur and the brightening while shown, on the chips' tint (the float tint as shipped, the user's pick over 70 and 78); the drawer's blur comes at once when it opens and holds until it has slid off screen. What holds dense text and controls is **solid**, `--ps-g-solid` (`#fbf8f2` paper by day, `#121827` at night): the settings pane, Help, the changelog, the connect form, the context menu, the Mentions popover, the composer's autocomplete, the emoji picker, the upload preview, the dialogs, the push prompt and the jump-to-recent disc. A native select and its options take the solid and its ink too, opaque, with the field's wash laid over the select as an image: Chromium draws a select's list from their own fills, and at night the field's translucent wash had left the night ink on a light list (the user's report). The message toolbar is solid too, but follows the column's treatment, not the chrome's light. No blur ever goes on `#status-bar-tint` or an ancestor of it: iOS does not sample a fixed element that carries a backdrop filter. ## The Princess pair

`princess` and `princess_` are a light/dark pair of IRCCloud-style themes, so that switching from IRCCloud costs the users who came from it nothing. Their palettes derive from the IRCCloud client, whose source is published under the Apache License 2.0, and are used here with that attribution; the values are tuned from there against the contrast bar the theme scenario pins. The naming follows IRC's own convention, the underscore being the alt the way a second connection takes one. Both draw nicks in messages bold, as IRCCloud does, and leave the member list at the regular weight it has there.

`princess` is the first theme here with a **light rail** — its buffer drawer is pale blue (`#d9e7ff`), not a dark gutter, so `--rail-*` inverts relative to every other theme. That inversion is what exposed a long-standing bug in `tools/scenarios/themes.mjs`: the check paired the selected channel's label against `--body-bg-color`, the rail surface, when the selected row has a background of its own. On four dark-rail themes a near-white label cleared 4.5:1 against the rail by accident, so the check had been passing for the wrong reason.

Both are also the first to use **row bands** — whole rows tinted by kind, so `.msg.self`, notices and server events each take their own background. Those restate selectors rather than tokens, and they work without touching `style.css` because the hover band is painted as a `background-image` gradient (see the message hover state above), leaving `background-color` free for the row. A mention row still wins over both from `style.css`'s more specific selector.

**In `princess`, the mention row is the constraint that shapes the rest.** `#c0dbff` is a strong tint, so everything drawn over it must clear 4.5:1 against it rather than against white. That is why its 32 nick slots are darker and less saturated than a white-only palette would need — 20 hues carried over, 12 more filling the widest gaps, each at the lightest tone that still passes on white, on the own-message tint and on the mention row (worst slot 4.60:1) — and why links are restated at `#1558c9` on the notice and mention bands. Four other values are darkened along their own hue, each checked on the surface it sits on: timestamps `#aaa` → `#5f5f5f`, the collapsed-row and placeholder grey `#afafaf` → `#898989`, links `#1e72ff` → `#1b69ed`, the inactive buffer `#9cc7ff` → `#516989`; the selected-buffer blue drops to `#1d6ef8` so its white label clears the bar.

`princess_` inverts the problem. Its chat surface is `#000000` and its bands climb in near-black steps — `#191919` server events, `#1f2530` own messages (the one cool band, so it tells apart from the events band five points below it), `#262626` notices, `#2b2b2b` a mention — so the band a row sits on barely changes what its text has to clear. Two values are lifted: timestamps `#8c8c8c` → `#929292`, the unread blue `#1e72ff` → `#2993ff`. One departure is deliberate: the palette it started from is greyscale, with a grey accent, but Seance draws links in the accent and a grey link is indistinguishable from body text — so the accent is the lifted blue and the grey becomes `--tok-punctuation`.

Both carry the classic mIRC 16 rather than `style.css`'s flat palette; slots 0, 1 and 16–98 already match, so only 2–15 are restated. In `princess` codes 8–11 stay low-contrast on white, and in `princess_` codes 2, 5 and 12 are left to `coffee.css` entirely — navy, maroon and pure blue cannot reach 4.5:1 on black, blue saturating at 2.44:1. A colour code is the sender's choice rather than the theme's.

## Following the system's light or dark mode

Five themes come as a light/dark pair: Coffee/Creama, Cobalt/Frost, Princess\_/Princess, Morning/Day and Keeki/Keeki Blush. With Settings → Appearance → "Match the system's light or dark mode" on, the chosen theme stands for its pair: whichever of the two matches `prefers-color-scheme` is loaded, and a change of mode swaps it live (`client/js/helpers/themeAppearance.ts`, `test/helpers/themeAppearance.ts`; `loadTheme` in `client/js/settings.ts`). The setting stays on the chosen theme. The toggle sits above the theme select, and while it is on the select lists each pair as one entry (`Coffee / Creama`, `Princess` for Princess\_/Princess; `pairLabel` and `themeChoices` in `themeAppearance.ts`) beside every unpaired theme, the entry staying selected whichever half shows; off, every theme is its own entry. A theme without a partner is shown as chosen. The setting (`matchSystemAppearance`) defaults to on in the native shell, where Apple's guidelines ask an app to honour the system setting, and off on the web, where a browser keeps the theme it was given. A new theme with a light and a dark variant joins by adding the pair, dark first, to `client/js/helpers/themePairs.json`; `vite.config.mts` also writes that list into `js/loading-error-handlers.js`, which picks the same half before the bundle loads so a cold start does not flash the other one.

## Your own messages

`style.css` greys an own message's text to `--body-color-muted`, TheLounge's look, and a theme was free to band the row instead (the Princess pair). The grey is hard to read on an iPhone under a dark theme — a system setting there flattens it into the background, which Android and a desk do not do — so the choice is the user's, not the theme's: Settings → Appearance → Your own messages picks **greyed text** (the default, every theme as it was), a **highlighted row** (the text like everyone else's, the row on a band) or **nothing**. The value lands on `<html data-own-messages>` (`client/js/helpers/ownMessages.ts`, `settings.ts`) and the three looks are rules in `style.css`, so no theme file needs to know about it. The three do not overlap: a band a theme paints on `.msg.self` itself (the Princess pair, Keeki) shows under **highlighted row** only, in the colour the theme names with `--own-bg` (without one the band is the text colour at 7% over the row). Own join and mode lines are `.self` as well and are left to the theme in every mode: the band is for what was said. Browser check: `tools/scenarios/own-messages.mjs` (coffee and princess, every setting, a reload).

## Looks

How the messages are drawn is the reader's choice of **look**, apart from the theme (the paint): Settings → Appearance → Look, stored as `messageLayout` and applied as `<html data-message-layout>` (`client/js/helpers/messageLayout.ts`, `settings.ts`). The stored names are the ones the setting had before the looks were named, so nobody's choice moved:

| Look      | Stored      | What it draws                                                                                                                                                                                                                                                                                                                                                          |
| --------- | ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Classic   | `lines`     | The IRC log every theme has drawn: time, nick and words in columns. The default.                                                                                                                                                                                                                                                                                       |
| Messenger | `bubbles`   | Each sender's run of lines a stack of bubbles beside their avatar, the nick and time over the first line, a later line's time on hover or long press beside the bubble, past its end (before it for our own in a private conversation; every bubble leaves `--bubble-time-room` for it, so it covers no words), the corners on the avatar's side tight where a run's bubbles meet. A private conversation is two-sided: no avatar or nick on either side, our own bubbles at the far side in the own fill. |
| Workspace | `workspace` | The same runs as flat rows across the column: the avatar a rounded square in a gutter, the nick bold and the time over the run, the lines beneath at full width, a later line's time on hover or long press over the row's end. A private conversation is drawn as a channel.                                                                                          |

A run is `MessageList.vue`'s `previous-source` (`helpers/messageRuns.ts`, under the "Combine messages" switch, which shows under Messenger, Workspace and ps). In Messenger every other row (a join, a part, a mode, a condensed group) is a quieter line whose icon stands where a message's text starts and whose time follows its words; an action is read as Workspace reads it (below), as narration rather than a bubble: a line in the bubbles' text column, a run's space above and below it, a mention of us in a mention bubble's fill and bar, our own under Your own messages greyed or not but never banded, and in the two-sided private conversation our own at the far side, its words end-aligned. Its time comes on hover or a long press, taking no room: just past its words, or over the line's end on the window's colour where the line runs nearly to the column's end (`--action-time`, about what the time takes, measured on the message list, a size container under Messenger). Workspace splits the other rows in two. An action is a line of the conversation: at a message's size and in the text colour, the actor's nick bold in its own colour and the words after it italic (no icon, nothing in the gutter: the row draws no avatar), a run's space before it, the mention band and Your own messages as a message has them. Every other row is a status line (a join, a part, a quit, a kick, a mode, a topic and who set it, a nick change, away and back, a host change, an invite, a condensed group's summary and its opened lines, and whatever else the server says): a step smaller (0.8125rem), in the row's muted ink (`--bubble-fg-muted`), its nicks in their colours but not bold, its icon in the same ink at the gutter's end where an avatar stands (the condensed summary takes the people icon; without avatars the icon goes before the words), so its words start at the text column; a block of them is held close (0.0625rem apart) with a run's space before it. A whois, a block of server text and an error keep their own colours, and a line whose `.from` holds words (an unhandled command, a plugin) keeps them before its text. Neither kind shows its time after its words: like a run's later line it comes over the row's end on hover or a long press, letting the pointer through. A reply's quote is a tinted strip over its line (at the top of its bubble in Messenger), the reply elbow (`ReplyElbow.vue`, the mark in Classic and the composer's bar too) before the parent's nick and words.

Messenger's reactions hang off the bubble they answer rather than sit in it: the chip row overlaps the bubble's bottom edge by a third of a chip (`--reaction-chip`, 1.625rem), inset 0.5rem from the bubble's start corner (its end corner for our own bubbles at the far side of a private conversation), each chip on an opaque fill of its own (`--bubble-reaction-bg`, ours `--bubble-reaction-own-bg`) ringed in the window's colour so it reads as lying on the edge. The bubble grows only by that third, and by a line where the chips wrap; its margin below makes the room, so the next bubble, of the same run or not, starts clear of them. In a channel the row is in the flow of `.content` (so a wrap makes its own room) with margins that add up to nothing in the bubble's width (a short bubble does not widen to its chips; they wrap at the pane's end, measured in `cqi` of the message list), laid out in the page's direction rather than the words', and `.content`'s Zalgo clip becomes a `clip-path` open below and to the sides. In a private conversation a run's first line keeps its time beside its words, so the bubble's end is not the words' end: there the row is placed from the bubble's corner (`.msg` is positioned) and `.content` keeps its clip and the baseline the time sits on; placed so, it makes no room for a second line, which two people seldom fill. ## The theme contract

What a theme may rely on, and what is checked. A theme is plain CSS loaded after `style.css` and before the user's own stylesheet; it changes the app's look through three things only.

**Tokens.** Custom properties on `:root`. A theme on coffee's rules (every theme but `day` and `morning`) sets the tokens coffee and `style.css` read, in groups: the surfaces (`--chat-bg`, `--window-bg-color`, `--body-bg-color`, `--canvas-bg-color`, `--menu-bg`, `--composer-bg`), the text (`--chat-fg`, `--chat-fg-muted`, `--chat-fg-faint`, `--body-color`, `--body-color-muted`, `--link-color`), the rail (`--rail-*`), what a message means (`--event-join`, `--event-quit`, `--nick-default`, `--notice-color`, `--action-color`, `--highlight-bg-color`, and `--own-bg` where it bands own messages), the notice boxes (`--note-*`, `--warn-*`, `--error-*`, `--ok-*`), the tints (`--tint-soft`, `--tint-strong`, `--focus-ring`, and the optional `--accent-tint-*`) and the code colours (`--tok-*`). Coffee maps them onto TheLounge's names (`--body-color`, `--window-bg-color`, …), which is what `style.css` reads; `day` and `morning` set TheLounge's names directly. A token nothing reads is a mistake, and so is a pair that misses its floor.

**Attributes on `<html>`**, set by the app for every theme, for a theme's selectors:

| Attribute                            | Values                                                             | Means                                                                                                                                                                                          |
| ------------------------------------ | ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `data-reduce-motion`                 | present                                                            | Reduce Motion: anything that moves goes behind `:not([data-reduce-motion])` (`helpers/systemAccessibility.ts`)                                                                                 |
| `data-contrast`                      | `more`                                                             | Increase Contrast: `style.css` folds the muted text tokens into the full colour; a theme that re-maps one below `:root` restates the reset (`test/tests/themeContrast.ts`)                     |
| `data-reduce-transparency`           | present                                                            | Reduce Transparency: a theme with glass turns it solid (§ Accessibility every theme inherits)                                                                                                  |
| `data-motion-rest`                   | present                                                            | Nobody attends to the window, or the device saves power: a theme's endless animations pause (`animation-play-state: paused`), as Keeki's drift does (`themeScene.ts` `installThemeSceneHooks`) |
| `data-own-messages`                  | `muted`, `band`, `plain`                                           | How the user wants their own lines (§ Your own messages)                                                                                                                                       |
| `data-message-layout`                | `lines`, `bubbles`, `workspace`; absent                            | The look (Classic, Messenger, Workspace), where the theme offers the choice (§ Looks)                                                                                                          |
| `data-bubble-paint`                  | `theme`                                                            | The theme paints its own bubbles (ps); `style.css` draws only their shape (§ Looks)                                                                                                            |
| `data-input`                         | `pointer`, `touch`                                                 | The last pointer, for hover against press affordances (`helpers/inputModality.ts`)                                                                                                             |
| `data-shell`, `data-platform`        | `desktop`, `native`; `ios`, `android`, `macos`, `windows`, `linux` | The app around the page; absent in a browser (`native.ts`)                                                                                                                                     |
| `data-system-text`, `data-font-size` | present; the font-size step                                        | The text size setting (`helpers/systemTextSize.ts`, `settings.ts`)                                                                                                                             |
| `dir`, `lang`                        |                                                                    | The interface language: new CSS uses logical properties (`docs/resources/i18n.md`)                                                                                                             |

`ps` adds its own (`data-ps-light`, `data-ps-text`, `data-ps-words`), which no other theme should read.

**Selectors.** Where `style.css` still has a literal colour (the sidebar rows and badges, header icons, the input and context menu, message-type icons, the mIRC colour table, nick slots `.user.color-1`…`-32`), a theme restates that selector. Prefer a token where one exists: a restated selector is coupled to the markup, a token is not.

**Checked without a browser** by `test/tests/themeContract.ts`, in CI: every custom property a theme declares is read by `client/` (ps's switched-off animal slots excepted; the check pools every file under `client/`, so it does not yet tell a token read by another theme only), and each theme's resolved tokens, light and dark, hold their floors on the surfaces the app paints them on: text, muted text and links at 4.5:1 on the window and the chat, text on a highlighted row, the rail's text on both ends of the rail's gradient (ps's rail is clear, so its text is measured on the glass's solid colour, `--body-bg-color`, not on the glass the browser draws), the join line at 3:1. A token that resolves to no colour (an empty value, a missing `var()`) fails. A translucent surface is measured over what it is painted on (a highlighted row over the window, the window, the chat and the rail over the page's own background), and a surface with nothing opaque under it in CSS must be named in the test as see-through. Besides `:root`, every block that re-maps either side of a pair is checked as its own surface, with the blocks it sits inside, that qualify it, or that match wherever it does (ps's light words under the outline, rim and glow settings): a `:root` under a width query (a phone's palette), zelenzy's dialogs and the same dialogs under Increase Contrast, ps by night and its night chat. Two kinds of block are named in the test and left out: ps's light words, painted on the scene rather than on a token, and the chat's own surfaces (the chat pane, a highlighted row) in a block scoped away from `#chat`. Glass and pictures are not a flat colour, so ps is measured in the browser as well (`tools/scenarios/theme-ps.mjs`); `tools/scenarios/themes.mjs` measures the themes it lists, which leaves out `macos` (its material needs the Mac app, `html[data-platform="macos"]`) and `zelenzy`. Known exceptions are listed in the test with their own floor, today's ratio, so the colour stays as it is and anything worse fails: `day`'s link green is TheLounge's own (3.0:1). Not checked yet: muted text and links on a highlighted row, which several themes miss today (day, princess, morning, creama, frost).

## Live rows

A theme can tell something that just happened from something it is drawing again, without shipping code (`client/js/liveRows.ts`). When a line arrives live in the open conversation, its row in the chat list carries `data-live` for three seconds from the moment it is drawn (`LIVE_HOLD_MS`; an arrival animation keyed on it must finish within that), so an entry animation keyed on it plays once, for that row, and an old row has nothing to replay when Reduce Motion is turned off or a stylesheet changes later. A reaction's chip and a sidebar row have hooks of the same kind:

```css
html:not([data-reduce-motion]) #chat .msg[data-live] {
  animation: my-arrive 0.35s ease-out;
}
```

| Attribute        | Values                         | On                                                                                 | Set when                                                                                                                                                                                                        | Held                                                                                                    |
| ---------------- | ------------------------------ | ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `data-live`      | `message`, `mention`           | `#chat .msg`                                                                       | someone else's message or action arrives (`mention`: it highlights us)                                                                                                                                          | `LIVE_HOLD_MS` (3 s) from the row's first draw                                                          |
| `data-live`      | `self`                         | `#chat .msg.self`                                                                  | our own message or action is confirmed: the server's echo that replaces the pending copy, or, without echo-message, the line itself as it is sent (also a line of ours sent from another device of the account) | 3 s from the row's first draw                                                                           |
| `data-live`      | `join`, `part`, `quit`, `kick` | `#chat .msg`, or the condensed group (`.msg[data-type="condensed"]`) it folds into | someone joins or leaves (a kick by anyone, us included; never our own join, part or quit)                                                                                                                       | 3 s from the row's first draw, or for a group from the newest line folded in                            |
| `data-arrived`   | `first`, `new`, `more`         | `#chat .msg-reaction` (a chip)                                                     | a reaction arrives on a message of the open conversation: the message's first chip, another chip, or another nick on a chip already shown (ours too, when the server echoes it)                                 | 3 s from when the chip takes it                                                                         |
| `data-mentioned` | (empty)                        | `.channel-list-item`                                                               | a mention arrives in a conversation that is not the open one (and is not muted)                                                                                                                                 | at least 3 s, gone within a second after (the activity pulse's sweep); opening the conversation ends it |

None is ever set for history, a catch-up (`catchup.ts`) or a reconnect's replay, a placed line, the lines the device kept and shows at page load, a notice rerouted to the open window, an edit or a redaction, a pending copy, a reaction taken off, nor while the page is hidden or a past view holds the live lines out of sight (`socket-events/msg.ts`, `liveKindOf`; `socket-events/msg_updates.ts`, `reactionArrival`; `socket-events/activity.ts`). A status line (join, part, quit, kick) under hidden status messages has no row and is not marked. `mention` is the message's own highlight, so it does not follow the highlightMessages setting or a jump's focus the way the row's `.highlight` class does.

The note for a row or a chip is held outside the store and taken once, by the first draw within `LIVE_MS` (1 s) of the arrival (`Message.vue`, `in-chat` from `MessageList.vue`; `MessageReactions.vue`; `MessageCondensed.vue`). Rows are keyed by message id, but the whole list is drawn again on a conversation switch or a past view closing (a status-message setting change regroups the status rows), and a flag stored on the message would replay every live row's animation on each of those; a row or chip drawn later is never marked. The search results and other lists of `Message` rows never take a note.

- **Condensed groups.** With status messages condensed (the default), a single status line is its own row; once a second one follows it the two are one group's row (`2 users have left`), so the mark is on whatever is drawn: the lone part's row while it stands alone, then the group's row when a quit folds it in (its value the newest arrival's, its hold restarted). A theme selecting `.msg[data-live="part"]` therefore also wants `.msg[data-type="condensed"][data-live]` if it is to catch every departure. The rows inside an expanded group are never marked.
- **Several at once.** A chip that takes another nick within its hold keeps `data-arrived="more"` and restarts the hold; the attribute does not change, so an animation keyed on it does not play again. The same for a sidebar row mentioned again within its hold (the hold is extended) and a condensed group taking another line of the same kind. A reaction taken off and put back is new again (`new`, or `first` if it was the only one).
- **Telling the first chip apart.** `first` is the chip that brings the message's reaction group in with it (style.css's `.reactions-enter-active`), `new` a chip added beside others (`.reaction-enter-active`), `more` a chip already shown (no enter class at all).
- **Another tab.** Each tab is its own client with its own open conversation, so a mention in a conversation another tab has open marks this tab's sidebar row.

`style.css` animates nothing on any of them: whether rows move is the theme's choice, and a period theme may want them still. Anything that moves goes behind `:not([data-reduce-motion])`, and a theme can answer reduced motion with something still (a colour, a border) on the same attribute. The attributes are set under reduced motion too.

Our own line settling in:

```css
html:not([data-reduce-motion]) #chat .msg[data-live="self"] {
  animation: my-settle 0.3s ease-out;
}
```

Someone leaving, on its own row or the group it folds into:

```css
html:not([data-reduce-motion])
  #chat
  .msg:is([data-live="part"], [data-live="quit"], [data-live="kick"]) {
  animation: my-fade-out-hint 0.6s ease-out;
}
```

A reaction arriving, a bigger pop for the message's first:

```css
html:not([data-reduce-motion]) #chat .msg-reaction[data-arrived] {
  animation: my-pop 0.2s ease-out;
}

html:not([data-reduce-motion]) #chat .msg-reaction[data-arrived="first"] {
  animation-duration: 0.4s;
}
```

A mention in another conversation, its sidebar row pulsing (still under reduced motion: an outline instead):

```css
html:not([data-reduce-motion]) .channel-list-item[data-mentioned] {
  animation: my-pulse 1.5s ease-in-out 2;
}

html[data-reduce-motion] .channel-list-item[data-mentioned] {
  outline: 0.125rem solid var(--highlight-border-color, currentColor);
}
```

## Accessibility every theme inherits

Three system settings reach every theme as attributes on `<html>`, set live by `client/js/helpers/systemAccessibility.ts`, never as media queries a theme reads itself:

- `data-reduce-motion`: Reduce Motion. `style.css` cuts every animation and transition to nothing; a theme puts anything that moves behind `:not([data-reduce-motion])` and may swap in a still look.
- `data-contrast="more"`: Increase Contrast. `style.css` folds the muted and faint text tokens into the full text colour.
- `data-reduce-transparency`: Reduce Transparency. A theme with glass (ps, macos) turns it solid. WebKit has no `prefers-reduced-transparency` (bugs.webkit.org 175497), so in the iOS and macOS apps the shell reports it (`Transparency` in `SeancePlugin.swift` and `Bridge.swift`, with change notifications); in the Android app the shell's live high-contrast report stands for it, as Chromium itself derives the query from that signal there and Android's WebView reads it only at startup; elsewhere the query is read where the engine has it (Chromium on Windows, macOS, Linux and Android, so the Windows app and a Chromium PWA on a Mac included). WebKit never sees it: Safari, a Safari web app, and every browser on iOS. Besides each theme's glass, the shared surfaces go solid too: the toolbar over an image or video preview (on black, at full opacity), the Mac app's image viewer and ps's user-list headings.

Windows' contrast themes are the exception: `@media (forced-colors: active)` at the end of `style.css`, since the mode is Windows' alone and the browser applies it live. The system repaints everything in its own few colours and drops shadows and gradients, so that block restates in system colours what the app says with a fill or a shadow alone: the keyboard focus as a ring outside the control, the composer's focus and the open conversation as an inset outline, what is chosen (a selected segment or tab, the context-menu row or completion the arrow keys reached) in the system's selection colours, so a focus on it still shows, a mention's bar in a channel and a badge's edge; takes the ps scene out of the page (`themeScene.ts` stops its frame loop too) and drops every blur. A theme needs nothing for it. Browser check for both: `tools/scenarios/forced-colors.mjs`.

## Checking a theme

`pnpm test` never loads a stylesheet. Build, serve `public/`, and look (`docs/resources/browser-testing.md`); the Appearance dropdown switches live. `tools/scenarios/themes.mjs` drives that dropdown through the themes in its list (all but `macos` and `zelenzy`) against the dev ircd, checks the stylesheet link, the stored name and the browser chrome colour, measures the pairs above on the four handoff themes (text, timestamps, links, the join line, a nick on a highlighted row at ≥ 4.5:1; icons and the placeholder at ≥ 3:1) from computed styles, and leaves a screenshot of the chat under each theme.

**The capture gallery** is the check for a change that should leave every theme as it was (or move only what it names): `tools/scenarios/gallery.mjs` draws one fixed conversation under every theme in the app's list (the registry, as `configuration.ts` hands it to the store, checked against `client/themes/*.css` both ways), in each look the theme allows (Classic, Messenger and Workspace asked for through the setting, the cell named for the `data-message-layout` the app then sets, absent counting as `lines`; ps is Messenger alone), at 1280×800 and at a 390×844 phone booted cold at that size, and saves the channel (and its start, `channel-top`, where it overflows) and a private conversation as `<theme>.<layout>.<viewport>.<window>.png`, with a `manifest.json` naming them and the browser, written only when the whole run passed. A theme whose stylesheet reads `prefers-color-scheme` (macos) is also captured dark, as `<theme>-dark`. No ircd: `lib/tiny-ircd.mjs` sends `lib/gallery-conversation.mjs` (a run of one nick, joins, a reply, a /me, a mention of us, a link, a notice, a mode, a topic, a part and a quit, our own line with a reaction, and the query), every line on a pinned `time` tag. The page's clock is held at 25 September 2026, 12:30 (a clear noon for ps's scene), in `Etc/UTC` and `en-US`; reduced motion is on (the system's, so `html[data-reduce-motion]` holds every theme still, ps's scene and Keeki's glitter included); and the live rows' hold has run out, nothing is hovered and the caret is transparent before each capture. `--stable-raster` (required; the scenario fails without it) has Chromium rasterise on one thread, whole tiles at a time: without it ps's and macos's blurred glass and macos's avatar gradients came out a few pixels apart from run to run. 224 cells today (52 of them `channel-top`), about a minute and a half. Two runs of the same build on one machine compare identical, so a difference in these views is the change's. What they do not show (anything in motion, hover, the caret, a phone's open sidebar, widths between the two) is the other scenarios' to check:

```sh
git switch develop && pnpm build
python3 -m http.server -d public 8000 &
node tools/browser-drive.mjs --quiet --stable-raster --out=tmp/gallery/base tools/scenarios/gallery.mjs
git switch my-branch && pnpm build
node tools/browser-drive.mjs --quiet --stable-raster --out=tmp/gallery/branch tools/scenarios/gallery.mjs
node tools/gallery-compare.mjs tmp/gallery/base tmp/gallery/branch
```

The compare prints each cell that is `changed` (with its count of changed pixels and their bounding box), `added` or `removed`, writes a before | after | changes picture for each changed cell to `tmp/gallery/branch/diff/`, and exits 1 on any of them. Capture both runs on one machine: the pixels depend on the installed fonts (emoji included) and on the Chromium build, which the manifest records. `GALLERY_THEMES=coffee,ps` narrows a run to those themes, for a quicker look; compare only like with like, or the rest reads as removed.
