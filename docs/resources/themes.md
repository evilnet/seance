# Themes

A theme is one plain CSS file in `client/themes/`, copied by webpack to `public/themes/` and loaded after `css/style.css` through the `<link id="theme">` in `index.html`. Picking a theme in Settings → Appearance rewrites that link's `href` to `themes/<name>.css` (`client/js/settings.ts`); `js/loading-error-handlers.js` does the same from localStorage before the app boots so there is no flash of the wrong theme. There is no preprocessing: a theme's rules simply cascade over the base stylesheet, and the user's custom stylesheet (Settings → Appearance) cascades over the theme. One theme, `ps`, is also the one exception to "one CSS file": it brings a script chunk of its own through a small theme-neutral hook (below).

`style.css` declares its palette as custom properties on `:root` (`--body-color`, `--window-bg-color`, `--link-color`, `--highlight-bg-color`, the `--tok-*` code colours, …) and reads them everywhere it can, so most of a theme is a `:root` block. Where the base stylesheet still has literal colours (the sidebar rows and badges, header icons, the input and the context menu, message-type icons, the mIRC colour table) a theme restates those selectors.

The list the Settings dropdown shows is static, in `client/js/configuration.ts` (`themes`, with a `displayName` and an optional `themeColor` for the browser chrome), and `defaultTheme` there is what a fresh browser gets; a deploy overrides that with `theme` in `config.json` (`docs/resources/branding.md`). A stored theme name the build no longer has falls back to the default at boot (`boot.ts`), which is how browsers that had `default` stored came over to `coffee`.

**To add a theme:** drop `client/themes/<name>.css` in, add its entry to `themes` in `configuration.ts`, and add the name to the list in `test/tests/build.ts`. Start from `creama.css` or `cobalt.css` for another colour direction on the same rules (tokens only), from `morning.css` for a theme on TheLounge's variables.

## The handoff themes

`coffee` and `creama` implement the warm direction of the colour redesign handed off in `docs/resources/themes/` (`README.md`, `ink-amber-theme.md` and the `ink-amber-*.png` mockups); `cobalt` and `frost` implement the cool one, `cobalt-frost-theme.md` with its own mockups. The handoff is colour only, and so are the themes: layout, spacing and type are untouched, and its suggestions beyond colour (a `data-theme` switch, sweeping the components for literal colours, hover/focus/mention states) were deliberately left for later — except the composer's focus ring, which is in: the bar is flush with the window, so `#form:focus-within` draws it as the top edge (accent border plus a 2px inset of `--focus-ring`) and the caret takes the accent (`caret-color`), in `coffee.css` and, through the import, the three token-only themes; `style.css` gives `day` and `morning` the same in their green.

The two directions share every rule. `coffee.css` is the one file with selectors in it; `creama.css`, `cobalt.css` and `frost.css` are token values alone, so a fifth direction is one more `:root` block and costs nothing in bundle size beyond its own colours. The handoff intended exactly that — both directions use the same token names, "so they are drop-in interchangeable".

The custom properties use the handoff's token names (`--chat-bg`, `--rail-accent`, …) so a value can be checked against its tables, plus a few the handoff does not have: the tints (`--tint-soft`/`--tint-strong`, translucent overlays that must be light on a dark surface and dark on a light one), the notice-box pairs (`--note-*`, `--warn-*`, `--error-*`, `--ok-*`), `--menu-bg`, and the message semantics (`--event-join`, `--event-quit`, `--nick-default`, `--notice-color`, `--action-color`). TheLounge's own variables are mapped onto the tokens at the end of `:root`, which is what keeps the rest of `style.css` in step.

Deviations from the handoff, all for contrast (`docs/projects/accessibility.md`), are listed in the header comment of each file, and both light variants needed the same ones: muted text, the link colour, the join green and the placeholder tone are darker than specified because the handoff's own light values missed its 4.5:1 rule (`frost` moves the link blue `#1f6feb` → `#2166e0` and the muted grey `#6b7a8c` → `#65727f`); `coffee`'s footer icons use the light rail's muted tone. Nick colours are the biggest addition: the handoff gives three per variant, `style.css` hashes nicks into 32 slots (`.user.color-1`…`-32`), so each theme carries a generated 32-colour palette — hues swept around the wheel at one oklch lightness and the chroma both directions agree on (0.115), every slot ≥ 4.6:1 on a dark chat surface or ≥ 5:1 on a light one, so a nick still reads on a highlighted row.

The rail gradient is on `body` as well as `#sidebar`, so the gutter `day.css` keeps around the window continues the sidebar instead of stopping at its edge; the two gradients coincide because both span the viewport.

## The `ps` theme

`ps.css` is a fork of the `<3` theme (`heart.css`, whose design record is `docs/projects/heart-theme.md`; the fork's own is `docs/projects/ps-theme.md`, whose plan 1, "the seam", landed 2026-09-24, plan 2, "the chrome", 2026-09-25, plan 3, "the plains", and plan 4, "the rest", 2026-09-26): coffee's rules with two palettes of its own, and — unlike every other theme — a scene of its own. **Fonts** (the user's picks, 2026-09-26, in place of Mulish and Fraunces): Source Sans 3 for the words (500, bold 700; the variable files carry 200–900, upright and italic) and Newsreader for the names (700, the static 16 pt instance Google serves for `wght@700`, the bytes the user picked by eye) — the nick column, channel and network names, the header title and the names in Appearance's font-size sample — ship beside it under `themes/ps/` as Google Fonts' woff2 files, Latin, Latin Extended and Vietnamese as separate files, OFL texts alongside. A nick named inside a message (a mention, an action's actor, a join or quit line's nick) is the words' face, in the nick's colour, bold (the user's I2), never a second face mid-line. `node tools/ps/fetch-fonts.mjs` fetches them and rewrites the `@font-face` rules between `ps.css`'s `ps:fonts` markers. A face needs all three of its files, or plain, accented or Vietnamese text draws partly in the fallback, so coverage is proved by rendering, not by FontFace status (the latin-ext trap, `docs/projects/ps-theme.md` §8); every other script, Cyrillic and Greek included, falls back to the system stack mid-line; a family name with a space or a figure is quoted, or the browser drops the rule. The two seconds formats' time columns come in to `8ch` and `10ch` (from `style.css`'s 8.5 and 10.5), so the gap after the time is about the nick's gap to the text in every clock format, and `#chat .content`'s basis is restated as `calc(30ch + 0.875rem + 1px)` so the text keeps its 30 characters beside the user list's panel (`style.css`'s border-box 30ch held the column's padding and rule too); the nick column's basis comes down to `9ch`, `style.css`'s floor (the user's pick), so a short nick sits nearer the time and one over about 8 letters ends in the column's ellipsis; the column stays border-box, since `style.css`'s `box-sizing: inherit` would hand content-box to a reply quote, which then overflowed. **Motion**: every `.msg` fades in on insertion — the entrance animations use `backwards` fill (never `both`), so none pins an opacity once it ends — the sidebar rows, header and composer rise on load, and a mention glows. An own message is the exception: its pending copy stands at `style.css`'s 0.55 with no animation, and the echo that replaces it, a new row, settles up from 0.55 (`ps-settle`) instead of fading in from nothing, which blinked every sent line. The `<3` theme's glitter is gone, and **embers** stand in for it (CSS only, on pseudo-elements, `@keyframes ps-ember`): the echo of an own message (`.msg.self:not(.pending):last-child`, a message or an action) lights four small glowing sparks from the row and its text column, and a reaction lights two from the chip's text as the first chip enters with its group or a later one alone; the chip's rule restates `style.css`'s `reaction-pop` beside a do-nothing hold (`ps-ember-hold`) so Vue keeps the enter class while the sparks rise, and the text column clips with a 3.25 rem margin (`overflow-clip-margin`) meanwhile rather than lifting its anti-Zalgo clip. Only in a channel's view (never a query, the lobby or search results), and never under reduced motion, where the scene also takes out of the render tree what exists only in flight (the birds, the rain, snow and seeds, the lightning, the smoke) and keeps the veil, the still fireflies and the colours of the hour.

**The scene** (`client/js/themeScene.ts`, `client/js/scenes/ps/{engine,colour,palette,scene}.ts`) replaces the old per-conversation meadow: one live sky behind the whole app, the same for every channel, following the viewer's own local clock. `themeScene.ts` is the app's one hook for a theme to bring page elements of its own — a table (`SCENES`) of the themes that have a scene, keyed by name; only `ps` is in it. `settings.ts` calls it when a theme is applied, `boot.ts` wires it to `visibilitychange` (`installThemeSceneHooks`), and `App.vue` tells it what kind of conversation is open (channel, query or neither): in a query the scene stands behind frosted glass, completely still (`ps-private`, spec §5.7 — its one wrapper `.ps-frost` blurred 1.125rem, desaturated to 0.85 and scaled 1.2, paused as a hidden page's is, its colours still on the hour). Applying `ps` mounts its scene into `#theme-scene`, an empty `<div>` in `client/index.html`; `style.css` keeps it `display: none` for every theme, and only `ps.css` shows it, so the element stays invisible even in the instant between a theme switch and its scene's removal. Switching away destroys the mounted scene. The engine and palette (`engine.ts`, `colour.ts`, `palette.ts`) are Vue-free and DOM-free, so mocha loads them directly (`test/scenes/ps/engine.ts`, `palette.ts`): a `Date` in, sunrise/sunset/season/weather and the sun's and moon's positions out of the engine, then the day's colour table out of the palette. `scene.ts` uses the DOM (never Vue or the store) to build the scene once, then — once a minute, and again the moment the page becomes visible — writes what the engine and palette computed as custom properties on its own root, and publishes on `<html>` the four values the rest of the chrome reads: `data-ps-light` (`day`/`night`), `data-ps-text` (`ink`/`light`), `--ps-halo` (the ink treatment's glow) and `--canvas-bg-color` (the sky-top colour of the hour, also read by the iOS status bar tint), and by day the glass's four tints. The scene is drawn at 24 frames a second by default (Settings → Appearance, under the theme select while ps is the theme, picks off, every five minutes, once a second, 24 or 60, whether a window not in use pauses it, and whether a sender's lines are combined; spec §10.4): its CSS animations and SMIL clocks are held and stepped together by one timer (`scenes/ps/stepper.ts`, spec §10.3). A hidden page's scene stops outright — CSS and SVG animation paused, no timer — and a scene mounted straight into a hidden page starts stopped rather than running unseen; a visible page nobody attends to — 15 s after the window loses the focus, or 2 minutes without input (`createAttention` in `themeScene.ts`) — rests the scene as a query does, still, its colours kept on the hour, and the focus or any input runs it again (spec §10.2); a bfcache restore catches it up, and a chunk that failed to load is retried once the network is back. **Without the chunk** (still loading, failed, or an older build), `ps.css` alone paints a fixed, legible daylight sky and ink text — never an unstyled or midnight page.

**The plains** (plan 3, `docs/projects/ps-theme.md` §5). Twelve layers, back to front: the Milky Way, 190 stars, the horizon glow, the moon, the sun, the clouds (five; nine in rain and a storm, and a low overcast deck behind them, lighter in plain rain (a shallower band, flatter billows), its billows' height tied to their width so a portrait phone draws the same wide ellipses; the wet weather's own clouds fade in and out over 2 s when the day's weather changes at local midnight on a page in view), the ground group (the land and river, the fireflies, the yurt and its smoke, the animal layer), the near grass, the skeins, the day birds, the weather's veil and the weather layer; the sky is the root's own background. The markup comes from Vue-free, DOM-free builders mocha loads: `plains.ts` (the land and river, the near grass and its flowers, the fireflies, the yurt and its smoke, the clouds, the weather's own clouds (`weatherClouds`), and `weatherLayers`), `birds.ts` (the moonlit skeins by night and around sunset, a buzzard and skylarks by day, none in rain or a storm, and `birdsAt`, their timing) and `palette.ts`'s levels (the river's water, dry in high summer; the flowers; the snow on the roof; the fireflies; the wind and the grass's sway; the heat; the veil) with the derived land and yurt colours, all published as custom properties and never mixed in CSS. Geometry is `%` of the scene, what travels across it `cqw`/`cqh` (`#theme-scene` is a size container), small marks `rem`. **The weather layer** holds the day's weather alone — seeds on any wind, rain drops, the storm's lightning, snowflakes, or the heat band and the `#ps-heat` haze that bends the ground group and not the near grass; nothing on a clear day — and is rebuilt when the day's weather changes, at local midnight with the page open or on waking into another day; a phone gets half its particles and half the fireflies. **The yurt** (`yurt.ts`) stands at 72 % of the message column (`#chat .chat`, observed with a `ResizeObserver`, found again on every conversation switch), clamped whole on screen, at 70 % of the scene before any column; a move over 1.5 rem fades it out, jumps it unseen and fades it back, never sliding, and the first place measured in the load's first second is taken at once; a scene not yet laid out (`display: none` until `ps.css` applies) places nothing, and the scene observes its own box as well as the column's. **Nothing animates unseen** (`layers.ts`): a layer outside its window (the stars, fireflies and smoke by day, the sun at night, the skeins by day, a flock past the night's count, the buzzard off the thermals, the larks out of season, the seeds while the wind shows none, the heat band off a hot midday) leaves the render tree, its SMIL paused, once its fade is over, and the haze's SMIL is paused while it bends nothing; the scene states its `box-sizing` rather than inheriting it, which made every restyle four times dearer.

**The chrome is glass over the plains** (`docs/projects/ps-theme.md` §6). The sidebar, the channel header, the user list, the composer (one surface with its reply, upload and connection bars and the typing strip) and the reaction chips are a translucent tint, `rgb(255 251 244 / var(--ps-g-tint))` by day and `rgb(12 17 32 / var(--ps-g-tint-a))` once the scene sets `data-ps-light="night"`, under `backdrop-filter: blur(0.625rem) var(--ps-g-lift,) saturate(1.12)` and a hairline edge on the side that meets the message column. **The day glass is luminous** (the user's pick; `glass.ts`): `--ps-g-lift` is `brightness(1.3)` on `:root[data-ps-light="day"]` alone, and each surface reads its own tint, which the scene solves each 5-minute step and publishes on `<html>` (`--ps-g-tint-header`, `-composer`, `-side` for a docked sidebar or user list, `-float` for the chips and a user list laid over a narrow chat): the lowest, within 0.40–0.78, that keeps the soft ink at 4.6 : 1 and the join green's marks at 3.1 : 1 through the filter over whatever can stand behind that surface; without the scene every surface falls back to the generated `--ps-g-tint-a` (78 %) unbrightened, and the night glass is the generated 74 %, unbrightened. A composer whose top rises above the near grass (a reply bar and a longer draft on a short window, a large font step, a touch keyboard) is marked `ps-form-tall` on `<html>` and takes the chips' tint. **On the phone layout** the always-on glass (the header, the composer, the chips) has no backdrop filter and the generated tint — the measured budget's pre-decided fallback, since the phone at 4× CPU ran over its budget — while the open drawer and the user list, laid over the chat, keep the blur and the brightening while shown, on the chips' tint (the float tint as shipped, the user's pick over 70 and 78); the drawer's blur comes at once when it opens and holds until it has slid off screen. What holds dense text and controls is **solid**, `--ps-g-solid` (`#fbf8f2` paper by day, `#121827` at night): the settings pane, Help, the changelog, the connect form, the context menu, the Mentions popover, the composer's autocomplete, the emoji picker, the upload preview, the dialogs, the push prompt and the jump-to-recent disc. A native select and its options take the solid and its ink too, opaque, with the field's wash laid over the select as an image: Chromium draws a select's list from their own fills, and at night the field's translucent wash had left the night ink on a light list (the user's report). The message toolbar is solid too, but follows the column's treatment, not the chrome's light. No blur ever goes on `#status-bar-tint` or an ancestor of it: iOS does not sample a fixed element that carries a backdrop filter. The two palettes are full ones, every token coffee.css reads defined on `:root` and again on `:root[data-ps-light="night"]` from the spec's glass primaries (`--ps-g-solid`, `--ps-g-ink`, `--ps-g-edge`, `--ps-g-field`, `--ps-g-selected`, `--ps-g-accent`) and creama's and coffee's secondaries, and they flip over `--ps-flip` (0.8 s, 0 s under reduced motion). The chrome writes and marks in a generated text accent, `--ps-g-accent-text`, since the spec's accent reads under 3 : 1 on the glass; the spec's accent stays for the open row's marker, the caret, the focus glow and the tints. Unread and mention badges are one style, the generated `--ps-g-badge` with a white numeral. Every wash on the glass moves the ground away from the text on it — lighter by day, toward black at night (`--ps-g-wash-soft`, `--ps-g-wash-strong` stand in for coffee's tints there) — while the solid panels keep creama's and coffee's tints. On the phone layout the scrim starts at the open drawer's edge, so the drawer frosts the plains rather than the scrim; a conversation on a network that is down fades its messages and the jump-to-recent disc's arrow rather than `.chat-content`, so the user list keeps its blur, and eases back on reconnect; and `prefers-reduced-transparency: reduce` makes all the glass solid, in every state (its block is `ps.css`'s last rule and names the phone's overlay states itself). On the desktop the windows sit flush with the sidebar, square and flat: `ps` drops `day.css`'s floating card. The scene also writes the hour's sky-top into `<meta name="theme-color">`, and hands the value it found back when it is destroyed, unless something else has written the meta since; before it loads, `configuration.ts` gives `ps` `#3f8fe6`, the daylight fallback's canvas.

**The generated colours.** With the meadow gone, message text sits straight on the open sky and the chrome is glass over it, so every colour that has to hold a floor there is solved rather than chosen, by `tools/ps/palette-blocks.ts` (it was `tools/ps/message-palette.ts` in plan 1), into two blocks of `ps.css`: `ps:message-palette` — every colour the message column reads in both treatments (muted text, links, join/quit, notices, the default nick, the code tokens and `--ps-code-bg`, the opaque box the column's code sits on), and its nick sweeps — and `ps:glass-palette` — the glass tint's opacity, its soft ink, the badge's fill, the text accent, and the chrome's day and night nick sweeps. Each colour keeps its base's OKLCH hue and chroma, the nicks all from one 32-hue table, and only its lightness is solved, to 4.6 (the 4.5:1 floor plus a 0.1 rounding margin), against the single worst ground its surface meets in `tools/ps/legibility.ts`'s dense sweep (every day, every five minutes, all six weathers): every area the scene paints, from the one ground list the page and the tools share (`grounds.ts` `sceneGrounds`: the sky, the moon's disc, the sun's core above the horizon line, the land and river, the yurt and its glows, the pool at its door, the clouds, the smoke; all under the veil on a veiled day), seen through the column's text layer at the strength `tools/ps/calibrate.mjs` measured from rendered pixels on real chat phrases (`ALPHA_HALO` 0.1614, `ALPHA_SHADOW` 0.6, the model's cap, measured again on Source Sans 3 and Newsreader in plan 4), or through the glass tint. Two treatments switch on `data-ps-text`: **light**, white on a close dark shadow over an eight-way outline and a faint wider ring, all day and all night; and **ink**, `#1b2638` on a close pale halo, only inside the day's ink window (`grounds.ts` `inkWindow`), where dark ink holds over every ground of the moment — over the year, snowy days alone — and changing at most once each side of noon. Under the light treatment every coloured word comes out nearly white, so links there are underlined, and the 32 nicks are held at 3:1 as large text, with a paler set, held at 4.5:1 over the sky, below the default font-size step. Where a spec colour misses its floor the generator raises the glass tint's opacity up to its cap or moves a secondary colour at most 0.08 in OKLCH lightness, and throws on anything more (`docs/projects/ps-theme.md` §11). The floors test (`test/scenes/ps/legibility.ts`) holds every generated colour, and the spec's own fixed colours (ink, faint ink, white, white at 80%), to the plain floor over a sparser sweep and every moment a block header pins — the margin is the generator's own, not what the test asks for. Every base lives in the generator (`NICK_HUES`, `SEMANTIC`, `CODE`, and the glass's in `legibility.ts`'s `GLASS`), which reads `ps.css` only to replace its blocks, so retinting a colour in the file alone never reaches them: edit the generator and regenerate. `npx tsx tools/ps/palette-blocks.ts` prints both blocks and their worst grounds without touching the file, `--write` replaces them in place (idempotent — a second `--write` changes nothing), and `--sweep=<name> --out=<file>` writes another light-nick set into a copy. Regenerate after changing a colour table in `palette.ts` or `engine.ts` too, since those move the worst grounds.

## The Princess pair

`princess` and `princess_` are a light/dark pair of IRCCloud-style themes, so that switching from IRCCloud costs the users who came from it nothing. Their palettes derive from the IRCCloud client, whose source is published under the Apache License 2.0, and are used here with that attribution; the values are tuned from there against the contrast bar the theme scenario pins. The naming follows IRC's own convention, the underscore being the alt the way a second connection takes one. Both draw nicks in messages bold, as IRCCloud does, and leave the member list at the regular weight it has there.

`princess` is the first theme here with a **light rail** — its buffer drawer is pale blue (`#d9e7ff`), not a dark gutter, so `--rail-*` inverts relative to every other theme. That inversion is what exposed a long-standing bug in `tools/scenarios/themes.mjs`: the check paired the selected channel's label against `--body-bg-color`, the rail surface, when the selected row has a background of its own. On four dark-rail themes a near-white label cleared 4.5:1 against the rail by accident, so the check had been passing for the wrong reason.

Both are also the first to use **row bands** — whole rows tinted by kind, so `.msg.self`, notices and server events each take their own background. Those restate selectors rather than tokens, and they work without touching `style.css` because the hover band is painted as a `background-image` gradient (see the message hover state above), leaving `background-color` free for the row. A mention row still wins over both from `style.css`'s more specific selector.

**In `princess`, the mention row is the constraint that shapes the rest.** `#c0dbff` is a strong tint, so everything drawn over it must clear 4.5:1 against it rather than against white. That is why its 32 nick slots are darker and less saturated than a white-only palette would need — 20 hues carried over, 12 more filling the widest gaps, each at the lightest tone that still passes on white, on the own-message tint and on the mention row (worst slot 4.60:1) — and why links are restated at `#1558c9` on the notice and mention bands. Four other values are darkened along their own hue, each checked on the surface it sits on: timestamps `#aaa` → `#5f5f5f`, the collapsed-row and placeholder grey `#afafaf` → `#898989`, links `#1e72ff` → `#1b69ed`, the inactive buffer `#9cc7ff` → `#516989`; the selected-buffer blue drops to `#1d6ef8` so its white label clears the bar.

`princess_` inverts the problem. Its chat surface is `#000000` and its bands climb in near-black steps — `#191919` server events, `#1f2530` own messages (the one cool band, so it tells apart from the events band five points below it), `#262626` notices, `#2b2b2b` a mention — so the band a row sits on barely changes what its text has to clear. Two values are lifted: timestamps `#8c8c8c` → `#929292`, the unread blue `#1e72ff` → `#2993ff`. One departure is deliberate: the palette it started from is greyscale, with a grey accent, but Seance draws links in the accent and a grey link is indistinguishable from body text — so the accent is the lifted blue and the grey becomes `--tok-punctuation`.

Both carry the classic mIRC 16 rather than `style.css`'s flat palette; slots 0, 1 and 16–98 already match, so only 2–15 are restated. In `princess` codes 8–11 stay low-contrast on white, and in `princess_` codes 2, 5 and 12 are left to `coffee.css` entirely — navy, maroon and pure blue cannot reach 4.5:1 on black, blue saturating at 2.44:1. A colour code is the sender's choice rather than the theme's.

## Your own messages

`style.css` greys an own message's text to `--body-color-muted`, TheLounge's look, and a theme was free to band the row instead (the Princess pair). The grey is hard to read on an iPhone under a dark theme — a system setting there flattens it into the background, which Android and a desk do not do — so the choice is the user's, not the theme's: Settings → Appearance → Your own messages picks **greyed text** (the default, every theme as it was), a **highlighted row** (the text like everyone else's, the row on a band) or **nothing**. The value lands on `<html data-own-messages>` (`client/js/helpers/ownMessages.ts`, `settings.ts`) and the three looks are rules in `style.css`, so no theme file needs to know about it. The three do not overlap: a band a theme paints on `.msg.self` itself (the Princess pair, Keeki) shows under **highlighted row** only, in the colour the theme names with `--own-bg` (without one the band is the text colour at 7% over the row). Own join and mode lines are `.self` as well and are left to the theme in every mode: the band is for what was said. Browser check: `tools/scenarios/own-messages.mjs` (coffee and princess, every setting, a reload).

## Checking a theme

`yarn test` never loads a stylesheet. Build, serve `public/`, and look (`docs/resources/browser-testing.md`); the Appearance dropdown switches live. `tools/scenarios/themes.mjs` drives that dropdown through every theme against the dev ircd, checks the stylesheet link, the stored name and the browser chrome colour, measures the pairs above on the four handoff themes (text, timestamps, links, the join line, a nick on a highlighted row at ≥ 4.5:1; icons and the placeholder at ≥ 3:1) from computed styles, and leaves a screenshot of the chat under each theme.
