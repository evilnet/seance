# Translating Seance — the `.po` workflow

Every UI label in Seance is rendered through one translation function (`t()`/`tCount()` from `useI18n()`, or the same resolver in the service worker), backed by gettext `.po` catalogs. This document is the fill-in workflow for a human translator or a machine-translation (MT) pipeline: where the table is, how to fill a row, how to keep a translation alive across upstream merges, and the two structural rules (`{var}` placeholders survive verbatim; a key is a whole translatable phrase) that a pipeline must not "helpfully" violate. The implementation status and label counts live in `docs/projects/i18n.md`.

## The table

`client/locales/messages.pot` **is** the output table: a flat gettext template — one entry per label, no `LC_MESSAGES` nesting. The columns map to the `.po` keywords like this:

| Table column     | gettext part  | Example                                                          |
| ---------------- | ------------- | ---------------------------------------------------------------- |
| Label key        | `msgctxt`     | `"connect.submit"` — a stable semantic identifier                |
| Context          | `#.` comments | _"Button on the connect form: submits it and dials the server."_ |
| Source text (en) | `msgid`       | `Connect` — plain English                                        |
| Translation      | `msgstr`      | empty in the template — the column to fill                       |

A filled row reads:

```po
#: client/components/Windows/Connect.vue
#. Button on the connect form: submits it and dials the server.
msgctxt "connect.submit"
msgid "Connect"
msgstr "Verbinden"
```

The `#.` context is written for humans _and_ machines: it says what the label is and does (a button? a tooltip? an aria-label heard by a screen reader?), where it appears, and what any `{var}` carries. Read it before translating — the `msgid` alone is often too short to disambiguate ("Close" the window vs "Close" the channel). `#:` lines above the context record where the label is rendered; they are maintained by the tooling and can be ignored while translating.

The file header (the first entry, `msgid ""`) carries `Language:` and `Plural-Forms:` — the template ships `Plural-Forms` preset to English's default (`nplurals=2; plural=(n != 1);`) and only `Language:` is empty; a real `.po` must have both filled in (below).

## Filling in a language

1. Copy the template to the per-locale table: `cp client/locales/messages.pot client/locales/<tag>.po` (e.g. `de.po`). The file name **is** the locale tag the rest of the pipeline keys on — BCP-47, lowercase base where possible (`de`, `pt-BR`).
2. Fill the header: `Language: de` and a `Plural-Forms` line taken from `tools/i18n/plural-rules.json` (see § Plurals — the file must carry one line for the tag before compiling).
3. Fill the `msgstr`s — by hand in any `.po`-aware editor, or by feeding the `.po`/`.pot` to an MT pipeline. The `msgid`s are plain English sentences, which is exactly what MT tools expect; the `#.` context can be passed along as prompt/instruction material. The context is metadata: never let a pipeline translate into `msgctxt`, `#.` or `#:` lines.
4. Compile: `yarn i18n:compile` (`npx tsx tools/i18n/compile.ts`). This
   first runs the language-list sync (`tools/i18n/sync.ts`: a target
   without a `.po` is scaffolded, a `.po` whose tag is no longer a target
   is archived -- § The build tracks the language list), then compiles the
   pot → `client/locales/en.json` and every
   `client/locales/<tag>.po` → `<tag>.json`, regenerates the locale list
   (`client/js/i18n/available.ts` and `tags.json`), and **fails loudly** on
   problems: a translation that lost a `{placeholder}` its msgid has names the key and stops the run; a `#, fuzzy` entry is skipped with a stderr warning (en serves that key) rather than half-applied.
5. Build and look at it: see § Verifying a translation.

Compile details worth knowing:

- `en.json` is compiled from the pot itself — the msgids _are_ the English copy; there is no separate English source. This is why the pot is the single source of truth and why an English copy change is a `msgid` change (§ Keeping a translation alive).
- A `<tag>.json` overlay contains **only the entries that carry a translation**. The runtime resolves `catalog[tag][key] ?? en[key] ?? key`, so an untranslated or fuzzy-skipped key silently falls back to English — a partial translation is always shippable.
- A plural entry is **all or nothing**. `compile.ts` maps each CLDR category the locale uses to the gettext slot its `Plural-Forms` expression yields for that category's smallest sample count (`zero` at n=0, `one` at n=1, `two` at n=2, then the smallest n ≥ 2 CLDR puts in `few`/`many`/`other`) — not to the first n that happens to hit it, which put `pt`'s singular in a slot nothing ever read. If any mapped slot is empty the whole key is left out of the overlay and English serves it, rather than the runtime serving the singular for every count. So a half-filled plural costs nothing, but it buys nothing either: fill every `msgstr[N]` or none.

### Machine-filling with the app's own engines

The MT pipeline the repository ships is the translation feature's own
(`docs/resources/translation.md`), run offline over the catalogs:

```sh
npx tsx tools/i18n/fill.ts --langs de,fr --dry        # what it would fill
npx tsx tools/i18n/fill.ts --langs ru --repo <dir>    # fill the empty slots
npx tsx tools/i18n/fill.ts --keys a.b,c.d --repo <dir>  # only these keys
npx tsx tools/i18n/sweep.ts                           # empty what cannot be trusted
yarn i18n:compile
```

`fill.ts` fills **empty msgstr slots only** (a singular entry has one, a
plural entry one per gettext form, planned by `tools/i18n/plural.ts`
`planPluralSlots`), rewrites the `.po` after every batch so a run resumes
where it stopped, and picks each language's engine from the app's own route
table. `--engine` scopes a run to the languages that table already places on
that engine; `--force-engine` puts every language of the run on one,
whatever the table says — the table is measured for a chat line under a
latency budget, while a catalog is filled once, offline, and the better
engine wins there (the 4B LLM writes Russian the OPUS-MT pair answers
degenerately). The LLM route needs a converted model directory (`--repo`,
`tools/translate-eval/norm-fp32.py`) and is named the target language in
words, not as a tag. `--keys` narrows a run to the keys named, which is
what a round that reworded two or three msgids wants: the empty slots an
earlier sweep left behind are empty because their answers were refused, and
asking again costs hours and changes nothing.

`sweep.ts` empties a slot the fill cannot be trusted to have got right, and
`fill.ts` refuses to write exactly what the sweep would empty — otherwise
the two loop, each undoing the other. One function judges both
(`tools/i18n/quality.ts` `slotVerdict`, against the English text **that
slot** translates):

| Verdict                           | What it catches                                                                                                                                                                                                                                                                                                         |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `placeholder`                     | the `{braces}` no longer match the source's                                                                                                                                                                                                                                                                             |
| `unchanged`                       | the answer is its own English source again (modulo case, punctuation, spacing) — unless the whole answer is `IDENTICAL_EVERYWHERE` words (acronyms, product names and the oper jargon the `#.` context says to keep: IRC, TLS, WebGPU, Qwen3, G-line, OK …)                                                             |
| `degenerate`                      | a repeated run — a non-letter char, or a word or short phrase four times over                                                                                                                                                                                                                                           |
| `runaway-length`                  | longer than `LENGTH_FACTOR × source + LENGTH_ALLOWANCE` (4× + 20)                                                                                                                                                                                                                                                       |
| `foreign-script`                  | a letter from a script the target does not write in (`EXPECTED_SCRIPTS`; Latin is allowed everywhere, for brand and protocol words)                                                                                                                                                                                     |
| `foreign-script:no-target-script` | a body with letters and not one character of the target's own script (`OWN_SCRIPTS`) — how French, Polish and invented pseudo-Welsh sat in the Ukrainian catalog passing every other rule                                                                                                                               |
| `padding`                         | the leading or trailing whitespace of the source is gone (or invented): a msgid padded on purpose is read beside something else, and every engine trims                                                                                                                                                                 |
| `english`                         | two English function words in a row (`hasEnglishRun`) outside placeholders and code spans, unless the target writes the word itself (its stopword table) or it is all capitals: a model that gave up halfway ("が now known as"), or the English of an older msgid that `unchanged` cannot see                          |
| `stray-latin`                     | in a catalog with a script of its own (`OWN_SCRIPTS`), a Latin token the source has no word for (or no word it begins): glued onto Han, kana, Hangul or Thai (ja `変iaz`, `あなたをmentionsする`, th `การเรnder`), or carrying a non-ASCII letter (a Spanish `líneas` in Arabic); all capitals is an acronym and passes |

Which English text a plural slot translates is the runtime's (CLDR) reading of it, not the gettext expression's (`plural.ts` `planPluralSlots` with the tag): a slot that n = 1 alone reads takes the singular, every other slot the plural. fil's "one" also serves 0, 2, 3, 5, …, ru's and uk's 21 and 31, fr's and pt's 0, so those translate the plural, the form with `{count}`; compile drops an entry whose such form lacks it. `sweep.ts --plurals` lists, without emptying anything, the plural entries whose forms for different counts are one text in a three-form language — the review list for "2 пользователей".

One exemption is the sweep's alone: a plural form that echoes English ("{count} Byte" in German) is kept while a sibling form of the same entry is translated, since emptying that one slot would send the whole entry back to English. The fill judges each slot alone, so it refuses such a form — stricter, never looping.

The fill does not _refuse_ a trimmed answer, though — it puts the source's
padding back on first (`quality.ts` `repad`), since whitespace at the ends
is structure and no engine keeps it. The `padding` verdict is the net under
the catalogs nothing re-padded: a hand edit, or a fill that ran before the
rule existed (all 23 catalogs had dropped `lobby.nickname`'s trailing space,
so a screen reader read "Nickname:alice").

An emptied slot is not a hole: the compile leaves the key out of the overlay
and English serves it, which is what the user would rather read than
machine noise. Machine output is a starting point for a native speaker, not
a finished translation.

**How the shipped catalogs were filled.** The 23 catalogs translate 93-99 %
of the pot's 2,319 keys (October 2026); the rest -- jargon, placeholder-only
frames, loanwords that read the same -- is left empty and English serves
it. The September fill ran through `fill.ts`; the upstream labels converted
in October and the worst of the earlier entries were written by translation
agents working slot by slot from the `#.` context and each catalog's
existing terms, outside the repository's tools. Either way the same gate applies: `sweep.ts --dry` must
empty nothing before a compile. None of it has had a native speaker's
review.

## Placeholders, whole phrases, and the two shapes

Two structural rules keep the catalog translatable. An MT pipeline that breaks either produces English-looking output that is broken in every language; the compiler catches the first, nothing can catch the second at build time.

**A key is a complete translatable phrase — never concatenate translated fragments.** Word order differs too much between languages for "label A + label B" composition to work. When a sentence needs a value inside it, the key carries a `{var}` placeholder and the whole sentence is one key:

```po
#. Notification title for a message in a channel: {nick} is the sender's
#. nickname, {target} the channel name. Translated as a whole so word order
#. is free; the unread-count suffix is appended after it, never inside.
msgctxt "sw.titleChannel"
msgid "{nick} in {target}"
msgstr "{nick} in {target}"
```

A German translation is free to reorder the frame around its variables — `"{target}: {nick}"`-shaped word order is exactly what placeholders are for; a fragment pair `"in"` + `"{target}"` glued together in code is not. The worked counter-examples are everywhere user content meets a frame: `connection.error` carries the server's or browser's technical text **verbatim** in `{message}` (`"Connection failed: {message}"`-shaped keys never reword `{message}`), and system-message frames wrap `<bdi>`-wrapped nicks with a frame key such as `msg.join` ("has joined the channel") instead of building "alice" + "has joined" + "the channel" from parts.

Rules for pipelines and translators:

- `{name}` tokens must survive **verbatim** — same set, same spelling; moving them inside the sentence is expected and correct, dropping, renaming or translating inside the braces is a broken row (compile fails with the key named).
- User content passed into `{vars}` (nicks, channel names, server text) is substituted at runtime and must not be inflected around: do not add grammar that assumes the variable's form (article gender, case endings) — prefer frames that keep the variable at a phrase boundary when the target language makes that necessary.
- Never split a sentence into several keys to "reuse" a word; if two labels genuinely share a phrase, they are two keys, each a whole phrase.

**Flat keys vs plural keys — both shapes exist on purpose.** Most keys are flat: one `msgid`, one `msgstr` — labels, verbs, tooltips, whole sentences (`cmd.lobbySend`, `cmd.usageJoin`, `connect.submit`). Keys rendered through `tCount()` are plural entries: they carry `msgid_plural` and one `msgstr[N]` per plural form of the language, and the compiler evaluates the tag's `Plural-Forms` expression for n = 0…199, cross-references `Intl.PluralRules(tag)`, and emits the text keyed by CLDR category (`{"one": …, "other": …}` for English; Russian compiles to `one/few/many/other`, Arabic to all six):

```po
#. Condensed block: {count} users joined while the block was collapsed.
msgctxt "condensed.join"
msgid "{count} user has joined"
msgid_plural "{count} users have joined"
msgstr[0] ""
msgstr[1] ""
```

Fill `msgstr[N]` exactly as gettext expects (`nplurals` slots, in the expression's index order — the `Plural-Forms` header's). Do **not** "fix" a flat key into a plural or a counted key into a flat one: the shape is chosen by the call site (`t()` vs `tCount()`), and a flat verb like `cmd.lobbySend` has no number to agree with. The English source of a plural entry is always the _singular_ first — the msgid — even where English uses the plural for most counts; that is gettext's layout, not a typo.

## What is never translated

The catalog is UI chrome and client-authored copy **only**. Never translated, never passing through `t()`, therefore never present in the `.po` files — and MT pipelines are never pointed at any of it:

- message bodies (own or anyone's), topics, MOTD, away/kick/part reasons, CTCP content, WHOIS output, channel lists, ban lists — anything a user or the ircd typed;
- usernames/nicks and channel names — they render verbatim, wrapped in `<bdi>` where they sit inside a translated frame;
- **server text** — numeric replies, `FAIL`/`WARN` payloads, the IRC server's own words. `connection.error`'s `{message}` is the server's or browser's technical message verbatim inside a translated frame: translate the frame, never the placeholder's content;
- brand names — `Seance` in the worker's fallback notification title included (the worker cannot read a deploy's `appName` today);
- dates, times, numbers, list conjunctions and sorting — `Intl.DateTimeFormat`/`NumberFormat`/`ListFormat`/`Collator` produce these per active locale (`client/js/i18n/dates.ts`); the only catalog copy in that area is `dates.today`/`dates.yesterday`.

A translator meeting English prose in the wild (a server notice, a user's message) is looking at data, not at a missing row.

## Keeping a translation alive

After an upstream merge or any pot change, sync every `.po` against the pot:

```sh
yarn i18n:merge                      # every client/locales/*.po
yarn i18n:merge de                   # one
```

`yarn i18n:merge` runs `tools/i18n/merge.ts` (msgmerge-lite) and keys entries by `msgctxt`: a translation survives an exact `msgid` match; a drifted `msgid` is re-adopted from the pot and the entry is marked `#, fuzzy` for review (the old translation is kept as the draft); keys new to the `.po` are appended with empty `msgstr` slots; keys the pot no longer carries are dropped. The `Language`/`Plural-Forms` headers are rewritten from `plural-rules.json`. It never invents translations.

- **Keys are stable identifiers.** A key rename is not a translation-preserving operation — merge would drop the old key and add the new one empty. When the English copy changes, change the `msgid` (via `tools/i18n/add.ts`, below) and keep the key; `merge.ts` then marks the entry fuzzy and the translation survives as a draft to re-review. Rename keys only when the _meaning_ changes, and let `merge.ts` do the bookkeeping — never by hand inside a `.po` (a hand-renamed `msgctxt` is exactly a drop-plus-add, with the translation lost).
- Fuzzy is reviewed, then un-fuzzied by removing the flag by hand (the one sanctioned hand edit alongside filling `msgstr`s); compile skips fuzzy entries either way.
- There is no `en.po`: the pot compiles straight to `en.json`. Likewise `qqx` (§ Verifying) has no `.po` — it is generated.
- The po writer has one canonical order for an entry's comment lines (`#.` context, then `#:` references), which the catalogs on disk predate: the first merge or sweep that rewrites a `.po` after this branch moves those lines into it, once, across every catalog. It is a comment reshuffle — no `msgid`, `msgstr` or flag changes — so read that diff by its stat line, not line by line.

## Adding a language

The language list lives in one place: `translation-languages.txt` at the repository root — there is no copy under `docs/`. For the beta, 22 shipped locales were dropped from it as unusable machine output (Afrikaans, Bulgarian, Bangla, Catalan, Welsh, Greek, Basque, Persian, Finnish, Irish, Galician, Hebrew, Croatian, Indonesian, Malay, Norwegian Bokmål, Slovenian, Serbian, Swahili, Tamil, Urdu, Hindi); `tools/i18n/sync.ts` archived their `.po` files to `client/locales/attic/` rather than deleting them, so a future refill un-archives one by adding its name back to `translation-languages.txt` and moving its `.po` out of `attic/` (or letting `sync.ts` scaffold a fresh one) before filling it.

1. Add the language's English name to `translation-languages.txt` (repository root) and its tag to `NAME_TO_TAG` in `tools/i18n/targets.ts` — the selector's list is generated from that file, in its order. An unknown name fails the compile with the name that has no tag.
2. Add one line to `tools/i18n/plural-rules.json` — the tag and gettext's C plural expression (`{"nplurals": 4, "expr": "(n%10==1 && n%100!=11 ? 0 : …)"}` for Russian). The expression is restricted to arithmetic; `compile.ts` refuses anything else.
3. Scaffold the catalog: `yarn i18n:sync` (or any `yarn i18n:compile`)
   writes `client/locales/<tag>.po` for you -- headers, the tag's plural
   forms from `plural-rules.json`, empty `msgstr`s; an existing file is
   never touched. Fill it (§ Filling in a language).
4. That is all: `yarn i18n:compile` picks the file up, regenerates
   `available.ts`, and the dev-only selector (the 🌐 globe beside the logo)
   lists it automatically. `en` and `qqx` are compiled from the
   pot/generated — a hand-written `en.po` or `qqx.po` is refused.

### The selector's list vs the catalogs

One language selection drives the interface and the reading language alike (`client/js/i18n/index.ts` `userLanguageRef`, consumed by `translate/reader.ts` `readingLanguage()`). It lives in the `locale` setting: `"auto"` — the default — resolves from `navigator.languages` against **every** language in `translation-languages.txt` (the translation roadmap), not just the ones with compiled catalogs — the exact tag, else its base language (`core.ts` `bestLocale`, restated in `client/js/prepaint.js`), so `pt-PT` takes the one Portuguese catalog, Brazilian. Traditional Chinese is the exception: `zh` is Simplified, so `zh-TW`, `zh-HK`, `zh-MO` and `zh-Hant-*` (`i18n/traditionalChinese.ts`; the script subtag beats the region) never fall to it, nor does the bare `zh` Chrome appends after them — they resolve to a later preference or English, interface and reading language alike, while a `zh-CN`/`zh-Hans` further down still picks `zh` and choosing Chinese by hand is unaffected. A production build has one manual selector, Settings → Translation's language select (`LanguageSelect.vue`); a development build adds the 🌐 globe beside the sidebar logo, the same component. The Settings select stands outside the tab's `translation.enabled` branch: a deploy that sets `translation.enabled: false` keeps it, labelled "Interface language", since it is then the interface's language alone. A pick without a compiled catalog is still the user's language: the interface falls back to English copy until its translation lands, while reading translates into it regardless. Labels are the language's own name (`Intl.DisplayNames` of the tag: `Deutsch`, `العربية`, `اردو` — never the English name, except English itself), each option rendered with its own `lang`/`dir`, so a right-to-left name shapes correctly inside the list. Direction itself comes from `core.isRTL()` — the single RTL source of truth the pre-paint script shares (pinned together by the tests). As `.po` files land, their catalogs activate on the next compile with no code change. The globe opens the list as a panel (no settings navigation, works over a dead network; a pick applies at once and the panel closes — `tools/scenarios/sidebar-language.mjs`).

### The build tracks the language list

`tools/i18n/sync.ts` keeps `client/locales/*.po` in step with the targets
in `translation-languages.txt` — standalone as `yarn i18n:sync`, and
automatically at the top of every `yarn i18n:compile`, so the build itself
tracks the list instead of a remembered manual step:

- a target with no `.po` is **scaffolded** (headers, the tag's plural
  forms from `plural-rules.json`, empty `msgstr`s; an existing file is
  never touched);
- a `.po` whose tag is no longer a target is **moved into
  `client/locales/attic/`** (an unstaged move — stage it like any other
  change). Nothing is deleted, and the attic subdirectory
  is invisible to compile's non-recursive listing, so a stray catalog
  never reaches the build; when attic already holds a file for the tag,
  the stray is left in place with a warning (the archived copy is the
  older one and wins).

A run with nothing to do prints nothing. This closes the two failure modes
the manual workflow had: a new tag got no `.po` until someone remembered
`scaffold.ts` (whose `--force` once wiped completed fills), and a removed
tag's `.po` kept compiling forever. The catalogs are tool-shaped by
scaffold/sync/fill, so prettier ignores them (`.prettierignore`) — a po
writer owns their formatting.

## Verifying a translation

```sh
yarn i18n:compile                                        # compile + validate
npx tsx tools/i18n/check.ts                              # pot ↔ call-site agreement (also run inside yarn test)
yarn build                                               # a servable development build (NODE_ENV unset)
python3 -m http.server -d public 8000                    # serve, pick the language at the dev globe
```

- **The compile writes the same files in every mode; the webpack build decides the flavor.** `compile.ts` reads no `NODE_ENV` at all: `available.ts` carries no `DEV` const, lists every compiled catalog and marks `qqx` `devOnly`, and `tags.json` lists every compiled tag, `qqx` included; the pre-paint script's list is that file read through `tools/i18n/available-locales.ts` `readAvailableLocales`, which drops `DEV_ONLY_TAGS` in a production build before webpack substitutes it into `js/prepaint.js` as it copies it (the pre-paint script can run no check of its own; it is a file rather than an inline script because a Content-Security-Policy refuses those). What hides the rig is the **bundler's own fold** — `DEV_I18N` in `client/js/i18n/core.ts` is `process.env.NODE_ENV !== "production"`, and the selector (`LanguageSelect.vue`) and `activate()`'s resolvable set both filter through it. That is why `yarn watch`, `yarn test:e2e` and a bare `webpack` — none of which compile — behave correctly whatever mode the last compile ran in, and why a production build leaves the tree clean.
- `yarn i18n:check` (`tools/i18n/check.ts`) cross-checks the pot against the live tree: every `t()`/`tCount()` call-site key exists in the pot, every pot key is referenced, every key carries `#.` context. It runs inside `yarn test` (`test/tests/i18n-toolchain.ts`, live-tree assertion), so a stale pot fails the suite.
- **`qqx` is the eyeball rig, not a language**: a generated pseudo-translation of `en` (accented lookalikes, doubled length, RTL-wrapped) listed in the selector only in development builds. It exercises direction, doubling-driven overflow and the plural plumbing with zero translation effort. **It never ships — at any layer**: a production build folds it out of the selector and out of `activate()`'s resolvable set (so a stored qqx pick — a settings restore from a dev machine — falls back to the automatic resolution), the pre-paint list webpack bakes into `js/prepaint.js` drops it (`client/locales/tags.json` lists it; `readAvailableLocales` filters it out for production, and `tags.json` itself is never copied to `public/`), so the pre-paint script does not know it either, the lazy `import()` of the locale catalogs excludes `qqx.json` (and `tags.json`) from the emitted chunks, and webpack does not copy `qqx.json` into `public/locales/`. The generated `qqx.json` itself is written on every compile — it is the rig's artifact, like any other catalog. A real locale is verified the same way the scenarios verify `qqx` (`tools/scenarios/i18n-rtl-layout.mjs`, `i18n-language-switch.mjs`) plus by eye: every theme, both directions, and the settings modal.

## Deploy rebranding vs translation

A deploy (an IRC network shipping its own client) overrides strings through `config.json`'s `strings` object; users' translations live in `.po` files. Resolution at runtime, first match wins:

**branding override → active locale catalog → `en` → the key itself**

(`client/js/branding.ts` for non-Vue callers, `useI18n().t` for components — one chain.) The override is the deploy's voice — in the deploy's language — and wins in every locale, translation included: a German user on a deploy that overrode `connect.submit` sees the deploy's wording. Any key in the English catalog may be named in `config.json` (see `docs/resources/branding.md` § `config.json` schema); `.po` files carry translations, `config.json` carries the deploy's own copy. The two mechanisms do not overlap.

The chain is uniform where the reader reads in-page copy: `useI18n().t`, `useI18n().tCount` and the splash loop in `activate()` all resolve through one override-aware helper (`brandingT()` in `client/js/branding.ts`), and the override interpolates its `{var}`s exactly as a catalog entry would — a plural key's override is the flat template, with `{count}`/`{n}` filled in. (`brandingString()` — the pre-i18n non-Vue entry point — resolves its own equivalent chain: string override → core resolver; same result, separate path.) Some bypasses are known and deliberate (the Task 4 ruling, documented):

- **The IRC layer resolves through core `t`** (`client/js/irc/**` imports from `i18n/core.ts`, not the Vue binding), so its status strings bypass overrides by ruling: they are catalog copy, not the deploy's voice.
- **The same is true of the Vue-free modules that import core `t` directly**: `client/js/helpers/contextMenu.ts`, `client/js/helpers/mediaTrustMenu.ts`, `client/js/socket-events/connection.ts`, `client/js/socket-events/msg.ts` and `client/js/upload.ts` (its thrown `UploadError` messages). A deploy overriding `menu.*`, `link.*`, `connection.*` or `upload.*` keys reaches only the pages' chain — these surfaces keep catalog copy. New Vue-free modules should make the same choice deliberately and note it here.

## For developers: adding or changing a string

- New UI strings go through `t()`/`tCount()` (`useI18n()` in components; core `t` for Vue-free modules; the worker's own resolver for `client/service-worker.js`) — never raw literals in templates, never string concatenation across keys (§ Placeholders).
- Register the key in the pot with `tools/i18n/add.ts`:

  ```sh
  npx tsx tools/i18n/add.ts <key> "<msgid>" [--plural "<msgid_plural>"] \
    --context "<what the label is and does>" --loc <file:line>
  ```

  The context lines are translator- and MT-facing documentation: say what the label is, where it appears, and what each `{var}` carries — including _verbatim_ markers for user content (`{message} is the verbatim technical message — never translate its content`). `add.ts` upserts idempotently, keeps the pot sorted, and never invents translations.

- Run `yarn i18n:compile` after pot changes (the compiled `en.json`/`qqx.json` and `available.ts` are committed, so a stale pot is a visible diff), and `npx tsx tools/i18n/check.ts` — or just let `yarn test`'s live-tree assertion catch the drift.
- `check.ts` reads call sites with a deliberately simple regex: the key is a **literal**, in either quote style (`t("key")` or `t('key')` — the latter is what a `"…"` Vue attribute forces), never concatenated and never computed. In a `.vue` file only the `<script>` block is read as JavaScript, so an apostrophe in template prose is prose, not an unterminated string.

## Numbers: {vars}, formatNumber, and the badge

A numeric `{var}` inside any translated frame is written by the active locale — digits, decimal separator, no grouping: `{seconds}` in the reconnect countdown, `{port}` in the STS notice, `{count}` in every plural. `en` writes `6667` and `1500`, `de` writes `1,5` for 1.5, `ar-EG` writes `٦٦٦٧`. Grouping is deliberately off for `{vars}` (a port or a countdown never reads `6,667`); a call site that renders a standalone number and wants the locale's grouping uses `formatNumber(n)` (`client/js/i18n/numbers.ts`): `1,500` / `1.500` / `١٬٥٠٠`. `formatCompact(n)` is the tight-spot form — the unread badge's `1.5K` (en), `15.000` (de), `١٫٥ ألف` (ar-EG). The locale owns both the abbreviation and the threshold: German has no "K" for thousands, so a de badge may read `1500` where the en one reads `1.5K`. The badge itself (`roundBadgeNumber`) is built on these; message timestamps, date markers and relative times were already Intl (`i18n/dates.ts`).

## Dynamic labels: the four classes and their disposition

A rendered label whose final text is produced at runtime is "dynamic" in one of four ways, each with its own ruling:

1. **Fragment + name combinations** — retired. The system messages (`msg.join`, `msg.part`, `msg.quit`, `msg.kick`, `msg.mode`, `msg.nick`, `msg.away`, `msg.back`, `msg.chghost*`, `msg.invited*`, `msg.ctcpRequest*`) used to place a translated fragment next to the interactive `<Username>`; the translator could not control the sentence around the name. They are whole-sentence keys now (`system.join`: "{nick} has joined the channel", …) with the nick as a VERBATIM `{var}` placeholder, rendered by `frameSegments()` (`client/js/i18n/core.ts`) for one placeholder and by `I18nFrame.vue` (`framePieces()`, slots in the order the translation puts them) for two or more: the translation is split on the placeholders and the interactive elements land inside it — the translator owns the full sentence, the click-for-context-menu behaviour is preserved.
2. **ListFormat phrase-combining** — accepted, and audited: `MessageCondensed` warns once per session — `dynamic label (fragment combination): N translated fragments joined via Intl.ListFormat`.
3. **`{var}`-filled frames** — the endorsed pattern, and audited: every frame warns once per key+locale in development builds — `dynamic label ({var} frame): "connect.connectingTo" renders 2 runtime values (host, port) — the sentence is dynamic; the translatable unit is the whole phrase` — so the census stays visible while you browse (26 lines in one chat-flow sweep).
4. **Key-argument composition** — zero, enforced. `check.ts` fails the suite on a `t()` key that is not one whole literal, and the dev-only instrument loader warns at the call site at runtime (next section).

Sentences with elements inside them (Help's `<code>`/`<kbd>`/links, the 333 topic line, the Aliases intro, the search header, the changelog) are one key each with a `{placeholder}` per element, rendered by `I18nFrame.vue`. `check.ts` flags the template form of a fragment (kind `adjacent`): two `t()` interpolations with the same parent and an element or text between them. A single `t()` with the element after it is no pair, so the pot is checked too: an English msgid that opens a parenthesis it never closes (`opensUnclosed`, "…(opposite of" + `<code>/collapse</code>` + ")") fails the check, since a translator handed the fragment closes it and the page shows the parenthesis twice.
