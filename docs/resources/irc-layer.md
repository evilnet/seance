# IRC layer notes

The IRC layer's module notes and the rules each protocol feature follows, moved out of `CLAUDE.md` on 2026-11-02.

## `multiline.ts`

**`multiline.ts`** — `draft/multiline`: `parseMultilineValue`/`IrcClient.multilineLimits()` (the one gate the whole feature is behind), `multilineBatch` (a received batch joined into one message, tags off the opener), `planMultiline`/`sendMultiline` (multi-line input as `BATCH … draft/multiline` with `draft/multiline-concat` chunks). **Batches go out one at a time, paced past the server's cooldown**: nefarious2 charges a cooldown per delivered batch and, for a batch opened inside that window, drops the opener while still delivering its lines as standalone messages (they duplicate; blank ones draw `ERR_NOTEXTTOSEND` and the closer `FAIL BATCH NO_ACTIVE_BATCH`). The echo comes back long before the cooldown ends, so the next batch waits out an estimated cooldown too — `batchCooldownMs`, the undiscounted `(2 + bytes/128) s` — held by the queue's `pace` timer (`paceAfter`), set after **every** delivered batch (so the gate outlives the message and the _next_ message's batch is paced too) and timed from **delivery** (the echo, or a settle period without `echo-message`), not from the send, so a batch the server processes late under throttling still starts its cooldown at the right moment. A `FAIL BATCH MULTILINE_COOLDOWN` (estimate too low) still re-sends rather than reports. `FAIL BATCH MULTILINE_*` and the server's per-message `WARN BATCH MULTILINE_FALLBACK` are in `handlers/standard-replies.ts`. See `docs/projects/multiline-messages.md`.

## Oper-tool modules

`request.ts` (labeled request → whole answer), `oper.ts` (oper state), `snotice.ts` (notice/WALLOPS routing), `noticelog.ts` (IndexedDB notice log), `operprefs.ts` (routes, snomask), `profiles/` (per-ircd notice classifier, STATS/CHECK report builders, ban rules), `services/` (per-package services profile: X3's snoop, audit and module-log parsers, ban command and replies), `services.ts` (the bots' liveness check, a bot's NOTICE in answer to a command, bans through the oper service), `quiet.ts` (a labeled PRIVMSG whose echo is dropped), `alerts.ts` (the alert builder's lookups: `stats alerts`, `trace print`, `addalert`, `delalert`, the opers by WHO, the own O3 level) and `servicesfeed.ts` (the services bots' channel lines into the notice log) are the oper tools — see the Oper tools bullet above.

## Other modules

`manager.ts` (`NetworkManager` registry, `createNetwork`), `bus.ts` (bus handlers, store-free), `history.ts` (`draft/chathistory` + batches; distinct from `client/js/history.ts`, the input history), `catchup.ts` (per-channel history/marker fetch after JOIN — the active channel at once, the rest through the background queue, in the order one `CHATHISTORY TARGETS` gives: channels written to most recently first, the ones it leaves out next, a reconnect's channels with nothing new last — still fetched, since the index is a hint, not proof; then a logged query's `MARKREAD <nick>` while it has unread lines, `enqueueMarkerFetch`: only with the cap, once per connection, a `last` job behind every channel's), `fakelag.ts` (`FakeLagClock`: the server's fake-lag clock replayed on our side — every line `IrcClient.send` sends after 001 is charged `2 + bytes/120` s, as nefarious2's `parse.c` does, and the server stops parsing our lines at 10 s ahead; `BackgroundQueue` = `IrcClient.background`: work nobody is waiting for — other channels' catch-up, marker queries (dropped at their turn when the server volunteered the marker first), the `MODE` of the open or first-opened channel, the reconnect walk's `CHATHISTORY BEFORE` pages, the oper-up queries (`IrcClient.whenRoom`), debounced `MARKREAD` sets (at the front, a channel's at most once per 10 s, so a busy open channel cannot starve the catch-up), the connect-time `WEBPUSH REGISTER` renewal — goes out only while the clock is under 4 s, so three of the user's own lines always go straight through; what the user asked for (opening a channel, typing) never waits there, and a `+typing` notice goes only when nothing is queued. The dev ircd's image turns fake lag off for users, so it never shows the delay; `tools/scenarios/connect-fakelag.mjs` documents running against a copy with it on. Tests pass `fakeLag: NO_FAKE_LAG` to keep the old immediacy and `IRCU_FAKE_LAG` to test the pacing, `test/irc/fakelag.ts`, `test/irc/catchup.ts`; browser check `tools/scenarios/connect-fakelag.mjs`; see `docs/projects/connect-burst.md`), `historysearch.ts` (`soju.im/search` and the search window's `CHATHISTORY AROUND`: rows go through the handlers in collect mode and straight to the window, never a channel; see `docs/resources/client-features.md` § Searching history), `persistence.ts` (nefarious2's built-in bouncer, `draft/persistence`: after `PERSISTENCE STATUS ON` the autojoin waits for the server's restoration batch, which is applied as state only; also the `PERSISTENCE ATTACH default <msgid>` catch-up cursor — offered in the `CAP END` flush after a successful SASL, its `evilnet.github.io/bouncer-replay` batch appended as new messages, and `catchup.ts` stood down while it is accepted. See `docs/projects/seamless-reconnect.md`), `sts.ts`, `saved-networks.ts` (`thelounge.networks`), `querylog.ts` (private conversations kept on the device, `thelounge.querylog.<uuid>`, saved networks only: a query's lines are logged from `pushMessage` and history pages, edits/redactions/reactions follow through `IrcClient.dispatch`, and the constructor brings the logged queries back as windows whose lines are one `more` page on the first announce — remembered by msgid, so the server's own replay of them is deduplicated. Each query also keeps its read point (`LoggedQuery.read`, moved by `handlers/markread.ts` `moveReadMarker`): restored lines past it count as unread, and `catchup.ts` `enqueueMarkerFetch` asks the server for the marker of each query with unread lines. A cycle, not an archive: 200 lines per query, 30 queries, ~300k characters per network, oldest conversation out first; closing a query forgets it, removing the network forgets all. A closed query stays closed: its tombstone (nick + the time of its newest line from the server, `irc/closedQueries.ts`, `thelounge.state.closedQueries`, shared as the private metadata key `seance/closed`, which opers can read; neither kept nor shared while `keepPrivateConversations` is off) keeps a replayed line from before the close from reopening it — catch-up, a batch, an unwrapped replay in the settling window, a log in another tab or device — while a later line, or any live one whatever its time (another server's clock can trail ours), reopens it, and `/query` is a reopen that outranks the close everywhere (`docs/projects/closed-queries.md`). The user can switch it off (Settings → General, `keepPrivateConversations`, default on; its `apply` calls `setQueryLogEnabled`, at boot too, before any network is created): off deletes every `thelounge.querylog.*` key and keeps and restores nothing. Tests: `test/irc/querylog.ts`; browser check `tools/scenarios/query-log.mjs`), `ids.ts` (one shared id allocator across networks; history ids are negative), `errors.ts`, `hostmask.ts`, `wire.ts`, `types.ts`.

## Replies, reactions, deletion and edits

Replies, reactions, deletion and edits (bus-contract §1.4): `Channel.idByMsgid` / `idOf()` is the msgid → id map; `client.react()` / `redact()` / `editMessage()` send, `handlers/tagmsg.ts` / `handlers/redact.ts` / `privmsg.ts` (`+evilnet.github.io/edit`, or `+seance/edit` while both are sent) dispatch `msg:react` / `msg:redact` / `msg:edit`. **An edit takes its original's place**, own or anyone's: the store (`helpers/messageUpdates.ts` `applyEdit`) moves the new message behind the hidden original and gives it the original's `time` (`editedAt` keeps the edit's), the pending copy of an own edit stands in the same way (`pending.ts` dispatches its `msg:edit`), and an edit raises no unread, no notification and no unread marker unless it highlights. Anything that refers to another message by msgid must go through `client.afterReplay(fn)` so that inside a chathistory replay it runs after the batch's messages have ids. **A quote of a message is one styled, inert line**: the reply quote under a message and the composer's `Replying to …` / `Editing` bar both render `QuotePreview.vue` — `quoteLayout(text, 80, {markdown})` (`layout.ts`, Vue-free, `test/helpers/layout.ts`) folds the message's tree to styled text nodes (bold stays bold, a code span or block monospace, a header bold, a spoiler stays `(spoiler)`, links/nicks/channels are their text since the quote sits inside a `<button>`), collapses whitespace and cuts at 80 visible characters; `helpers/fragment.ts` `createFragment` (shared with `parse.ts`) gives each run the message's own `irc-*` classes. Markdown only when the setting is on; IRC control codes always become styles. The tooltip and aria-label use `toPlainText` of the same nodes. Browser check `tools/scenarios/reply-quote.mjs`. Wire constants (`REPLY_TAG`, `EDIT_TAG`, `REACT_TAG`, `UNREACT_TAG`, `REDACTION_CAP`, `TYPING_TAG`) live in `wire.ts`.

## Unread counts live in the IRC layer

**Unread counts live in the IRC layer.** `IrcClient.pushMessage` counts what someone else said (`SAID_TYPES`, not an edit) or a highlight, unless someone is looking at that conversation (`presence.attended` and the open one) or it is at or before the read marker; a catch-up (`replay`) counts the same way and only skips the notification. Lines delivered without `pushMessage` — a history page (`deliverPrepend`), restored query lines — count past a known marker through `countsAsUnread` and reach the store through `markread` (`more` carries no counters). `applyReadMarker` only ever lowers a count, from the per-line `MsgRef.unread`/`highlight` flags. Our own speech clears the counters (an old line of ours in a catch-up or a history page recounts up to its time); our own JOIN/MODE never does. Someone opening a conversation, or attention returning to the open one, reads it through `readNow` (counters to 0, `markread` to the store — `RoutedChat.vue` zeroes nothing — and a `MARKREAD`); the read point moves even where the server keeps no markers (a query's is kept in its log), and a client created on a hidden page starts unattended (`manager.ts` `createNetwork`). A catch-up that leaves a query unread asks for its marker (another device may have read it). The store takes the counters as sent, the open conversation's included (the app badge sums highlights). Tests: `test/irc/history.ts` (catch-up), `test/irc/markread.ts`, `test/irc/presence.ts`, `test/irc/attach-cursor.ts`, `test/irc/querylog.ts`; browser check `tools/scenarios/unread-badges.mjs`.

## Reconnects are quiet: a join burst is state, only what was asked for is a line

**Reconnects are quiet: a join burst is state, only what was asked for is a line.** A reattach can bring the server's join burst several times over (session restore, our re-JOIN, the bouncer's alias attach), and a page that was reloaded or killed in the background (F5, a phone's PWA) remembers none of the earlier ones, so nothing may be shown by comparing with what the page last saw. `topic.ts` puts a 332 in the header (`topic` event, when it differs) and prints it and its 333 only for a channel the user joined by hand on this page (`Channel.topicWanted`: the `/join` request is consumed by a JOIN that is neither a restore nor a re-join, `handlers/join.ts`, and cleared by that burst's 366 — the header truncates a long topic) or for `/topic` (`Channel.topicAsked`). `mode.ts` prints a 324 only for a bare `/mode` (`Channel.modesAsked`); the lazy `MODE` the client asks itself (`catchup.ts` `queueModes`) is state. A topic or mode that changed while we were away comes back as the TOPIC/MODE event in the history (`draft/event-playback`; nefarious2 stores both), with who and when, in its place in the timeline. A JOIN for a channel already JOINED produces no line and no second `CHATHISTORY`/`MARKREAD`/`MODE` (`Channel.rejoining`, `client.restoring` and the state check in `handleMessage`). The catch-up (`CHATHISTORY LATEST`, then a `BEFORE` walk back to what we hold, `history.ts`) is what shows what actually happened. Keep new join-burst handlers consistent with this. The bouncer's own setup chatter (`NOTE BOUNCER ALIAS_ATTACHED`, the `Session resumed…` NOTICE) is silenced by the settling window instead — `persistence.ts` `beginSettling`, opened by _every_ registration, because `PERSISTENCE STATUS` does not reach us on every server's attach path.

**A reconnect's catch-up lines go in by server time.** The walk keeps a page line unless it is older than `min(newest held − CATCHUP_FUZZ_MS, oldest held)` (it was never loaded: scrolling up brings it as history), and drops one whose msgid is already shown. What is newer than every line held at the JOIN takes an id from the block reserved when the catch-up started (`IdAllocator.reserve`), so it sorts above the lines relayed live meanwhile. What is not newer — a line missed between two held lines (#292), or one inside the skew window but older than everything held (#290) — goes after the last server-stamped row no later than it (after a tie), or before the first one: `history.ts` `placeByTime` gives it an id between its neighbours' ids, which is what `insertMessage` orders rows by. A run after a row is spread evenly over the open interval up to the next row, at most one unit past the lower id's integer part, so placed ids are fractional, never collide with an allocated one, and the unit above an id holds only its own channel's rows. A run before every row takes fresh history ids (`IdAllocator.historyIds`) instead: a fraction under the first row would sit in the unit of another channel's id. Out of float precision after very many splits of one gap, a line keeps a reserved id and shows below its newer neighbours. No line that is not newer becomes `newestRef`, one of ours moves `firstUnread` only forward (`msg.placed` on the bus), and one that counts as unread under the marker moves `firstUnread` back to the row before it, so the marker sits above it; it is flagged `msg.counted`, and the store does the same against its own marker. Live lines are untouched, and so is the server-driven replay off the ATTACH cursor (`deliverCatchup`), which has no held set to place against. Tests: `test/irc/history.ts` (`#292`, `#290`).

## A SASL login that was asked for must succeed

**A SASL login that was asked for must succeed.** When `options.sasl` is set and the exchange does not end in 903, `IrcClient.saslFailed()` reports why in the lobby and — unless the deploy set `features.saslDisconnectOnFail: false` in `config.json` (`saslRequired`) — QUITs instead of registering unauthenticated. What follows the QUIT depends on the failure's cause (`SaslFailureCause`, `saslFailed`). **The server could not check the login** (`server`): our 12 s timeout, nefarious2's own 10 s one — which comes first, as `904 :… request timed out` — its services unreachable (`904 :… service unavailable`) or split mid-exchange (a 906 it sent; `sasl.ts` `isServerSideFailure`, `SaslResult.retryable`): the client QUITs and hands the socket to `transport.abandon()`, which reports it as lost and reconnects on the usual schedule (`closeExplained` silences the duplicate close report). **No usable `sasl` cap or a NAK** (`unavailable`; nefarious2 drops the cap from `CAP LS` while its services are split — and still ACKs a request for it, so the NAK is other ircds') is retried the same way on a network where this account has logged in before (`irc/saslTrust.ts`, `thelounge.state.saslOk`, uuid → account), and final anywhere else. **A bare 904** (`unexplained`: nefarious2 sends it for a wrong password and for a Keycloak it cannot reach alike) gets `SASL_TRUSTED_RETRIES` (3) more connections for such a login — then this connection stays down but the login and the autoconnect are kept (`SASL_TRUSTED_GAVE_UP_HINT`): a Keycloak outage reads as bare 904s for its whole length, with `sasl` withdrawn and re-offered between them, and the cold start after it must still dial; the next connect gets the retries again. The trust is forgotten when the credentials are edited (Settings, with or without a live client; also in `applyPendingOptions`, so an edit made while the old login ran and succeeded does not inherit it) or typed anew on the connect form (`typedCredentialsDiffer`: a password the entry does not remember starts untrusted at every sign-in — the user is there to read a refusal), when a refusal is final, when the network is removed (`saved-networks.ts` `remove`, which the Networks page calls with no client) and when a settings backup is restored (`CLEARED_ON_RESTORE`; the backup never carries the key). Everything else — missing credentials (caught in `onOpen`, before `CAP LS`), 902/905/907, an untrusted login's 904 or missing cap — is final: the network stays down, the login is forgotten and autoconnect is turned off (`onSaslRejected`). Once the user has disconnected, a failure ends with its report: no retry, no held-back close report. Tests: `test/irc/client-sasl.ts` "the server could not check the login", `test/irc/saslTrust.ts`. `handlers/cap.ts` drops whatever the negotiator had queued once `client.isQuitting` or the socket is gone (`client.socketOpen`: a retried failure abandons it inside `beforeEnd`, and the `CAP END` flush would otherwise be reported line by line as sent while disconnected; `finalLines` and `registrationAwayLine` check the same, so no state is set for a line that does not go out). See `docs/resources/nefarious2-websocket.md` § SASL for what the server does.

## The retry schedule spaces automatic retries only; anyone who asks restarts it

**The retry schedule spaces automatic retries only; anyone who asks restarts it.** `WsTransport.connect()` from outside (the foreground poke `reconnectAll` on a `reconnect-wait` network, a click, `redial()`) zeroes the attempt counter, and so does a socket lost while `probe()` was waiting, so a failed foreground dial waits 1 s next, never the 60 s cap that built up while the app was away. Waits at the cap stay at or above 45 s (jitter `[3/4, 1]`): nefarious2's IPcheck refuses the fourth connection from an address within 40 s gaps and a refusal renews the window (`docs/resources/nefarious2-websocket.md` § Connection throttle). `transport.abandon(reason)` is how a layer above drops a socket without dropping the network. See `docs/projects/seamless-reconnect.md` § Round seven. The server's connection throttle is the server's to say: an `ERROR` with `throttled` in it makes the retry after the close wait the seconds it names (and one more), else 42 s, shown as `status.retryReason` = `"throttled"` in the strip (`handlers/error.ts` → `IrcClient.noteThrottled` → `WsTransport.throttled`); a dial that fails before it opens (nefarious2 refuses before the WebSocket upgrade today, which reads as any failure, and so does a network not ready yet) is retried after 1, 2 and 4 s, then waits 42–47 s each time until a socket opens, past IPcheck's 40 s window (a dial that hung until the connect timeout, or one made offline, keeps the backoff); those long waits and the server's hold against the foreground poke (`WsTransport.holding`), while Connect now, the sidebar's status icon and a typed `/connect` dial at once whatever the wait (`docs/projects/reconnect-throttle.md`, browser check `tools/scenarios/reconnect-throttle.mjs`). A hold is judged by the clock, not its timer, which stands still while a phone sleeps: the server's is over once the time it named has passed, ours once the host has had no dial for `UNREACHED_RETRY_MS` (`WsTransport.hostQuiet`, this transport's dials and `thelounge.lastDial`'s), and the poke then dials. The quick retries come back after such a quiet spell too, for a `connect()` (the poke, Connect now) or a retry that comes due `WAKE_LATE_MS` (60 s) or more after its time (a frozen page, a phone asleep; it may fire before the poke does): the dials that spent them failed in the background, where the OS takes the network away, and the app coming back is the radio waking. Within the window Connect now still earns none. Tests: `test/irc/transport.ts` § the server's throttle ("slept", "late"). **The long wait after unreached dials is spaced per address, not per dialer**: IPcheck counts every connection from the address, so two networks or two tabs on one host whose 42–47 s waits interleave would keep each other inside the 40 s window for good. Every dial notes its time per host name in `thelounge.lastDial` (localStorage, so the page's networks and its tabs share it), and when such a wait ends sooner than 42 s after the host's last dial, whoever made it, it is pushed back to that point plus the usual jitter (`WsTransport.spacingWait`; the `reconnecting` event says `spaced`, so the strip's countdown follows). A wait that may end claims the host first (its entry names the transport) and reads the claim back 200 ms later (`DIAL_CLAIM_SETTLE_MS`): of two tabs whose waits end together, only the one whose claim stands dials, and the other is pushed back past it. It narrows the race rather than closing it: a tab suspended between its check and its claim can still dial inside the window. The server's own throttle wait is not pushed back: its word stands. A browser cannot see addresses, so two host names on one address are not spaced. Test `test/irc/reconnect-sts.ts` § long waits are spaced per address.

## Every dial applies the stored STS policy

**Every dial applies the stored STS policy** (`sts.ts`; spec `extensions/sts.md`). A policy for the host (learned by this network, another one on the host, or another tab: the store is `thelounge.sts` in localStorage) turns a `ws://` dial into `wss://` on the policy's port before it goes out: at `IrcClient.connect()`, at each of the transport's own retries (its `retry` event: the client closes the plain transport, which then does not dial, and dials the secure one at once), and at the foreground poke's `IrcClient.redial()` of a stuck dial; the upgrade is saved with the network (`onStsUpgrade`). On a plain connection the final `CAP LS` (or a `CAP NEW`) carrying `sts=port=` is acted on before the CAP handler sees the line (`IrcClient.checkSts` runs first in `handleMessage`), so that socket carries nothing but the QUIT: no `CAP REQ`, no `CAP END` that would let the server register us there; a secure connection's `CAP END` still goes in the same flush as its `CAP REQ`. The close of a secure connection that opened reschedules the host's policy to the close plus its last advertised duration, also when its expiry passed during the connection (`refreshPolicy` reads the stored entry whether or not it has expired, and falls back to the copy the connection took when it opened or learned since, `IrcClient.stsPolicy`, when another dial pruned the stored one meanwhile, but not after a `duration=0` on any connection removed it: `thelounge.stsRemovals` counts each host's removals, and a copy is good only under the count it was taken with; a dial that never opened leaves the store alone), and so does the page going away (`pagehide` → `IrcClient.unload`, which also sends the QUIT), since no close event follows it. Tests `test/irc/sts.ts`, `test/irc/reconnect-sts.ts`.

## The catch-up cursor is offered exactly once per connection, and only then

**The catch-up cursor is offered exactly once per connection, and only then.** `IrcClient.cursor` (the newest msgid shown on the network, by `@time`, persisted in `saved-networks.ts`) goes out as `PERSISTENCE ATTACH default <msgid>` from `saslProgress` on SASL _success_, before `CAP END` in the same flush — never without SASL (the server answers `FAIL PERSISTENCE ACCOUNT_REQUIRED`), never after 001, never without the `attach-cursor` token in the `draft/persistence` CAP 302 value, and never with a msgid of 64 bytes or more. While the server accepts it (`client.serverReplay`) the restoration JOINs must not schedule a catch-up of their own (`persistence.ts` `serverReplayCovers`) — the server's replay is that catch-up, and it arrives as an appended `chathistory` batch, not as `more`.

## A refused history is not shown, and not asked again

**A refused history is not shown, and not asked again.** `FAIL CHATHISTORY INVALID_TARGET` is the spec's answer for a target the client may not read as well as one that does not exist, and a network may keep history for logged-in accounts only: nefarious2 with `CHATHISTORY_REQUIRE_AUTH` (on at AfterNET) refuses every channel without `+H` to a client that is not logged in, on every connect. So when it answers a request of ours (by label, or naming its target), `history.ts` `chatHistoryFailed` answers the request with nothing (the "show older" button goes) and `standard-replies.ts` shows nothing; a `/quote CHATHISTORY …` the user typed matches no request and is still shown, and so is any other code. If we were in the channel when it came (a query always counts), `Channel.historyDenied` keeps the account we were logged in as (`""` for none) and `canRequest` sends nothing more for it while `client.account` is the same — the JOIN fill, a reconnect's catch-up and scrolling up alike, across reconnects, since each refused request is a ~2 s command on the connect path. A login or logout (900/901) lifts it; so does a reload. A refusal while not in the channel (a JOIN the server turned down: nefarious2 serves members only) is silent but not remembered. Tests: `test/irc/history.ts` § refused history.

## Bouncers: soju and ZNC

Neither needs a profile; each is told by what it offers. `IrcClient.behindBouncer` is true with `BOUNCER_NETID` (soju bound to a network), `soju.im/bouncer-networks` or any `znc.in/*` cap.

- **The bouncer owns the channel list.** Behind a bouncer the saved channels are JOINed only on the entry's first registration there (`autojoin`, `SavedNetwork.bouncerSettled`, and an in-memory flag for an unsaved network), so the channels typed into the connect form reach a fresh ZNC; after that the bouncer JOINs us to what it holds, and a channel parted from another client stays parted here. A new channel is joined by hand once, and the bouncer keeps it from then on. A soju control connection JOINs nothing. Tests: `test/irc/bouncer.ts`.
- **ZNC's buffer replay** (`BATCH +x znc.in/playback <target>`, on every attach) goes the catch-up's way (`history.ts` `zncPlaybackBatch` → `deliverCatchup`): appended, unread but silent, a closed query reopened only by what was said since. ZNC has no msgids, so a line is known by its time, sender, kind (message, action, notice) and text, per conversation (`noteZncLine` counts the live ones, at most 2000 per conversation). A query's lines restored from this device (`querylog.ts`) are counted in at its first replay on the page (`seedFromQueryLog`), so ZNC's QueryLog buffer does not repeat them after a reload. A buffered line is kept only when the batch holds more copies of it than were already shown, so a buffer ZNC keeps (`AutoClearChanBuffer` off) is not shown twice, and two equal lines in the same second both stay. Our own lines are known only through `echo-message` (ZNC 1.9 offers it), which carries ZNC's time: without it, a line we sent comes back once in the next replay.
- **ZNC's login** is the server password `username/network:password` (`PASS`); a missing or refused one is a 464 before 001 (`serverPasswordFailed`), which stops the entry. ZNC 1.10 also takes SASL PLAIN (its `saslplainauth` module, account `username/network`). ZNC before 1.10 offers no `sasl`, so an entry set to SASL there stops before `CAP END` like any server without it, and the lobby adds the server password hint, unless the entry has a server password already (`saslFailed`, `test/irc/client-sasl.ts`). Checked live against ZNC 1.9.1 and 1.10.3 through a WebSocket line bridge: PASS, SASL, both at once, a wrong password, no login.
- **soju's networks** (`bouncer.ts`, `soju.im/bouncer-networks` and `-notify`): a login without a network is the control connection (the cap, no `BOUNCER_NETID`, and no `bouncerNetId` of its own). It JOINs nothing. Without `-notify` it asks `BOUNCER LISTNETWORKS` through the background queue; with it, soju sends the list by itself. Networks are added only when the control connection logged in with SASL, since soju refuses `BIND` to a PASS login; without it the lobby says so once per connection (`bouncer.saslNeeded`). The manager (`addBouncerNetworks`, choosing with the pure `networksToAdd`) adds each network the entry has not offered before (`SavedNetwork.bouncerSeen`, the newest 200 ids, so one the user removes, or one already saved by hand, is not added back; one left out for want of room is not marked), that is not saved already (bound to it, or added by hand as `account/name`), while fewer than 50 of the account's networks are saved here (`BOUNCER_NETWORKS_MAX`; removing one makes room, and the lobby names any left out), as a saved network of its own: the same server and login, `join` empty, `bouncerNetId` set. Ids must match `[A-Za-z0-9._~-]{1,64}` (`isNetworkId`) or they are dropped. A bound entry sends `BOUNCER BIND <id>` in the `CAP END` flush (`finalLines`), and so does the service worker's own connection for a notification's reply or mark read (`swIrcOpen`, the stash's `bouncerNetId`; it gives up if the cap is not offered). The control connection does not subscribe to push; the bound ones do. `findMatching` skips bound entries, so the connect form finds the bouncer's own. A network deleted on the bouncer (`BOUNCER NETWORK <id> *` on the control connection, or `FAIL BOUNCER INVALID_NETID` answering a bound entry's `BIND`) stops that entry connecting by itself; the refused `BIND` also closes the connection without a reconnect and says so in its lobby (`bindFailed`, `IrcClient.bouncerNetworkGone`). The entry stays for the user to remove. A rename on the bouncer (a `-notify` line or a list giving a new `name`) is followed by the entry bound to it while it still has the bouncer's name (`SavedNetwork.bouncerName`, kept when the network is added; `followRename`); a name the user chose here is kept. A line for an id never seen that gives neither a name nor a host (`state=connected` alone) adds nothing. soju's admin `+o` on the control connection is no oper level (`oper.ts`), so the oper tools ask soju for nothing.
- **The bouncer panel** (`Windows/BouncerPanel.vue`, `/bouncer/<uuid>`, the server button in the control connection's header): every `BOUNCER NETWORK` line on the control connection, whichever way it came (the list's batch, a `-notify` line, a labeled reply), goes through `takeNetworkLine`, which keeps the network's attributes in `IrcClient.bouncerNetworks` (a change merged in; a key without a value is an attribute removed; a whole list forgets what it leaves out) and dispatches `bouncer:networks`. The panel lists them with their state and error and, where the server has labeled-response (`canRequest`; soju 0.7 has none), adds, changes and deletes them through labeled `BOUNCER ADDNETWORK|CHANGENETWORK|DELNETWORK` (`bouncerRequest`; a line over `MAX_LINE_BYTES` is refused before sending). Without labeled-response it is read-only. soju puts the requester's own `BOUNCER NETWORK` inside the labeled batch, so `bouncerRequest` feeds those lines to `bouncerLine`: a network added from the panel is offered like one added from another client (the SASL gate, the cap and the seen-list), and one deleted stops the entry bound to it. Tests: `test/irc/bouncer.ts` § the panel's requests; browser check `tools/scenarios/bouncer-networks.mjs` against the dev soju (`tools/soju-dev/`, soju master, which has labeled-response) and the dev nefarious2.

## A login can give its dial back

## `/who`

**`/who`** (`commands/who.ts`, `handlers/who.ts`): one `who` message per query, rendered as a table by `MessageTypes/who.vue` in the channel the mask names (or where it was typed). With `WHOX` in ISUPPORT the query asks for `%tcuhsnfdar,<token>` (account names included; the token is checked on every 354), otherwise a plain `WHO` and 352 rows; queries are matched to replies in order, a user's own `%fields` spec is sent as typed and answered as plain text, and a reply nobody asked for lands in the lobby as text. The table reads only the base tokens (`--body-color-muted`, `--link-color`, `--window-heading-color`) so every theme colours it; the server is a tooltip on the host, not a column. Tests: `test/irc/who.ts`; browser check: `tools/scenarios/who-list.mjs` (also `--mobile --width=390 --height=844`).

## Pending outgoing messages

**Pending outgoing messages** (bus-contract §1.9, `irc/pending.ts`): with `echo-message` a sent line shows at once as a _pending copy_ — a `msg` with `msg.pending: true`, dispatched straight from `pending.ts` (never `pushMessage`) — and `msg:settled {chan, id}` takes it down when the server answers: the echo, a rejection numeric, an `ACK`, `PENDING_TIMEOUT_MS` (60 s) of silence, or the close. The echo is matched by the `@label=s<n>` every outgoing PRIVMSG/NOTICE (and multiline opener) carries under `labeled-response` — nefarious2 relays it on the echo and on the rejecting numeric — so **tests that pin an outgoing line with both caps negotiated expect `@label=s<n>` in front**. The store keeps copies as a trailing block (`helpers/messageUpdates.ts` `insertMessage`) so the echo lands in place. Tests: `test/irc/pending.ts`; browser: `tools/scenarios/pending-messages.mjs`.

## Nothing but registration before 001

**Nothing but registration before 001.** `IrcClient.send` only checks that the socket is open, and a reconnect's socket is open through the whole CAP/SASL phase, when nefarious2 answers anything else (MARKREAD, CHATHISTORY, JOIN, WHO, TAGMSG…) with `451 Register first.` A sender that can fire on a timer or from the UI while a reconnect registers checks `client.isWelcomed` (001 seen; `isConnected` waits for the end of the MOTD); a debounced MARKREAD that comes due early, or that a dying socket was holding, is kept (`Channel.markReadDeferred`) and sent by `flushDeferredMarkRead` on registration. Tests: `test/irc/markread.ts` "across a reconnect".

## Don't add per-channel commands to the connect path

**Don't add per-channel commands to the connect path.** Every command costs ~2 s of server-side fake lag and past 10 s ahead the server leaves our lines unparsed in its receive queue (`docs/resources/nefarious2-websocket.md` § Fake lag). Autojoin is one `JOIN a,b,c` (`joinChannels`), `MODE` is asked lazily on first open, and anything else per channel goes through `catchup.ts`; the one per-connect command it adds, `CHATHISTORY TARGETS`, pays for itself by ordering the per-channel fetches, the channels written to first. Anything automatic that nobody is waiting for goes through `IrcClient.background` (`fakelag.ts`), not straight to `send`; a fixed timer cannot see what else went out and parks the server's clock at its ceiling. Before adding a command to the connect path, check whether the server already volunteers the answer (nefarious2 sends the read marker after every JOIN for a logged-in account, and `PERSISTENCE STATUS` during registration) and whether it can go before `CAP END`, where it is free (but check the server keeps what it was told there: `AWAY *` under `draft/pre-away` survives a held session's revive only from nefarious2 `d9f806d` on, `CapNegotiator.finalLines`).
